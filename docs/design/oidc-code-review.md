# OIDC implementation review

Reviewed on 2026-10-04 at
[`9086d15`](https://github.com/erwinkn/coffre/commit/9086d1550788b4edcc9cc0a2a32cf88dbd5c2570),
covering PRs #100, #104, #105, #106, #107 and #110 against
[the design](oidc.md) and the [final-pass verification cases](oidc-review.md#final-pass).
References below point to that revision. Unrelated changes in the series
were examined only where they affect these paths.

**Verdict: ship after the listed fixes.** I would not release this revision
as is. There is one high, six medium and two low findings. The high finding
affects deployments with Hyperdrive query caching enabled, rather than the
cache-disabled configuration generated by coffre's setup. The replay key,
credential MAC domains and transaction boundaries held up under the checks.

## Ranked findings

### F1. High: the binding and tombstone check can return cached authorization

Location: [packages/server/src/db/queries.ts:673](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/db/queries.ts#L670-L678),
called separately from [findCredential at line 559](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/db/queries.ts#L544-L565).
Design sections 2 and 6 require the same uncached credential query.

`findCredential` selects the database clock to bypass Hyperdrive caching,
but its subsequent `bindingStands` query has no such protection. On a
cache-enabled Hyperdrive configuration, authenticate once, successfully
unbind, then restore the genuine old binding and credential rows and their
MACs as the database owner. The successful unbind remains intact. The fresh
credential read sees the restored credential, while the cached binding
read still says there is no tombstone. Authentication succeeds until that
cached answer expires or the credential does.

A probe caching only the actual PostgreSQL binding-query result reproduced
`GET /api/me` returning 200; the same restored rows through a fresh query
returned 401. This models documented caching, not a live Cloudflare test.
[Hyperdrive caches eligible SELECTs and writes do not invalidate them](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/).
Coffre's generated configuration disables caching, so it avoids this case.

Fix: join the binding and tombstone into the existing clock-bearing
credential query, as designed, or explicitly make the separate query
uncacheable. Add a cached-result restoration test. Apply the same freshness
rule to the preflight spent-token lookup at `queries.ts:705`: its cached
negative answer can send replays into the vault and commit transaction,
although the unique constraint still prevents a second issuance.

### F2. Medium: revocation records attribute an action to its target's run

Location: [packages/server/src/api/context.ts:58](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/context.ts#L55-L59),
[packages/server/src/api/signin.ts:576](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/signin.ts#L570-L598),
and [packages/server/src/api/audit.ts:211](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/audit.ts#L207-L218).
Design section 2 requires the authenticated credential's provenance on every entry.

`traced` puts the caller's `credentialId` before the operation's metadata.
`token.revoke` already uses that name for the credential being revoked, so
it overwrites the caller. With exchanged credential A, requesting
`DELETE /api/sessions/22222222-2222-4222-8222-222222222222` produced a genuine
404 denial entry naming that caller-chosen ID instead of A. If the target
is another exchanged credential B, `withRuns` attaches B's run to A's
attempt. Even an ordinary owner's revocation of B is displayed as B's run.

Fix: reserve a field for the authenticated caller and give the operation's
target a separate field, such as `targetCredentialId`. Update all credential
creation/revocation metadata and audit consumers consistently. Test both
allowed and denied revocations, including an ordinary owner acting on a
run's credential. Reversing the spread alone would lose the target.

### F3. Medium: unbinding rewrites every expired credential before committing revocation

Location: [packages/server/src/api/workloads.ts:349](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/workloads.ts#L346-L351),
using [packages/server/src/db/queries.ts:106](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/db/queries.ts#L98-L117).
This affects section 2's serialized commit and section 6's revocation.

The sweep selects every credential with this `createdBy` and no
`revokedAt`, including credentials that expired months ago. `updateAuth`
verifies and updates them one at a time, under the shared audit head.
A probe with 1,000 genuine expired credentials and one current credential
counted 1,001 credential UPDATEs during one unbind. Routine CI use builds
this history indefinitely. With 50,000 rows and 10 ms per database round
trip, the updates alone would occupy the head for about eight minutes.
Other audited operations wait, and the unbind has not committed yet.
JWKS-URL replacements take the same path.

Fix: commit the binding revocation and tombstone without rewriting the
credential history. Every subsequent authentication already checks that
binding. If credential rows need a cosmetic revocation marker, sweep them
later in bounded batches. Alternatively, restrict the synchronous sweep
to unexpired credentials with an appropriate index. Test that unbinding's
synchronous work stays bounded when expired history grows.

### F4. Medium: the anonymous candidate query scans retired binding history

Location: [packages/server/src/db/queries.ts:647](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/db/queries.ts#L647-L666)
and [packages/db/src/schema.ts:409](https://github.com/erwinkn/coffre/blob/9086d15/packages/db/src/schema.ts#L399-L410).
Design sections 1 and 2 bound the initial lookup by live bindings.

The index contains only `(principal, issuer)`. Immutable replacements leave
all retired rows in that range; `revoked_at`, generation and the ordering
are filtered afterwards. `LIMIT 17` bounds returned candidates, not the
history examined. After repeated workflow or release-tag replacements,
any stranger naming that service and issuer pays for its full history
before their signature is rejected.

With one live binding and 50,000 retired bindings, PostgreSQL's actual
query plan scanned and filtered all 50,000 retired rows. The existing
query-count test is real, but its index assertion disables sequential
scans and uses a tiny fixture. It proves that an index is available, not
that irrelevant history is excluded.

Fix: add a partial live-binding index supporting the principal, issuer,
current generation and requested order, for example
`(principal, issuer, generation, created_at, id) WHERE revoked_at IS NULL`,
on both engines. Retain the overflow rejection. Exercise the actual query
plan with substantial retired and prior-generation history.

### F5. Medium: the issuance-rate check scans the service's credential history under the audit head

Location: [packages/server/src/db/queries.ts:715](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/db/queries.ts#L714-L721),
called at [packages/server/src/api/workloads.ts:438](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/workloads.ts#L425-L442).
Design section 2 requires a cheap, serialized per-binding issuance cap.

`exchangesSince` filters by principal, issuing binding and creation time,
but the credential index is only `(principal, generation)`. Expired
credentials are retained. Thus every successful exchange, and every
verified request refused at the issuance cap, scans historical credentials
while holding the head needed by other audited operations. With 50,000
expired credentials and one recent credential, `EXPLAIN ANALYZE` showed a
sequential scan discarding all 50,000 expired rows to return a count of one.
The cost grows with the installation's age despite the 60-per-minute cap.

Fix: add an index on `(principal, created_by, created_at)` on both engines,
so the count visits the current binding's recent interval. A bounded count
that stops at 60 can also avoid unnecessary work. Test the plan against a
large historical fixture. Expired-row cleanup is useful but must not be
the only thing keeping this critical section short.

### F6. Medium: Node drains rejected HTTP bodies outside the size bound

Location: [packages/server/src/workloads/node-transport.ts:63](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/workloads/node-transport.ts#L61-L72).
Design section 4 bounds discovery and JWKS responses at 64 KiB.

For any non-200 response, `read` calls `response.resume()` and immediately
rejects. The 64 KiB counter is installed only for a 200. A failing issuer
or CDN can therefore send a large 503 or redirect body after the exchange
has already returned and released its in-flight slot. A local HTTP probe
sent 2 MiB in about 400 ms after the transport rejected the response at
its headers. The five-second deadline remains, but the byte bound and
in-flight accounting no longer cover this work. Discovery and lookup use
the same transport.

Fix: destroy/cancel non-200 responses before rejecting, as the Workers
transport does, rather than drain them. Test a streaming error response
and assert that rejection closes its connection promptly. Keep the
existing deadline over connection establishment and successful bodies.

### F7. Medium: a cold unknown-kid request fetches JWKS twice

Location: [packages/server/src/workloads/keys.ts:79](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/workloads/keys.ts#L76-L93).
Design sections 2 and 4 allow at most one key fetch per exchange.

On a cold or expired cache, line 81 fetches the current keys. If the
request names an absent `kid`, verification then enters the rotation
branch and line 91 immediately fetches the same URL again. An unsigned
attacker only needs a known service/issuer and an invented key ID. A probe
observed two fetches for the first request and zero for the next request
during cooldown. Cold concurrent isolates multiply the first-request
cost. The existing rotation test starts with a populated cache and misses
this case. If the second set still lacks the key, this first request also
returns 401 rather than the specified issuer-unavailable 503.

Fix: track whether this request already fetched. A missing key in that
fresh result must start cooldown and return `IssuerUnavailable` without
another fetch. Preserve the one refresh for an unknown key in an older
cached set, and keep valid fresh cached keys usable during cooldown.
Test cold, expired, warm and concurrent-cold cases with explicit fetch counts.

### F8. Low: forged tokens for a bound issuer cause an extra migration query

Location: [packages/server/src/api/workloads.ts:407](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/workloads.ts#L395-L421).
Design section 2 and the review brief require one initial indexed query
before the token proves it matches.

After finding a candidate, the exchange counts the migration ledger before
verifying the token. A valid-shaped token with the right service/issuer
and an all-zero signature caused two actual SQL statements: candidate
lookup and `SELECT count(*) FROM drizzle.__drizzle_migrations`. It caused
no vault call. The existing one-query test only exercises requests with
no live candidate, so it passes without covering this anonymous traffic.
The extra work is small but repeated for every admitted forgery aimed at
a known binding.

Fix: defer this migration check until after signature, audience, time and
claim verification, immediately before the spent-token table is needed.
Retain the missing-binding-table fallback. Extend the statement-count test
to bound-issuer invalid signatures and valid signatures with mismatched claims.

### F9. Low: the maximum accepted token age is 3,630 seconds, not 3,600

Location: [packages/core/src/identity/workload-token.ts:111](https://github.com/erwinkn/coffre/blob/9086d15/packages/core/src/identity/workload-token.ts#L108-L115)
and [packages/server/src/api/workloads.ts:435](https://github.com/erwinkn/coffre/blob/9086d15/packages/server/src/api/workloads.ts#L432-L437).
Design section 3 explicitly requires `t - iat <= 3600`.

`jose` applies `clockTolerance` to `maxTokenAge`, and the commit check
explicitly adds the same 30 seconds. A correctly signed assertion with
future expiry and an `iat` 3,629 seconds ago was accepted; 3,631 seconds was
refused. This extends the documented exchange window by 30 seconds. It
does not defeat the two-hour replay-retention requirement.

Fix: explicitly enforce the exact one-hour age bound during verification
and at commit, sharing the predicate. Keep the separately specified
30-second tolerances for expiry, not-before and future issuance. Test
3,600 seconds and immediately beyond it, including time elapsed before commit.

## What should be kept

- Hashing the received `header.payload` and consuming it globally in the
  same transaction as the credential and `token.exchange`. The ES256 twin
  and concurrent replay tests exercise the exchange itself. An injected
  failure after credential insertion rolled back all three writes; the
  same assertion succeeded on retry.
- Vault access follows binding MAC checks, signature/audience/time/claim
  validation and the spent-token lookup, outside any app transaction.
  Commit takes the audit head and rechecks membership, binding and time.
  Forced expiry and a remove/re-admit between the vault snapshot and
  commit both refused issuance without consuming the assertion.
- Server-enforced profiles and exact string matching, including immutable
  GitHub repository/owner IDs, caller ref plus pinned reusable callee,
  GitLab namespace plus project IDs, and explicit organization-wide trust.
  `push`, `workflow_dispatch`, `schedule`, and `release` are the allowed
  GitHub events; PR and `workflow_run` events remain refused. Custom
  issuers require `sub`.
- MAC coverage includes the binding ID and canonical claim serialization.
  The `binding:<id>` credential representation is sound under the current
  verifier: the distinct MAC domain covers `createdBy`, so stripping,
  adding or repointing the marker invalidates the MAC. Binding ownership
  and generation are checked at every authentication.
- Only successful app-authored unbinds for the exact ID are tombstones.
  Their presence across retained history is enough to deny; their MAC
  need not be checked to grant nothing. The 16-binding cap and replacement
  policy are enforced under the audit head.
- The Node resolver validates every returned address at connection time,
  preserves the TLS hostname, and blocks private, shared, mapped and
  transition address ranges. Workers uses public fetch. Discovery and
  the authenticated lookup route share the transport. Keep no redirects,
  no header-supplied key URLs, fixed RS256/ES256, and RSA's 2048-bit minimum.
- Workers JWKS state holds settled documents and timestamps, never shared
  pending promises. The concurrent-cold test actually waits for both
  independent fetches to start. Both admission scopes are required and
  limiter failures refuse; the documented per-location/per-process
  approximation is accurate.
- Normal app and vault entries carry the verified credential ID, with UUID
  validation and no vault authorization decision based on it. Both vault
  transports preserved it in execution checks. Audit joins survive
  credential deletion, and the run label is a React text child, not HTML.
- The CLI exchanges through request bodies, keeps the returned credential
  in memory and masks both credentials during GitHub export. The Action
  passes the service through the environment, and GitHub token acquisition
  sets the instance URL as audience. Access mode refuses workload auth.
  Production public origins reject the loopback-development switch.

## Verification and remaining coverage

The following checks ran with Node 24.21.0 and pnpm 11.8.0. PostgreSQL used
the restricted runtime login and isolated scratch databases.

| Check | Result |
| --- | --- |
| Core workload/profile/token, server binding/exchange/transport, and CLI workload suites on SQLite | 47 passed; the PostgreSQL-specific statement-count test was skipped |
| Server binding/exchange/transport and runtime-role suites on PostgreSQL | 36 passed, including the real statement-count test |
| Vault credential provenance through local workerd RPC | Passed, including invalid UUID rejection |
| Additional PostgreSQL probes | Confirmed F1, F2, F3, F4, F5 and F8; rollback after credential insertion, commit-time expiry, and generation change refused safely |
| New code with workload tables actually absent | Existing service authentication worked; workload operations returned migration-required errors |
| Additional transport/token probes | Confirmed F6, F7 and F9; RSA-1024 refused; the 16 KiB streaming reader cancelled excess input; Unix-socket provenance and UUID rejection passed |
| Public-origin variations | Non-loopback hosts, userinfo, fragments, lookalike hosts and mapped IPv6 refused; numeric/short IPv4 spellings that normalize to actual loopback remained loopback |

The Final pass's denied-versus-allowed unbind, row restoration, concurrent
binding-cap, caller-ref, namespace, replay-twin and JWKS-replacement cases
exist and passed on both database engines. F1 shows why the plain-database
restoration case is insufficient for cache-enabled Hyperdrive. Existing
exchange/unbind and JWKS-replacement races use `Promise.all`; they exercise
concurrency but do not force every interleaving. Keep deterministic barriers
around the precommit boundary when extending them. The additional
generation-change and expiry probes did force that boundary.

Migrations 0002 and 0003 are additive. Old credential/identity columns are
unchanged; new code degrades when the new tables are missing. Runtime-role
checks passed. The new grants permit binding SELECT/INSERT and only the
intended mutable columns, consumed-token SELECT/INSERT, and no vault-role
access to those app tables. There is no per-user RLS policy on these app
authentication tables; vault/audit isolation continues through the existing
roles and policies. This review did not rerun the complete disposable-cluster
`test:schema` workflow.

Two implementation choices differ from the literal proposal without
creating another authorization finding. The MAC-protected `createdBy`
marker replaces the proposed column and composite foreign key, leaving
that relation enforced by authentication code. Consumption records are
retained indefinitely, rather than pruned after two hours. That preserves
single use but leaves a storage-maintenance requirement; future pruning
must retain the full acceptance window and never delete unbind tombstones.

The repository documentation check found only the two existing references in
`AGENTS.md` to the not-yet-generated UI route tree in this fresh checkout.
The new report's links and source line references were checked separately.

This was a code review with focused execution, not a full release validation.
It did not run live GitHub/GitLab jobs, deployed Cloudflare Hyperdrive caching,
the full build, or the full conformance suite. Temporary probes were removed;
this PR changes only this review document, with no implementation or design edits.

Where the fix differs from the one suggested:

- **F1 keeps a separate query, made uncacheable, rather than a join.**
  `findCredential` runs on every request, and must work on this release
  before `coffre migrate` has made `service_bindings`; joining that table
  would break every sign-in in that window. The binding query runs only for
  exchanged credentials, which cannot exist before the migration.
- **F2 leaves `token.exchange`'s `credentialId` as it is.** The credential
  it issues is the run's own, the request has no credential of its own to
  record, and `audit_log_exchange_idx` (0003) finds runs by that field.
- **F3 also bounds the members page and the sweeps of member removal and
  re-admission.** They read every credential a member ever had, which a CI
  service runs to thousands, the same history as the unbind.

`0004_live_indexes` only adds indexes, so this release works before it runs,
on the same queries, more slowly. Like 0002 and 0003, it builds them with a
plain `CREATE INDEX`, which holds writes to `credentials` and
`service_bindings` for as long as the build takes.
