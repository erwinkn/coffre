# 0.15's log: the schema (W215)

PR 2 of 0.15's plan ([`0.15-plan.md`](0.15-plan.md)). It ships
the tables, columns, functions, grants and login that 0.15's hot path
runs on, as one expand migration: `0022_log_015` on Postgres,
`0018_log_015` on SQLite. 0.14.5 serves on it unchanged; 0.15 runs on it,
its log the default since the plan's PR 10.

The design is W208's and W211's "one call per use"
([`hot-path-one.md`](hot-path-one.md)), the Merkle checkpoints of W209 and
W212 (#365, #368), and the spec on main: [`HotPathOne.tla`](../../formal/HotPathOne.tla)
for uses, changes and the cap, [`Migration015.tla`](../../formal/Migration015.tla)
for 0.14's writers beside them. The tests name the invariants they hold.
This page says what the schema adds and how it is tested; the calls made
porting the prototype, with their numbers, are in hot-path-one.md.

## What it adds

- **The log**, numbered from one sequence, `log_number`, every number
  taken under the fence's lock:
  - `log_changes`: every write to a decision input, kept for good. Its
    index `(object, number) INCLUDE (seal)` gives each input's newest
    change from the index alone.
  - `log_uses`: the slim row (R53), partitioned by the day of `at`
    (`make_day`). One index, `(at, request_id)`, the replay's.
  - `log_reads`, `log_read_days` and `log_reads_cursor` (T166, 0049):
    each sealed use as the audit pages list it, on the whole log and by
    member, written by the vault's projector apart from sealing,
    partitioned by day with the uses (`make_reads_day`); the days each
    member read on, which their pages read alone; and how far it has
    gone. The app reads them; only the vault writes them
    (`project_reads`). Since 0050 (T175), by place too: an index on each
    column of `log_reads` naming a place, and `log_read_place_days`, the
    days each key, environment and project has reads on, which triggers
    on `log_reads` write (`log_reads_at` reads them).
  - `log_bulk`: the bulk cap's last use of each key per principal.
  - `log_fence`: the floor of `at`, raised by each barrier.
  - `log_checkpoints`: the signed pair of tree heads, one row a tick.
  - `log_tiles`: both trees' tiles, the uses tree's leaf tiles partitioned
    by leaf range (`make_tiles`), its levels above in one table.
- **Seals**: a nullable 16-byte `seal` on each table one of W216's
  objects lives in (PR 3): `vault_members` (a principal, its grants under
  it), `credentials` and `service_bindings` (both credentials),
  `environments` (with a new `protected`, which 0.14 keeps in its policy's
  entries), `secrets` (its current version and a reference's source under
  it). The policy and the roles, which no table held, get `log_config`,
  one sealed row each.
- **Functions**, each `SECURITY DEFINER` (but `log_object`), run by the vault's group alone:
  - `use_credential`, a use in one call, in the prototype's two forms
    (with the seal probes, and without, for the seal cache). A use stamped
    more than a minute past the database's clock answers `ahead` and
    writes nothing: past that, a proof would not find it from its window
    (W217, #376);
  - `change_input`, a change: a member's queue and row, 0.14's head, then
    the fence exclusive (that order everywhere); a retry finds its entry; a
    row that is not its object's newest change's is refused `stale`
    (ChangeChecksSeal); CAS on the object's seal (ChangeCAS). It knows one
    op, `genesis`, the cutover's (plan, PR 9). PR 4 adds the ops that
    change what a row says;
  - `close_one`, the checkpointer's barrier, which also answers the floor
    it found, for the checkpointer to hold against its last signed one;
    `write_checkpoint`, the checkpointer's write, tiles and the pair of
    heads in one call, a tile only growing (W217, #370); `prune_bulk`;
    `make_day`; `make_tiles`;
  - `log_object(kind, id)`, an object's key: the first 16 bytes of
    SHA-256(`coffre.object.v1` 0x00 kind 0x00 id), as a uuid, kinds
    `principal`, `credential`, `secret`, `environment`, `roles` and
    `policy` (the last two with id `instance`). W216's `objectKey`, held
    to its vectors.
- **OldWritesFence**: a trigger on 0.14's `audit_log` that takes the 0.15
  fence exclusive for every allowed entry but those W211's
  `Migration015.tla` lists as changing no input: reads and uses, sign-ins,
  and the log's bookkeeping and alarms. A sign-out revokes a credential,
  so it fences; so does any action the list does not name.
- **`coffre_vault_hot`**, the hot path's login: a member of `coffre_vault`,
  with `lock_timeout` 1 s, `statement_timeout` 2 s and
  `plan_cache_mode = force_generic_plan`. It is made unable to log in;
  0.15's `coffre setup` gives it a password (plan, PR 5).

## What it does not do

- **No caller.** The functions are the spec's actions as the prototype
  wrote them. PRs 4 and 5 call them, and may replace them in a migration
  of their own, which nothing stops while nothing calls them. PR 4a's
  `0023_change_path` does: its `change_input` takes every op of the
  vault's own inputs (0.15-plan.md, "As built: PR 4a").
- **SQLite gets the tables, not the functions.** It has one writer, so
  the fence is implicit (plan, "Postgres serves; SQLite is for tests").
  It has no sequence: the PR that writes the log there numbers entries.
- **No days, no tiles' ranges.** `make_day` and `make_tiles` make them;
  the checkpointer calls them ahead (plans PR 6 and 7). Migration 0035
  makes the first days (yesterday's, today's and the next three, the
  checkpointer's `daysAround`), so that a use on a database just migrated
  does not wait for the checkpointer's first run (T143).

## Tests

- `pnpm test:schema` runs `packages/db/test/log-guarantees.sql` as the
  vault's login, on the shared cluster and on a non-superuser owner's:
  writes refused but through the functions, the hot login's settings,
  the object keys against W216's vectors, genesis and its CAS, a use, its
  replay, a cover, the seal cache, the cap, the deadline, the floor, the
  barrier, pruning and the checkpoint's write. `log-owner.sql`, as the owner: a policy row put
  back moves no cap, and partitions are known by their bounds. Over two
  sessions: a 0.14 revoke's entry waits for the fence and a read's does
  not; a 0.15 change passes a 0.14 write in flight on the same member; a
  use that waits past its deadline writes nothing.
- `packages/server/test/db/log-015-migration.test.ts` migrates a database
  0.14.5's schema made and used, on both engines, and holds 0.14.5's
  reads and appends to it after.
- `pnpm test:compat` runs 0.14.5's own conformance on this schema.
