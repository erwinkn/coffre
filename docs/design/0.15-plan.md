# 0.15: the implementation plan (W211)

How the hot path of [`hot-path-one.md`](hot-path-one.md) (W208, W211) and the
Merkle checkpoints of W209's `merkle-checkpoints.md` (#365, with W212's tree
shape, #368) become shipped code.
It is a sequence of pull requests, each of which leaves `main` shippable.
Written 2026-10-27, after Erwin's decisions R50 to R55.

## The rules every PR follows

- **The spec comes first (R45).** PR 1 is the TLA+ spec, and every later PR
  names the part of it that it implements. A PR that changes a protection
  changes the spec in the same PR. TLC must fail without each protection.
- **Behind one switch until the end.** The 0.15 path is built next to the 0.14
  path behind one internal setting, `log: '0.14' | '0.15'`. It is not a
  deployment option: the default stays `'0.14'` until PR 10 flips it (done:
  "As built: PR 10").
  - Until the flip, a release behaves exactly as 0.14.5, and `pnpm test:compat`
    (0.14.5 against this checkout's schema) stays green.
  - Each PR runs the suite on both settings, so the new path is tested as it
    grows.
  - 0.16 removes the 0.14 path (the contract step).
- **Migrations only add (AGENTS.md, expand then contract).** 0.15's migration
  adds tables, nullable columns, functions and grants. 0.14.5's code keeps
  serving on it until the deploy. What 0.15 stops using is dropped in 0.16.
- **Postgres serves; SQLite is for tests.** The hot path is Postgres-only
  (R50). SQLite (tests, local development) gets the same `decide`, `applyOp`
  and replay, in one `BEGIN IMMEDIATE` transaction per call. SQLite has a single
  writer, so the fence is implicit: every guarantee the model checks holds
  trivially there. One test file runs the same cases on both engines.
- **Reviews (R29).** Muse on every PR. Each PR marked **high** also gets
  Fable, once, after Muse passes.
- **Numbers.** Every PR keeps `pnpm bench:workers` and `request-cost.test.ts`
  within the budgets measured here: about 0.6 ms of Postgres CPU per use, 1
  statement, under 30 buffers, flat as the log grows (R48).

### 3. Seals, decisions and replay as pure code (high: auth, crypto)

- **Scope.** In `packages/vault`, beside `decide.ts`:
  - **The object model.** Every decision input is one object with a seal,
    HMAC-SHA256 cut to 16 bytes under the row key:
    - principal: the member, its grants, its role assignment;
    - credential: a token or binding, with its scopes;
    - secret: a value version, with its nature and wrapped key; a
      reference's holder key carries its `source`;
    - environment: with its slug, protection, parent and owner (forks, `@me`).
      A slug-scoped role decides on the slug, so a rename is a change
      (`environment.rename`), and 0.14's `environment.update` takes the
      0.15 fence during the cutover (PR 2's trigger);
    - roles: the role tables, as one object;
    - policy: the deployment's cap configuration (`bulkLimit`), as one
      object.
    - 0.14's `Policy` value is rebuilt from the roles object and the
      protection of the environments read.
    - **An object's key** is the first 16 bytes of SHA-256('coffre.object.v1\0'
      + kind + '\0' + id), as a uuid (W216).
  - **The use row** (W216) adds what the replay needs:
    - `purpose` and `keepsSensitive` in one smallint: the purpose's code
      (0 reveal, 1 run, 2 compare, 3 copy, 4 use, 5 expose), plus 256 when
      a copy keeps values sensitive (schema 0022; `purposeCode`);
    - `at`, the place, a uuid, or NULL when it is the key's environment.
  - **Pure functions:** `applyOp` (a change applied to a state), `decide`
    (stale and tampered per input, then the 0.14 rules, then the bulk cap),
    `bulkStep`, and the replay.
  - **Cost:** each seal is one probe on a cache miss (measured: about 25 µs
    each, uuid keys about 20% cheaper than the prototype's text keys).
    - A plain use reads about six inputs.
    - A use through a reference reads the holder's secret, its source, and
      up to three environments: up to nine probes.
    - PR 5 measures the worst case against the budget of under 30 buffers
      per use.
  - **The bulk cap:** others counted over `window + refresh + deadline`. That
    is TLC's finding: uses are decided in number order, not by `at`.
- **Files.** `packages/vault/src/decide.ts`, and new modules for the objects,
  replay and bulk; `formal/lean` in the same PR. `pnpm formal:lean` holds
  `decide` to its model, so the Lean model learns stale, tampered and the cap.
- **Spec part.** `HotPathOne`'s `Decide`, `ReplaySound` and the cap rule.
- **The cap's configuration is a sealed input** (review r1, W216).
  - **Where it lives:** every change to the policy object carries the whole
    policy as its `value`, `count` and `windowMs` included.
  - **How a use reads it:** `use_credential` reads the newest policy change's
    `value.bulk`, in the use's own snapshot, never the policy row: the
    statement moves the cap before anyone checks the row's seal, so a row
    put back would move it otherwise than the replay. It is not a call
    parameter either. So during a deploy where two configurations coexist,
    live still equals the replay, and a stale policy row is refused `stale`.
  - **How it changes:** at every vault start, before it serves a use, the
    vault writes a policy change under the fence whenever the log's policy
    differs from its `bulkLimit`. The cutover (PR 9) writes the first one.
  - **Spec:** `HotPathOne` models it as protections `CapFromPolicy` and
    `CapSealed`.
  - **Test:** change the count, restart with two configurations serving at
    once, and hold the replay to live across the change.
- **Tests.** Unit tests; hegel property tests that `decide` over `applyOp`'s
  replay equals `decide` over the rows whenever the rows are the replay's,
  and differs only as `stale` or `tampered` otherwise; `pnpm formal:lean`.

### 4. The change path (high: locking)

- **Scope.** Every vault write to a decision input becomes one call to
  `change_input`:
  - the fence exclusive, a CAS on the object's seal, the payload applied as
    logged, the entry numbered under the lock;
  - **a seal check on the base row** (`HotPathOne`, ChangeChecksSeal; Fable
    on PR 1). Under the lock, `change_input` refuses `stale` unless the
    row's seal equals the object's newest change entry's seal: one probe of
    `log_changes`, as a use makes.
    - **Why the CAS is not enough:** it only compares with what the vault
      read. A row a writer put back passes it, and the change would seal its
      payload applied to the tampered base, re-sealing the rollback.
    - **Example:** revoke B seals {A}; a writer puts back {A,B}; a grant of
      C would seal {A,B,C}, and B would be served.
    - **Who builds it:** PR 2's `change_input` gets the probe too.
  - it answers once the entry is sealed (R51; until PR 6 lands, once
    committed).
  - The app's other audited writes (none of them a decision input) append
    to `changes` under the fence shared, as uses do. They never wait for a
    use.
- **Files.** `packages/vault/src/store.ts`, `vault.ts`, `log.ts`, and the
  server's writes through the vault.
- **Spec part.** `HotPathOne`'s change actions: `ChangeLocks`,
  `ChangeNumberUnderLock`, `LockToCommit`, `CommitBeforeAnswer`, `ChangeCAS`.
- **Lock order: row, head, fence** (`Migration015.tla`, ChangeHeadFirst,
  RowFirst). Until 0.16, a 0.15 change also advances 0.14's fence (PR 9).
  - **Row:** it takes the object's member queue lock first, as 0.14's
    `lockMembers` does: 0.14 takes member rows before its head.
  - **Head:** then 0.14's head.
  - **Fence:** then the 0.15 fence.
  - **Any other order deadlocks:** with a 0.14 write under PR 2's trigger,
    with a 0.14 decision holding a member row, and with a vault start on the
    cutover's slow path. Postgres breaks such a cycle only after 1 s, while
    the fence blocks every use.
- **Tests.**
  - The integration fixture's transaction tracking, kept, so that no vault
    call happens inside an app transaction.
  - fence-one's cases as integration tests: the replay of a change, another
    payload under its request id, two changes to one object.
- Behind the switch.

#### As built: PR 4a (W218), and what waits for 4b

PR 4 is two pull requests (coordinator, 2026-10-27). The vault's own
inputs go first: members, grants, the roles, the bulk cap, an
environment's protection and slug. The app's writes to credentials,
bindings, environments and secrets come in 4b (T117). There are about
40 of them, in `signin.ts`, `workloads.ts`, `services.ts`, `projects.ts`,

may not call the vault, and a secret's version carries ciphertext that

up to a tick (500 ms) for its seal (R51).

What 4a builds:

#### As built: PR 4b (W220), the app's writes to credentials

4b is two pull requests too. This one routes every write of the app's
that makes or ends a **credential**: sign-ins, tokens, handles, CI and
workload sign-in, renewal, sign-out, revokes, a member's removal and
re-admission, unbinding, the legacy scope seal, and the APP_KEY
rotation's sign-outs. Environments and secrets follow in the next one,
on the same mechanism (below, "As built: PR 4b, part 2").

**The design.** The vault prepares, the app commits, and the vault
answers once sealed:

1. **Before the app's transaction,** the app sends the vault
   (`Vault.prepare`) each row it will write: its columns as it read them,
   with their seal, and as it will write them. The vault reads nothing.
   - It checks the seal is its own over the columns it was given
     (`tampered` otherwise).
   - It works out the ops that turn the before into the after
     (`opsBetween`: `credential.issue`, `.scope`, `.renew`, `.revoke`).
   - It applies them with the replay's `applyOp` and seals each one. It
     refuses any other difference, such as a principal changed or a revoke
     undone.
   - It returns each change sealed and MAC'd.
2. **In the app's transaction** (`audited()`), once its rows and its 0.14
   entries are written, all of the changes go in one round trip of
   `app_change` (migration 0025). It is a definer function that only
   `coffre_app` may run:
   - 0.14's head, which `audited()` already holds, then the fence
     exclusive;
   - a retry finds its entry by request id;
   - ChangeChecksSeal: the row's seal is its object's newest change's;
   - ChangeCAS: the seal moves only from the one read;
   - the entry, numbered under the lock.

   The app writes its rows itself, as 0.14 does, and `app_change` writes
   only the seal.
3. **After the commit,** the app asks `Vault.waitSealed` for the newest
   number (R51), then answers.

The row and its change commit together or roll back together. No vault
call is made inside a transaction: the fixture's guard holds that for
the two new calls too.

**Example.** Ada revokes token T, whose row is (live, seal S1):
- the vault's `prepare` gets (live, S1) before and (revoked) after, and
  returns `credential.revoke` from S1 to S2;
- the transaction sets `revoked_at`, appends 0.14's `token.revoke`, then
  calls `app_change`. Under the fence, the row's seal is S1 and so is
  T's newest change: S2 is written and the entry numbered;
- the commit, then `waitSealed(n)`, then 200.

If a writer had put back T's row from before an earlier revoke, the seal
would be valid (the vault made it once) but not T's newest. `app_change`
refuses it as stale, and the whole write rolls back.

**Sets chosen under the head.** Some writes revoke "every live credential
of X": a member's removal, an earlier membership's, a binding's, an
account's sessions, a rotation step's. The app reads the set before the
transaction to prepare it, and reads it again in the transaction. They
must be the same (`AppChanges.expectRevoked`). Otherwise another write
came between, and the write is prepared again (`retrying`, three tries).
Without that check, a credential issued in between would be revoked with
no change: its row would be revoked while its log said live.

**What a workload's proof decides under the head** (an enrollment's
scope and end, `kind.commit`): the first try prepares with the binding's,
and if the proof decided otherwise, the write is prepared again with what
it decided. Those are database facts, so the second try matches.

**Answers to the brief's questions:**

1. **Atomicity:** as above.
2. **Secrets:** next PR. Ciphertext stays in `secret_versions`: the object
   is W219's `secretObject`, which holds the version id, the nature and
   the wrapped key. It does not need a digest of the ciphertext. Each
   version has a fresh data key, and the envelope's AEAD binds the
   ciphertext to it, so a swapped ciphertext fails to open.
3. **R51's wait on hot paths:** milliseconds, not the 250–500 ms feared.
   `sealThrough` ticks at once, rather than waiting for the 500 ms beat.
   Numbers are below. R51 stands for every change, issuance included,
   and nothing is left for Erwin to decide here.
4. **The gaps W218 found:**
   - `revokePriorMembership` and `removeMember` now log each revoke as a
     change.
   - `renewSession` runs in `audited()` (the head first) with its
     `credential.renew` change. It still writes no 0.14 entry ("the
     session's last use shows it"), and with 0.14's log it is unchanged.
   - A project's deletion, which tombstones its slug but not its
     environments', is the next PR's.

**Bindings are no input of 0.15's.** No decision of 0.15's reads a
binding, so no change of the log is made of one, and its seal stays
unused:
- `use_credential` reads `credentials` only.
- A credential issued through a binding now carries the binding's scope
  in its row: `exchangeToken` copies it with 0.15's log on, which 0.14
  ignores (it reads the binding's).
- A workload's session carries its effective scope, `sessionScope`, the
  binding's reads included.
- A binding's end revokes what it issued, each revoke a change.

**Decisions:**

| decision | instead of | why |
|---|---|---|
| the vault prepares from columns the app hands it, and checks their seal by HMAC | the vault reading the rows itself | It needs no grant on `credentials` and no database round trip. Under the fence, `app_change` holds the seal to the object's newest change, so a valid but stale seal is caught there (ChangeChecksSeal). |
| the app writes its rows; `app_change` writes the seal | the vault writing the app's rows through definer functions | Those rows carry the app's MAC under APP_KEY, which the vault does not hold, and about 40 sites' logic would move into plpgsql. |
| one atomic transaction | the app commits, then the vault seals after | The vault would seal whatever the row holds, a writer's row included, which is the attack ChangeChecksSeal exists for. A crash in between would leave a row the log never covers. |
| `app_change` takes no member lock: head, row, fence | `change_input`'s member, head, fence | The app's transaction holds 0.14's head before any row. Taking a member's lock after it would wait for a 0.14 decision that holds the member and waits for the head: a cycle (Migration015App, `AppHeadFirst`; TLC finds it without). |
| the ops come from the difference of the columns (`opsBetween`) | each site naming its op | One mapping, W219's `credentialObject`, and no op for the app to get wrong. A difference no op makes fails the write. |
| R51 for every change, issuance included | issuance not waiting | It costs about 5 ms alone (below), and the rule stays one rule. |
| ticks shared by the changes waiting at once (`Checkpointer.tick`) | a tick per change | 8 changes at once wait 22 ms at p50 instead of 42 ms, and 32 at once 77 ms instead of 178 ms. Throughput is 300–490 changes/s instead of 150–220. |
| the app learns the switch from `about().log`, once per vault object | a setting of the app's own | One switch, the vault's. The runtime keeps its vault for the isolate, so it is asked once. |

#### As built: PR 4b, part 2 (W222): environments and keys

The rest of the app's writes to the objects a use decides on go through the
same `prepare`, `app_change` and `waitSealed`:
- **environments:** made (a fork's and a personal config's included),
  renamed, archived, restored, deleted;
- **keys:** a value written, marked or restored (a new version each), a
  reference made, archived, unarchived, reset to the parent's in a fork and
  overridden again, and erased with their place;
- **a project's deletion:** each of its environments too.

`prepare` takes three kinds of rows now, each mapped by W219's function
(`credentialObject`, `secretObject`, `environmentObject`), and `opsBetween`
finds the ops between the objects before and after:
- **a key:** `secret.write`, the whole object, value or reference; or
  `secret.delete`. A key's object is small and every write of it replaces
  it, so there is no finer op.
- **an environment:** `environment.create`, with the protection the policy
  gives its id (a protected fork's: `protectIds` protects the id before the
  row exists); then `.rename`, `.archive` (both ways), `.delete`, in that
  order. Its protection stays the vault's (4a's `environment.protect`).
  A change of the app's to it, or to a parent, an owner or a project, fails
  the write.

**What of a key enters the log** (the brief's question 3): the version's id,
its nature, its KEK's ids and its wrapped data key. Never the ciphertext,
the IV or the tag, nor a digest of them (a test holds the payload to that).
That is enough, because each version has a data key of its own and the
envelope's AEAD binds the ciphertext to it:
- a writer who swaps in another version's ciphertext gets a value that
  fails to open with the sealed key: refused, never served;
- a writer who swaps the wrapped key changes the object: `tampered`.

**An archived key is no object.** Archiving is `secret.delete`, whose seal
is none, and `app_change` writes none on the row. `use_credential` reads
only unarchived keys, so the row and the log agree: no key. Unarchiving is a
`secret.write` from no object. Example, key K sealed S1:
- archive: `archived_at` set, `secret.delete` from S1, row seal null;
- a writer clears `archived_at` around the app: the row reads live with no
  seal, and every use is refused (`stale`), as is the next change
  (ChangeChecksSeal: no seal on the row, the log has changes);
- unarchive through the app: `secret.write` from no seal, row seal S2,
  of the object the log last sealed (S1's), its rows held to it (T134:
  "Unarchives restore what the log sealed", below).

**Deletion.** Under the head, in the deletion's own transaction:
- each environment it takes (the one, its personal configs; or a project's
  every standing one) gets its tombstone and `environment.delete`;
- each live key under them has its versions erased, gets `secret.delete`
  and, with 0.15's log, is archived.
- **Why archive:** a use reads unarchived keys. Left unarchived, an erased
  key would read as an object with an empty wrapped key under no seal:
  `tampered` live where the replay says the key is gone. Archived, both say
  no key. With 0.14's log the keys stay unarchived, exactly as 0.14 leaves
  them; a test pins that.
- **A project's environments' tombstones** (T130): with 0.15's log only,
  each standing environment of the project becomes `<slug>~deleted`
  (`deletedWithProject`), in the deletion's transaction, one `UPDATE`.
  - **Why a tombstone at all:** 0.15's environment is deleted by its own
    slug (`environmentObject`: the slug before the `~`, `deleted`), and
    `use_credential` reads no project row. 0.14 takes the project's
    tombstone for its environments', and leaves them `dev`.
  - **Why undated:** a project is deleted once, so within it nothing else
    holds `dev~deleted`, and an environment deleted alone holds a dated
    one, `dev~deleted-2026-10-05`. The project's tombstone dates both.
  - **Its old path still names it.** The deletion's result lists its
    environments as they were (`dev`, `prod`), and 0.14 reads their entries
    as `coffre audit market~deleted-2026-10-27/dev`. `resolvePath`, asked for
    tombstones, takes `dev` as `dev` or `dev~deleted`: at most one exists
    (no live slug holds a `~`; only the project's deletion writes
    `dev~deleted`, and 0.14 never does). So the same path reads the same
    entries under either log, and across the cutover.
  - **Example:** `market/dev` deleted alone on the 5th
    (`dev~deleted-2026-10-05`), a new `dev` made, then the project deleted
    on the 27th: `market~deleted-2026-10-27/dev` and `…/dev~deleted` name
    the second; `…/dev~deleted-2026-10-05`, the first.
  - **The object is unchanged:** whichever tombstone, it is the slug before
    the `~`, deleted. The seal, the change and the replay are those of an
    environment deleted alone; the vault's tests run both tombstones.
  - **Spec:** no lock taken or state re-checked changes (the rename is in
    the deletion's transaction, under the head, on the environments
    `Erasure.hold` already holds to the set prepared). No model changes.
  - The cutover's half is PR 9's: "Places 0.14 deleted".

**Sets chosen under the head.** A deletion's environments and keys, and the
personal configs an archive or restore takes with their environment, are
read before the transaction to prepare their changes, then read again under
the head (`Erasure.hold`, `patchEnvironment`). A different set is a write
meanwhile: the whole write is prepared again (`retrying`), as part 1's
`expectRevoked`. Example: a personal config's owner writes `LATE` while the
config is being deleted. Without the check, `LATE`'s version would be
erased with no change logged: a live row, its wrapped key emptied, under its
old seal, `tampered` to every use. With it, the deletion reads again and
deletes `LATE` too (tested).

**A key's or an environment's state re-checked under the head.** An archive,
an unarchive or a reset is prepared from the row as read; the transaction
must find it as read: an environment archived or not, a key's object whole
(`stillAsRead`). ChangeCAS refuses a row whose seal moved, but not in two
cases:
- nothing to change: the read found the key archived already, and a key
  unarchived between the read and the transaction would be archived with
  no change;
- a change from no object (an unarchive), which moves the seal from none:
  a key unarchived, written and archived again meanwhile has none either,
  and the unarchive would seal the version it read over the one written
  (review r3's P1).
`setSecrets` and `restoreVersion` re-check the keys under the head against
their first read (`secretHeads`), so the read of the objects they prepare
from must be that state too, or the write is prepared again (review r2's
P1: a key archived and unarchived between the two reads).

**A new environment carries its protection in its row** with 0.15's log (the
app inserts `protected`; it may insert any column, and updates only slug,
name and `archived_at`). `audited` holds the caller's policy to the head
(`policyStill`), so the protection sealed is the one the policy has.

**Lock order, and the spec.** Unchanged: the head, the rows, then the fence,
as in part 1 (Migration015App's AppObject is any of the app's rows,
environments and keys included). A write of many objects, a project's
deletion, takes the head once, writes its rows, and makes all of its
changes in one round trip of `app_change`, under the fence once. The
re-reads of a set or a state under the head are app-level guards of the
same kind as part 1's `expectRevoked`, not a lock or a re-check of the
change path's, so `formal/` is unchanged; tests hold each one (below).

Decisions:

#### Uses never wait on sign-ins (T123, W224)

R58: a use never waits on a sign-in. Before this, every CI or sidecar
sign-in held every use up:
- its credential's issue is a change, and `app_change` took the fence
  exclusive for it, from the change to the commit;
- 0.14's trigger (PR 2) fenced its `token.exchange` entry too, from the
  append to the commit;
- so each sign-in stopped every use for its last two round trips (about
  40 ms through Hyperdrive), and a burst of sign-ins, one after another
  on 0.14's head, stopped them over and over.

**Why an issue needs no fence.** Nobody can name a credential before its
issue commits: its token is handed out after. And an issue changes no
input any other use reads. So no use can overlap it, and its number
orders it against every use the same whichever side of it the use falls.

**Why not the fence shared** (the first plan). Postgres queues a shared
request behind a waiting exclusive one. The checkpointer's barrier takes
the fence exclusive at every tick, and R51's waits make a tick for every
sign-in. A barrier waiting for an issue's commit round trip would hold
every use up behind it all the same.

**The design: a lock of its own.**
- An issue takes the *issue lock* (advisory key 1668244070/1) shared, and
  its number under it. It never takes the fence.
- The barrier (`close_one`) takes the issue lock exclusive, then the
  fence. It waits for the issues in flight while holding nothing a use
  waits for, then waits only for the uses in flight.
- The order everywhere: a member's row, 0.14's head, the issue lock, the
  fence. Whatever takes the fence in a transaction that may also issue
  takes the issue lock shared first: `app_change` and 0.14's trigger.
  - Example: a browser sign-in revokes its account's earlier sessions and
    issues one. Its append's trigger fences, for the revokes; then it
    issues. Without the issue lock first, it would hold the fence and wait
    for the issue lock, which the barrier holds while it waits for the
    fence: a deadlock that Postgres breaks after a second, with every use
    waiting.
  - The vault's `change_input` never issues, and takes no issue lock;
    its transaction's 0.14 entry, appended first, takes it through the
    trigger.
  - For PR 9: the cutover takes the head, then the fence. If its
    transaction appends a 0.14 entry the trigger fences, the trigger
    asks for the issue lock while the cutover holds the fence: a cycle
    with a barrier. Its order must be head, issue lock, fence, or its
    entry one the trigger lets by.
- 0.14's trigger lets `token.exchange` by, as it does `sign_in`. Its
  transaction writes the new credential, the spent token and the binding's
  last use, none of them a decision input: `decisionInputs` holds the CI
  exchange and the workload sign-in to that in the suites.
- `app_change` skips the fence only for an issue of a row its own
  transaction wrote (the row's `xmin` is its). The app issues only rows it
  inserts: `prepare` makes an issue only from no row. Any other row (one
  committed before, which a use may name, or a savepoint's) takes the
  fence as before.

**The fold.** `appendEntries` takes the write's prepared changes and runs
the `app_change` calls in the statement that appends 0.14's entries
(`WITH appended AS (INSERT …), moved AS (UPDATE head …) SELECT
app_change(…)`). One round trip less under 0.14's head, which serializes
every sign-in. On SQLite, or past 3,000 entries, they run after, as
before.

**The spec** (R45; `docs/formal.md`):
- `HotPathOne` gains issuers, the issue lock and a two-step barrier.
  - HotPathOneIssue holds (2.0M states).
  - `UsesNeverWaitOnIssues` breaks without IssueOwnLock or
    BarrierIssueFirst.
  - `CheckpointsHold` breaks without BarrierWaitsIssues or
    IssueNumberUnderLock.
  - `ReplayAgrees` breaks without NamedAfterIssue: a use numbered after
    an issue it could not see.
- `Migration015` gains the issue lock in the order, the barrier, 0.14's
  `token.exchange`, a 0.15 sign-in, and one that also revokes.
  - Migration015Issue holds (2.0M states), with `BarrierAvoidsHead`.
  - `NoWaitCycle` breaks without IssueBeforeFence or BarrierIssueFirst.
  - `ExchangeChangesNoInput` and `NothingAllowedAfterAnswer` break
    without ExchangeOnlyIssues.

#### One hot principal, cold backends (T127, T131, W228)

Two stalls left on the use path after T123, both measured there (above).
Migration `0028_use_stalls` replaces `use_credential` once more; nothing
else changes.

**T127: one principal's uses queued on its own lock.**
- **Before.** A use whose key's bulk row was stale took its principal's
  lock exclusive and read again, as a key entering the set does. One
  principal at 1,000 uses a second over 7 keys: when the keys' rows went
  stale (every refresh, a minute by default), every use that saw a stale
  row took the lock in turn, each holding it to its commit.
- **Worse than it looks.** Such a use holds the fence shared while it
  waits. The checkpointer's barrier, every 500 ms, queues for the fence
  behind it, and every other use, of every principal, queues behind the
  barrier. One principal's queue becomes the instance's.
- **The design.**
  - A key *entering* the set (no row, or one out of the window) takes the
    principal's lock exclusive, counts the other keys, and writes, as
    before. That happens once per key and window.
  - A key *in* the set whose row is from an earlier refresh period takes
    the lock **shared**, reads again, and moves the row on. Moves never
    wait for one another; an entering key waits for the moves in flight,
    so it counts every move numbered before it.
  - Every write is the start of the use's refresh period, `at − at %
    refresh`, never the use's time, and a move only raises the row. Two
    moves of one key at once write the same period, or the greater stands:
    the row ends where the replay's does, whichever commits first.
  - A move is an `UPDATE … WHERE last < period`, and one use per key and
    period makes it. The first takes a lock of that key and period's own,
    without waiting (`pg_try_advisory_xact_lock`), and moves the row. The
    others take that lock shared: they wait for the first one's end,
    never for each other, then read the row again (a plain read) and leave
    it moved, locking no row. If the first rolled back, the row is still
    stale: they elect another the same way, on the lock's next round (its
    key carries a round number), and the rest wait for that one alone.
    - **Why not a plain UPDATE** (review r1): one that waits on a row
      another is moving, then finds it moved, keeps the row locked to its
      own commit, as an upsert does. Each would queue the next: a chain of
      one commit each, at every period, on a hot key. Review r2 found the
      same chain after a rollback, when every follower ran the UPDATE: hence
      the rounds.
    - The model writes a move at its commit, so this lock changes when uses
      wait, never what the rows hold. `use.test.ts` holds it with three
      sessions (the third answers while the second still holds its
      transaction open), and with four after a rollback.
  - Both writes leave the statement every use runs. A call that took the
    principal's lock makes them in a statement of its own, after the one
    that read, in the same transaction and under the same locks. The uses
    that find their key fresh, nearly all, plan and run no write of the
    row.
  - A key is fresh while its row is from the use's own period; covers ride
    only then (CoverFresh).
  - `refresh` is at least 1 ms (a tenth of a window under 10 ms was 0).
- **Why the cap still holds, exactly.** A period starts less than a
  refresh before its use (`periodOf_lags`, Lean), which is the margin the
  set's bounds already add for a refresh's lag. No overshoot: R52's
  guarantee is unchanged (BulkCapHolds), and the replay decides each use as
  live did (BulkReplayAgrees).
- **Example.** Refresh a minute; key K's row at 10:00:00. Uses U1
  (10:01:00.020, number 40) and U2 (10:01:00.025, number 41) both see it
  stale, take the lock shared, and write 10:01:00 each. The replay, in
  number order: U1 writes 10:01:00, and U2 finds the row fresh. Same row.
  Had each written its own time, live would end at .025 (the greater) and
  the replay at .020 (U2 fresh behind U1): 5 ms apart, which decides a use
  at the window's edge 16 minutes later. TLC finds it with `RefreshPeriods`
  off.

**A hole TLC found on the way: other keys count a minute longer.**
- **What.** An entering key counts the other keys whose rows are younger
  than `window + refresh + deadline`. That margin covers a use decided up to
  the deadline after its `at`. But a use is also decided up to a minute
  *before* its `at`, when its Worker's clock runs ahead (`ahead` refuses
  only past a minute).
- **Example** (TLC's trace on 0024's rule, HotPathOneBulkSkew's constants:
  window 4, refresh 3, deadline 1, skew 1, cap 1): K1 enters at −1. At Postgres time 6, a use of K2 stamped 7
  (a Worker ahead) is decided first: K1's row (−1) is past 7 − 4 − 3 − 1, so
  K2 enters. Then a use of K1 stamped 5 is decided: K1 is still in the set
  (−1 > 5 − 4 − 3), so it passes. K1 at 5 and K2 at 7: two keys in one
  window of 4.
- **0024 has it too.** Main's model breaks the same way with the clock run
  to 9 instead of 5. With periods, rows start earlier, and TLC found it
  within the scenario's clock.
- **The fix:** count other keys over `window + refresh + deadline + 60 s`
  (`AheadSlack`; `bulk.ts`'s `USE_AHEAD_MS`, Lean's `useAhead`). Stricter,
  never looser: by default a key counts against a new one up to about two
  minutes past its 15-minute window, where it was one. R52's guarantee, at
  most `count` distinct keys in any rolling window, now holds under every
  clock the function accepts.

**T131: a new backend planned its statement under the fence.**
- **Before.** A new backend's first call planned its statement holding the
  fence shared (29 ms against 1.5 ms after), and a barrier queued behind it
  held every use up meanwhile.
- **The design.** A session's first call runs each of the four statements
  (probing or cached, plain or whole) once, dry, before it takes the fence:
  `WHERE NOT dry` is a one-time filter in the generic plan, so each reads and
  writes nothing, and its plan stays cached for the session. Then the
  session sets `coffre.use_planned` to the migration's number, so a function
  replaced again plans again. A rollback, or `RESET ALL` (`DISCARD ALL`),
  clears it, and the next call plans again, as it must then.
- **Not changed:** the lock order. The dry runs take no advisory lock
  (like any statement, they take each table's AccessShare lock to the
  commit).
- **Its price:** a new backend's first call plans four statements where
  it planned one: 56 ms against 29 ms, all of it before the fence. The cap's
  two writes, now statements of their own, are planned at a backend's first
  write, under the fence (well under a millisecond each).
- **Left:** a plan invalidated mid-session (DDL on a table the statement
  reads) is made again under the fence, once per backend: see "Left open"
  below.

**The spec** (R45; `docs/formal.md`):
- `HotPathOne`'s principal's lock is shared or exclusive, granted as
  Postgres grants it (a shared request waits behind a waiting exclusive
  one).
- HotPathOneBulk holds with `RefreshesNeverQueue` (a use whose key is in
  the set waits on the principal's lock only for one entering a key) and
  `SharedStaysInSet` (a move never needs the lock exclusive).
- Each new protection is shown necessary:
  - without `RefreshShared`, `RefreshesNeverQueue` breaks (by definition;
    the harm is the bench's);
  - without `RefreshLocks` (a move takes no lock), `BulkReplayAgrees`
    breaks: a key entering misses a move numbered before it;
  - without `RefreshPeriods`, `BulkReplayAgrees` breaks: two moves at once;
  - without `AheadSlack`, HotPathOneBulkSkew's `BulkCapHolds` breaks.
- The Lean model's `bulkRule` writes the period (`periodOf`), held to
  `bulk.ts` on generated cases; `periodOf_lags` proves the lag bound.

#### use_credential correctness (W226: T125, T126, T129)

Three gaps found on #381 (W222 and its review), closed before the flip
(PR 10) in one migration, `0029_use_objects`, which replaces
`use_credential` once more and adds one nullable column (and turns JIT
off on every function run as its owner: "JIT, found on the way",
below). Each is a part of
a row the decision depends on that no seal covered. The spec came first:
`formal/SealedObjects.tla` models which rows and columns make an object,
and TLC fails without each protection below (docs/formal.md,
"SealedObjects.tla"). The sets a write chooses under the head (a project's
environments) are app-level guards, as in PR 4b, held by tests, not by the
model.

**1. An ended reference stops serving (T125).** 0.14 ends a reference
(broken, replaced, a deletion's, R22's cut) with its vault's
`reference.end` entry alone: no row says so. 0.15's holder took its
source from its newest `secret_references` row, ended or not.
- *Example:* `billing/prod/DB` refers to `market/prod/DB`. Market's
  access manager breaks it. 0.14 refuses every read through it after;
  0.15's use kept serving market's value, and its log held nothing that
  said the reference had ended.
- *Now:* the end is in the row, `secret_references.ended_at`. A holder's
  object takes its newest row's source only while that row has not ended.
  An ended one holds neither a version nor a source, which `decide`
  answers `ended`, 0.14's code (and `formal/lean`'s model with it).
- *Who writes it:* the vault's `endReferences` decision, with 0.15's log,
  stages `secret.write { source: null }` for each holder whose standing
  reference it ends. `change_input` then writes the holder's seal and the
  row's end in the decision's own transaction, beside `reference.end`
  (EndInRow, EndWithEntry). An end the holder no longer stands on (a
  value written over it, a newer reference, or an abandoned write that
  stored no row) changes no object.
- *A holder that stands on nothing:* archived, holding a value, or on a
  newer reference. Its end changes no object, but its row still ends
  (`end_reference`), in the same transaction. Otherwise a holder archived
  when its reference was broken would read it live again once unarchived
  (review r1's P1). Since T134 its kept object is logged ended too
  (below, "Unarchives restore what the log sealed").
  The same for a standing holder 0.14's log alone holds (no seal, no
  change: before the cutover), whose change logs nothing: its row ends, so
  the cutover's genesis seals it ended (review r3).
- *What an end decides on:* only what the vault authenticates (R53), never
  rows alone, which a database writer may rename, plant or mark. Three
  reviews in turn fooled a rule read off the rows (a planted row to the
  same source, an end marked on a row, a planted row to another source, a
  renamed row id, a live holder marked archived), so:
  - the holder's object holds the id of the reference row it reads
    through, beside its source (`SecretInput.reference`;
    `use_credential` reads it from the row it already reads, no probe more).
    A row renamed, planted or ended around the vault changes the object,
    and every use refuses it `tampered` (ReferenceInObject);
  - whether the holder has an object is its log's, the seal of its newest
    change, never its row's `archived_at` (`heldByLog`; LivenessFromLog);
  - that the reference has not ended is 0.14's log's (`reference.end`,
    MAC'd), already checked before any write;
  - a holder whose object, checked against its seal, reads through the
    reference ended changes (`secret.write`, no source, no reference;
    `change_input` ends its newest row). One whose rows the log does not
    bear out refuses the end, `tampered` or `stale`: the break does not
    happen, and 0.14's entry is not written either;
  - any other end is its row's alone, by id: an abandoned reference's
    stored none, so nothing ends, and no other reference with it. A holder
    with no object (archived, or 0.14's alone before the cutover) has only
    rows, which decide nothing: an earlier version ended its newest
    same-source row too, which ended another request's reference in an
    honest race (review r8). A row planted on such a holder is the
    unarchive's to refuse (T134, below) or the cutover's.
  - who may end it (the holder's `secret.write`, the source's
    `grant.manage`) is decided twice: by 0.14's reader, and by 0.15's
    (`readerOf`, as a use's) on sealed objects alone, the actor's principal,
    the roles and each holder environment, each checked against its seal.
    An end needs both. 0.14's reads rows no seal covers (an environment's
    slug, a project's tombstone and the protection they make): a writer who
    swapped one could let a member end what they may not (reviews r10 and
    r11); with both, an unsealed row can only refuse an end. Every other
    vault decision still authorizes on 0.14's rows alone; holding them to
    sealed objects is the decision rewrite's, not an end's.
  Example: a writer renames the genuine reference's row. The holder's
  object names another reference than its seal: every use is `tampered`,
  and so is the break; renamed back, the break holds.
- *Closed by T134:* an archived key had no object, so its unarchive
  sealed what its rows held: a reference row planted to *another* source
  on an archived holder was sealed in. Its unarchive now restores the
  object its log last sealed ("Unarchives restore what the log sealed",
  below).
- `end_reference` locks the holder's row, refuses a standing reference of
  a logged holder (that end is the holder's change), a missing time, and
  ends a row once.
- *Why the vault and not the app:* the end is a vault decision (who may
  break what). Written by the app after the vault answers, 0.14 would
  hold the reference ended and 0.15 live in between, and for good after a
  crash between the two. TLC finds that window without EndWithEntry.
- The vault's login now reads `secret_references` (0029 grants `SELECT`):
  it reads each object it changes, a holder's included. Conformance
  checks the vault's writes only; this is a read.

**2. A project's archival on its environments (T126).** 0.14's snapshot
takes an environment as archived when it or its project is. 0.15's object
read the environment's own `archived_at`, so a use through a fork of an
archived project passed `throughOk`. The app refuses such a read first, so
nothing was served, but live and replay disagreed with 0.14.
- *Now:* an environment's object holds `projectArchived` beside its own
  `archived`, and `throughOk` refuses either. A project's archive or
  restore logs `project.archive` on each of its live environments, the set
  read again under the head (as a deletion's is); `use_credential` reads
  each environment's project, one primary-key probe of `projects` each.
- *Apart, not one bit (TLC's finding, ArchivedApart):* with the object's
  `archived` made of both, a writer clears an archived fork's own
  `archived_at` while its project is archived. The object is unchanged and
  its seal still holds; the project's restore then seals the edit in, and
  the fork, archived on its own, reads live.
- A deleted environment holds no project's archival: its project archived
  or restored after changes nothing of it (`environment.delete` clears it).
- `change_input` holds an environment's `projectArchived` to its project's
  row, and never writes it: the project's row is the app's.

**3. A plain value's text under its seal (T129).** A plain version's
object held `key: null` and nothing of its text, so a writer who edited
`secret_versions.plaintext` changed the value under a valid seal.
- *Now:* the object holds `digest`, the SHA-256 of the text, base64. The
  app hands the vault the text in `prepare` (it is no secret), the vault
  hashes it, and `use_credential` answers the text (`v_plaintext`), which
  the vault hashes against the seal: an edited text is `tampered`.
- *What it binds:* every use of the key, or of a reference to it, refuses
  an edited text; `prepare` refuses the next write of it; PR 8's row
  audit names it. A use of a plain value is still `bad_claim` (the app
  hands plain values back, as 0.14 does), now read under its seal.
- *Not bound yet:* the app's own reads of plain values (listings, exports,
  reveals) read the text without the vault. PR 5b, which routes reads
  through `use_credential`, decides how they are held to the seal.
- The log holds the digest, never the text: a plain value is visible to
  whoever lists its key, and its digest tells a log reader no more.

**For the offline scan (PR 8 has no row audit, D145):** each
`secret_references` row must be named by an authentic `reference.create`

not only made harmless by one (an unarchive refuses it since T134).

**For PR 9 (the cutover):**

#### Unarchives restore what the log sealed (T134, W236)

**The bug** (since PR 4b part 2, #381; found by W226 on #386). An archived
key is no object: its archive is `secret.delete`, and its row's seal is
none. Nothing checks its rows while it stays archived, and its unarchive
was a `secret.write` from no object, sealed from whatever the rows held
then. A database writer, with no vault key, could edit them meanwhile and
have the unarchive seal the edit in. Example, key K:
- K written twice, `v1` then `v2` (seal S2), then archived;
- the writer points `secrets.current_version_id` back at `v1` (or at a
  version row they planted, or plants a reference row to another source);
- an Owner unarchives K: the vault sealed `v1` (S1'), and every use since
  served `v1`, live as replayed: the log itself says so.

**The fix: an unarchive restores the object its log last sealed.**
- *What the vault holds it to* (`keptObjects`, in `prepare`): the key's
  newest change that left a seal, the archive's `secret.delete` leaving
  none. A key's every sealed change is its whole object (a `secret.write`
  or a genesis), so that change's payload is the object; its seal is
  checked over it. The rows' object must be that one, or `prepare`
  refuses the unarchive, reported as a stale row (`vault.tampered`, code
  `stale`). The app marks an unarchive `restores` (`secretChange`: an
  archived key brought back as its rows hold it: an unarchive, an
  override made again, a reference written again unchanged); a key given
  a new value or reference over its archived row is made from the write's
  own columns, and restores nothing.
- *Still so at the commit* (`app_change`'s `p_restores`, 0030): the
  vault's read takes no lock, so the change carries the seal it restores,
  and `app_change` holds it to the log's newest sealed one under the
  fence. Without it, an end committed between the two, its row's end
  cleared by the writer, leaves the rows as the prepare read them, and the
  reference is sealed live again (TLC's counterexample, RestorePinned).
- *An end while archived changes what is kept* (`change_input`, 0030). A
  reference's end on an archived holder was its row's end alone
  (`end_reference`). Held to the kept object, an honest unarchive after
  it would be refused (the rows say ended, the log live), and a writer who
  cleared the row's end would have it restore the reference live. So the
  vault's end, for an archived holder whose kept object reads through the
  reference, logs that object ended (`secret.write`, no source) and
  deleted again (`secret.delete`), in its decision's transaction, under
  the fence: still no object, and its unarchive restores it ended.
- *A key its log never held* (0.14's alone, before the cutover): nothing
  to hold it to; its unarchive logs nothing, as any of 0.14's rows'
  changes (requestId null), and the cutover vouches for it.
- *An end on an archived holder whose rows a writer edited* (moved, given
  a version) is refused and reported (`stale`), as a live holder's is:
  its rows must make the kept object (`rowsAsKept`), or the ended write
  would find none of them (Fable's review).
- *Data from before 0030:* a holder archived and then ended under 0029
  has its row's end and a kept object that is live, so its unarchive is
  refused. No deployment runs 0.15's log yet, so none has such a key.

**Why this shape.** Two were weighed (the brief's (a) and (b)):

| | an archived key keeps a sealed object (`archived: true`) | an unarchive restores what the log sealed |
|---|---|---|
| what changes | the object (a new field), the op (`secret.archive`), the replay, `use_credential` (it must read archived rows to check them, or skip them as now and decide `missing` on a row it never checked), `formal/lean`, erasure | `prepare` reads one probe of the log for an unarchive; `app_change` checks one seal; an archived holder's end logs two changes |
| one source of truth | the row's seal | the log's newest sealed change, which ChangeChecksSeal already trusts |
| cost on `/use` | a use of an archived key reads and checks its row | none |
| cost on writes | none | an unarchive: one indexed probe; an end on an archived holder: two changes |

Both refuse the same edits. The second changes no object, no use and no
replay rule, and leaves "an archived key is no object" true; the log
already holds what an archived key was.

**Rejected inside it: accepting an unarchive as "the kept object, or that
object ended".** It would have kept the end on an archived holder a row's
end alone. TLC found the hole at once (EndWhileArchived): the end
committed, the writer clears `ended_at`, and the rows make the kept,
live, object again. The end must be in the log.

**Spec** (`formal/SealedObjects.tla`): the holder's kept object (`kept`),
an unarchive in two steps (`PrepareUnarchive`, `CommitUnarchive`, and
`Abandon`), and the end on an archived holder. Three protections, each
shown necessary: without RestoreFromLog, without RestorePinned, without
EndWhileArchived, TLC breaks `AllowedAsOld` (a use through a reference
0.14 holds ended); without EndWhileArchived also `HonestUnarchive`, the
new invariant that, with no writer, an archived holder can always be
unarchived. Every scenario of the module holds with all on.

**Numbers.** `packages/server/test/bench/writes.ts`, 200 calls in turn,

### 5. The use path (high: concurrency)

Built in two parts:
- **5a (W219):** the vault's call and migration `0024_use_015`, measured in
  [`hot-path-one.md`](hot-path-one.md#the-use-path-on-main-w219-plan-pr-5a).
- **5b:** the server's routes. It comes after PR 4's two halves, because a
  use is allowed only on objects the change path has sealed.

- **Scope.** `/use`, reveals, sign and verify, and CI sign-in each make one
  `use_credential` call.
  - **The deadline:** 3 s at most from the request's time. The Worker races
    it, and Postgres holds it (R54) by `clock_timestamp()`. `now()` is the
    transaction's start, before any lock wait, and would pass a late use.
  - **Admission:** a per-isolate cap derived from the pool size, then 503 with
    `Retry-After`. Its numbers are measured in T112; they are not fixed
    here.
  - **Covers** per isolate.
  - **The entry's MAC** is the log's (`entryMac` under `logMacKey`, the
    uses tree in what it covers, KindInMac), the one the checkpointer
    checks: `use.test.ts` seals real uses on both engines (T128).
  - **The seal cache** per isolate, keyed on the log's newest change by
    number and MAC.
  - **The statement in two forms:** without the probes while the cache is
    current, with them otherwise.
  - **Generic plans** on the vault's login.
  - These three cut Postgres CPU per use from 0.72 to 0.58 ms in the
    prototype.
  - The app's `Accesses` and `pageClient` keep asking the vault once per
    request.
- **Files.** `packages/vault/src/vault.ts`, `snapshot.postgres.ts` (replaced
  by the call), `cloudflare.ts`, `node.ts`; `packages/server`'s `/use` and
  reveal routes.
- **Until 0.16, a use also sees 0.14's writes** (`Migration015.tla`,
  UsesSeeOldWrites).
  - **The check:** the use reads its object's newest authentic 0.14 access
    entry, and is `stale` until the new log accounts for it.
  - **Why:** without it, there is a one-tick window after a late 0.14 write
    in which a writer who puts the old row back is served.
  - **Cost:** one more probe per use, measured here against the budget
    (under 30 buffers, about 0.6 ms).
  - **Kept** by the coordinator: a revoke that does not hold for a tick is a
    revocation hole.
  - **The cheaper alternative, weighed and rejected** (`Migration015Marker`):
    PR 2's trigger marks the object's row stale, and the use refuses on it,
    with no extra probe. A writer who can put a row back can also clear an
    unsigned column, so the marker alone is as weak as no check (TLC).
    - Defeating the probe needs deleting or editing a MAC'd 0.14 entry. That
      also defeats 0.14's own `#integrity`: it is 0.14's guarantee, no
      weaker.
    - The probe costs one `audit_log` index probe per use (about 25 µs and
      2–3 buffers, about 4% of the budget; this PR measures it).
    - The marker's only use would be on top of the probe.
- **Risk: the probing form is over budget.** W215 measured the call on the
  real tables (#372) at 0.74 ms probing and 0.38 ms from the seal cache,
  against the prototype's 0.42 and 0.26 ms on the same container. Weighted
  by Cloudflare's 27% probing share, that is about 0.48 ms a use.
  - **The answer if PR 5's bench misses** the ~0.6 ms budget: the cuts of
    the decision log (the fence and bulk rows read once, roles and policy
    grouped, fewer plan nodes in the probing form).
  - **Reference uses** (up to nine probes) are measured on their own.
- **Spec part.**
  - `HotPathOne`: `UseLocks`, `StatementSnapshot` (the function, never a bare
    CTE), `UseNumberUnderLock`, `ReleaseAfterCommit`, `SyncCommit`, covers.
  - `HotPathOneClock`: `DeadlineChecked`, `FloorChecked`, the cap.
- **Tests.**
  - fence-one's cases as integration tests: the bare-CTE trap, replays, late
    calls, the floor, rollback of each input, the cap at count 10 over a
    day, covers, and the deadline in Postgres.
  - `request-cost.test.ts`: one statement, buffers flat from 10k to 1M
    entries.
  - Conformance: live equals replay on every run.
- Behind the switch.

#### As built: PR 5b (W232): the app's reads through `use_credential`

**The switch.** The vault says it answers uses (`about().uses`): 0.15's
log, and the hot path's login. The app asks once per vault and keeps the
answer (`uses015`, beside `keeps015`).

**One door.** Every value the app opens goes through `openValues`
(server `keys.ts`): a reveal or a run (`POST /api/reveals`, `coffre
run`, `export`), the credential proxy's use, sign, verify and tunnel
checks, a CI run's reads after its sign-in, a dry run's compare, and a
fork's copy. With the switch on and a credentials row behind the
request, each sealed value is one `use_credential` call (`useValues`).
- **Example:** Ada's `coffre run` of 9 keys makes 9 uses, 4 at a time
  (`USES_AT_ONCE`, so a whole environment leaves the isolate's admission
  room). Her grant revoked after the 4th: the 5th is refused, 403, and
  nothing goes back. Every request is logged, refused ones included.
- **A plain value** asks no vault, as before.
- **A reference** names its holder key (`holder`); the vault finds the
  source as it reads it then. A fork's inherited key names the fork as its
  place.
- **What goes back** is the version the app read, decrypted from the
  use's envelope under the ids the vault bound (a reference's source's). A
  use that read another version answers 409 (`changed`), so the rest of
  the answer is of the same version.
- **A proxy read of plain values only** asks no vault, so no use records
  it: the app still appends its `credential.use` under 0.14's head, as
  before. Plans of placeholders and plain values only, never the proxy's
  inject. Beside a sealed one, a plain value is recorded nowhere: the
  uses name the sealed keys alone (review, Fable). PR 8's pages say so.
- **Not routed:** a request with no credentials row (a browser behind
  Cloudflare Access, a service binding, an MCP connection) keeps 0.14's
  unwrap. Giving them objects is PR 9's or 10's to decide. (Done since:
  "As built: T147 (W270)".)

**Around the call.**
- **No `credential.use` entry**, by the vault or the app: the use is the
  record. So no 0.15 read takes 0.14's head. The row is slim (R53): the
  proxy's context (upstream host, credential name, claims, a signature's
  SHA-256, presign, egress) is no longer logged anywhere. A read an MCP
  approval applies names the browser session, not the connection. For
  Erwin's review.
- **Refusals** are the rules' on the rows as they are, with 0.14's
  messages (`REFUSAL_MESSAGES`, now in core). An ended credential is 401,
  a key gone or written since the app read it 409 (`changed`: what goes
  back is always the version the app read), a use not decided (late,
  overloaded) 503 with the vault's `Retry-After`.
- **All or nothing, to the caller; not in the log.** A request refused
  part-way leaves the uses already allowed in the log as allowed, though
  their values never went back, and counted by the cap. The safe
  direction for an audit, but not exact: PR 8's pages say so, or the app
  records the withholding, as `credentialStill`'s refusal does.
- **A kept answer** (`Accesses`) is vouched for when every value going
  back was a use's, each read where it is held. A use proves less than
  0.14's check of the answer's revision: it checks the caller where the
  key is held, and of a fork the value is inherited in only that it is
  one. So with a value inherited in a fork, or a plain one beside, the app
  asks (`confirm`), as before. Example: Ada's grant on a fork revoked, her
  parent's kept: her read of the fork on a kept answer is refused, as
  0.14 refuses it (review r1).
- **`credentialStill` stays.** 0.15's credential object has no member
  generation. A removal ends credentials in its sweep, after
  `member.remove`. A use between the two, with the account admitted again
  meanwhile, is allowed, and only that check withholds the value.
  `Credentials.tla`'s `Revoking015` finds it with the check off.
- **The vault's cap at start (`#limit`)** is read first, unlocked. The
  bench found every vault's first call taking 0.14's head and the fence for
  it, and one that missed retrying on every call after, under load.

**The spec.** `Credentials.tla` gains `Uses015`: a read is one atomic use
on the rows as they are, no account row, no head, no kept answer
(`HotPathOne.tla` proves the order). `Revoking015` holds (82k states).
`NoReleaseAfterEnd` breaks without `CredentialFenceUnlocked`, and without
`RevokeIssuedCredentials`.

**Before the cutover** (known, not this PR's):
- 0.15's log has no roles object until PR 9's genesis. A use decides on
  the built-in roles (`noEdits`) where 0.14 decides on the edited ones.
  `natures-properties` found it: a service refused `no_grant` that an
  edited role lets use. The other way holds too: a role narrowed is, to a
  use, as it ships, and allows what the edit forbids wherever the app
  leaves the decision to the vault alone (a reference's source). Under
  0.15's log the suites edit no role (`EDITS_ROLES`), so neither way is
  tested there. What holds it is the order: PR 10 must not flip the
  switch before PR 9 makes the genesis.
- Rows planted around the app (0.4's tokens, tokens before 0.11) are
  `stale` to a use until the cutover seals them (`LOG_014_ONLY`).
- Days of uses are made by the test setup (`setup-test-database.sh`). In

#### As built: T135 (W235): the app's reads before a use, in one call

**What a use cost.** After PR 5b, a handle's `/use` with the proxy's cache
off ran, on the app's connection, the handle's credential with the newest
policy change, the place, and every key of the environment; then
`use_credential`; then `credentialStill`. The stable URL (`/use/<credential>`,
the one an app's config names, R14) checked the handle twice, with a vault
`access` call between. Measured one at a time with pgbench at 400/s on the
bench's Postgres (2 vCPU, 2 GB), Postgres CPU per statement:

| statement | sent as now (unnamed) | prepared |
|---|---|---|
| `select 1` | 0.11 ms | 0.09 ms |
| the credential, with the newest policy change | 0.82 ms | 0.31 ms |
| the place | 0.58 ms | 0.21 ms |
| the environment's keys | 0.88 ms | 0.32 ms |
| `credentialStill` | 0.33 ms | 0.15 ms |
| the first three folded into one statement | 2.48 ms | |
| the same in a plpgsql function | 0.66 ms | |
| that function, its columns lean | 0.48 ms | |

Planning was most of it. Each statement goes unnamed, planned again for
every request; folding them into one plain statement plans more, not less.
A plpgsql function's statements are planned once per backend, whatever
connection asked: on Workers too, where each call has a connection of its
own and named statements would be prepared again for each (Hyperdrive does
not say whether it keeps them across client connections).

**`app_read` (migration 0031).** One call reads what those three statements
read, as one JSON value: the credential by its token's hash, with its sign-in
account, the clock and the newest policy change; the project and environment
by slugs, standing ones, and a fork's parent's slug; and the environment's
keys, each row and its current version, the named ones only when the proxy
names them. `readAhead` (server `db/read-ahead.ts`) maps each row back as
Drizzle would have read it, by each column's own decoding, and the code
after it is unchanged: the MAC, what is live, a fork's layers, references.
- **Who calls it:** with 0.15's uses, on Postgres. A handle's use reads its
  credential, place and keys in it (`pluginContext`'s `readFor`); any other
  read of a whole environment, its place and keys (`reveal`'s
  `readValues`). A personal config (`dev@me`) and a key's own path read as
  before; so do SQLite and 0.14's log.
- **One snapshot** (`STABLE`): the place and keys are read with the
  credential, before the vault is asked, as the credential and the policy
  change already were. It decides nothing.
- **Planned once:** `force_generic_plan`, as the hot login's. Without it
  plpgsql planned the statement on every call (13,993 plans for 13,993
  calls at 400/s), each plan locking every index it weighed: the
  `LockManager` waits the bench showed.
- **Probes only:** `enable_seqscan = off`. A generic plan reads a small
  table whole where an index probe is dearer by its estimate, and those
  pages grow with every row of the instance (R48). The named keys are one
  probe each, by `(project_id, environment_id, key)`: each by a lateral
  with `LIMIT 1`, which the planner cannot flatten into a read of the
  whole environment joined on key (review r4).
- **`jit = off`,** as `use_credential` has it: a generic plan's estimate,
  a disabled scan's above all, can pass `jit_above_cost`.
- **Hyperdrive's cache:** the call reads the clock, as `credentialRow` does.

ahead and asks the vault about the person, as it always did; the `use`

#### As built: T143 (W251): the first days of a new database

**The gap, reproduced.** The migrations defined `make_day` and made no
day. A use on a database just migrated, before the checkpointer first
made any (`daysAround`, from its upkeep after a tick on Workers and Node's
start), failed in `use_credential`: `no partition of relation "log_uses"
found for row` (23514), thrown, so a 500 where a refusal or a value was
due. The window is real: on Workers the first tick can come from a change's
`seal`, and the upkeep that makes the days runs on the alarm after it
(500 ms); on a database flipped from 0.14 the credentials already exist
and uses need no change at all. SQLite does not partition (`log_uses` is
one table, `makeDays` a no-op): no gap there.

**The fix: the migration makes them.** 0035 makes `daysAround`'s days at
migration time: yesterday's (the fence's floor starts three seconds before
the migration), today's and the next `DAYS_AHEAD` (3). A deployment
migrates before it deploys, so they exist before any use can. Nothing is
added to a use, and nothing to the vault's start, which would only narrow
the window. A day boundary crossed with the checkpointer down is the same
gap later: bounded by the days made ahead, between three and four days
from the last upkeep (the migration's, if it never ran), and the Workers
checkpointer's alarm says when it could not make them (`#makeDays`).
`use-fresh.test.ts` holds both: the days the migrations leave are
`daysAround`'s, and a use on a database no checkpointer has touched
answers. The suite's template no longer makes days of its own
(`setup-test-database.sh`), so every file starts as a new instance does.

#### As built: T145, PR B1 (W242): a request's one key, the vault's one call

**What it does.** A request that names one key is one call of the vault,
`Vault.useNamed`, which takes the request as it names it: the token's hash,
the place's slugs, the key's name. A proxy `/use` on the environment's URL,
a handle's standing at its stable URL, `POST /api/reveals` of
`market/dev/API_KEY`, and of `market/dev` with `keys: ['API_KEY']` (what
`coffre export --keys API_KEY` sends) all go this way. In the vault:

- **Names to ids, in the vault.** An isolate maps (token hash, place) to the
  ids they name, the credential and the environment (`UseCache.names`), and
  (environment, key name) to the key's id, whoever asks (`keyIds`). A miss
  is one statement, `use_resolve` (migration 0044), SECURITY DEFINER on the
  vault's login as `use_credential` is. The maps hold ids only, never an
  answer, and each drops its least recently used past `uses.names` (10,000
  by default): about 250 and 120 bytes an entry, some 4 MB with both full,
  per isolate.
- **The use, held to the names.** `use_credential` takes the names beside
  the ids and answers `moved` when its rows no longer bear them out: the
  token's hash is another credential's, the key was renamed, a slug moved.
  Nothing is written or locked then; the vault reads the ids again and uses
  once more (`formal/Naming.tla`: without it, a key renamed away is used by
  the id kept). A use by ids, the multi-key path's, logs its request
  whatever it finds, as before. A key deleted and made again under its name is the same case,
  answered `missing` by the old id: read again, the new key is used, and
  the first attempt left no row (`use-named.test.ts`).
- **The caller, sealed.** The use decides on the credential and principal
  objects the vault sealed, as every 0.15 use does, and answers the caller's
  standing as it read them (`standingOf`): the app decides on that, and
  asks the vault nothing (`verify`'s `standing`). No answer is kept
  (`Accesses`), so none is confirmed after a busy refusal.
- **The app's rows in the same statement.** `use_credential` answers the
  rows `app_read` would (`app`): the credential, its identity, the newest
  policy change, the place, the key's rows. The app reads nothing itself on
  Postgres; SQLite's vault answers none, and the app reads its own there.
- **A key the place does not hold, and a plain value.** Both are decided by
  the vault on the caller's standing where they were sought, with no row:
  `missing` only to a caller who may act there, refused otherwise, as for a
  key held (`decideChecked`). A plain value's text goes back once decided,
  counted toward no cap. What the app logs of a missing key is what it

#### As built: T158 (W252): the standing decided before the principal's lock

**Why.** A use of a sealed key whose row of the cap's is not fresh for its
caller (its first in the window, or one that moves its row on to a new
period) took the principal's lock before the vault decided anything. A key
never made takes no lock. So a revoked caller whose principal's lock was
held by another call (theirs, or their account's other credentials') waited
for an existing key and not for a missing one: a 503 past the deadline, or a
403 a lock wait later, beside an immediate 403. Reviews r1 to r4 of #412
each found a way through B1's patches around that wait; r4 reproduced it
with every statement 1.1 s slow, as the confirm then ran out of time.
Erwin's rule (D149): a caller without standing never gets a 503 that
depends on the key, and its answer, and how long it takes, are the same
whether the key exists, was deleted, or never existed.

**What it does** (migration 0045, `use_credential`; `useOnce` in
`packages/vault/src/use.ts`; formal/Probing.tla `DecideBeforeLock`,
`DecideEachLock`, `CoveredRefusalAnswered`; formal/HotPathOne.tla
`NoLockWithoutStanding`):

- **The rules stay in TypeScript.** Postgres reads the rows, but the
  standing is the vault's decision on them (`readerOf`, `keyRefusals`;
  roles with their sealed edits, scopes, grants' ends, protected
  environments), on seals Postgres cannot check: a copy in plpgsql would be
  a second rule engine the Lean model does not hold. So the statement
  decides only whether the vault already did.
- **No standing kept** (D153). T158 first kept one per credential, place
  and permission (`stood`): the log's newest change when a use last found
  the caller standing there, a digest of the rows it read, and the soonest
  end of what it stood on, so that a later use took the lock in one
  statement. It needed four protections of its own, and review d1 of #416
  found the digest missing a field (a version's nature written beside its
  row). Every use that would take the principal's lock now decides first,
  each time (`DecideEachLock`): two statements where one held, only for a
  key with no fresh row of the cap's.
- **So the call answers `decide`**, having locked and written
  nothing, with the rows it read. The vault decides the caller's standing
  where the key is held (`decideStanding` then, folded into
  `decideChecked`'s standing-first order by D153: the credential, account,
  roles, policy and that environment, each sealed and its newest, then the
  rules there, nothing of the key's). Refused, it answers as for a key the
  place does not hold, with no entry and no row of the cap's; the app's
  own entry records the request (`deny`), as for a missing key. Standing,
  the vault makes the use, a second call (`p_decided`), which
  takes the lock as before, waits if it must, and decides on what it reads
  then: someone revoked between the two waits and is refused, having stood
  at the first.
- **A name with no key, kept as such.** The vault's map of key ids
  (`keyIds`) also holds `null` for a name the place held no key of, and the
  statement answers `moved` once a key of that name is held there (0045),
  so a key never made costs a use the statements one held does: B1's
  timing residual, a read of the names on every request for a key never
  made, is gone. A key deleted since its id was mapped is decided on the
  caller's standing first, as below; a caller who stands has the names
  read again, once.
- **One order, in every form of the statement and SQLite's** (review d3
  of #416, and the class of every finding before it): first what no key
  decides (the deadline, the floor of `at`, the clock, the cap's config),
  then the caller's standing, then only what the key or the map of names
  decides (`moved`, `unnamed`, a missing key, the principal's lock, the
  cap's row). An archived place or project ends the request as the app
  answers it, before any of that: its names are never read again
  (`AdmissionBeforeKey`; `ProbingFloor` and `ProbingArchived` show it
  necessary, for the floor and the place).
- **A map out of date decides the standing first, at the place named.**
  A named call that answers `moved` (a key made under a name the vault
  holds as none, one deleted since its id was mapped, one renamed, a place
  renamed and its slug taken by another) or `unnamed` is read again
  probing, in the same call, which then reads the place the request names
  now into its first slot, as `use_resolve` would: by its slugs (unique in
  their project, archived places included), or, for a handle's stable URL,
  the handle's own place by its id. The vault decides the caller's standing
  there and nowhere else (`refusedHere`), and refuses there, as for a key
  the place does not hold; no such place now, or an archived one, ends it
  as a read of the names would. Only a caller who stands has the names
  read again and the use made again (review d2 of #416: that took three
  statements for a key made or deleted since, one for a key never made).
  Review d4 found the standing decided at the place the map pointed to,
  not the one named: with `market/dev` renamed and a new `dev` made, a
  caller who kept access to the old place had a key held there read again
  and used again (three calls, a 503 on a slow database) and one deleted
  refused at once; one whose grant moved to the new place was refused a
  key the map held and allowed one it did not. Erwin's D150: decide at the
  place named, and take the map as anything at all rather than list its
  stale states. `Probing.tla` now chooses the map freely for every request
  (its credential, place and key ids, each right, another's, or none that
  exists), `DecideAtNamedPlace` is shown necessary for `SameAnswer` and for
  `AnsweredAsNamed` (the map costs calls, never another decision), and a
  handle's call is held to the handle's own place by its id

- **A refusal on a cover is answered in its one call.** A repeat of an
  allowed use rides its entry while no change came after it; refused on

  made again as an entry of its own, as before, but a named one is
  answered as it is, as a key the place does not hold is, and the app's
  entry records it: the second call told a key held from one never made

#### As built: D153 (W253): one `no`, at a fixed cost

**Why.** Review d5 of #416 found the class once more, outside the name
map: a revoked caller who re-asked for a reference they had used, its
source deleted since, was told `ended` (403, "the reference read through
was ended") where a key never made answered `no_grant`. Each review since
r1 of #412 had found one more reason a refusal told keys apart. Erwin's
D153 ends the class rather than the case: "/use arrives; one path checks
whether the key exists and the requester has access to it, one single
path for both checks, all scenarios; yes → success; no → failure, don't
specify why."

**What it does.**

- **One answer.** A named use the vault refuses, whatever the reason (no
  standing, none to read, no such key, a reference ended or whose source
  is gone, a fork's or a sensitive rule, a row put back, `stale`,
  `tampered`, `no_policy`), is answered `not_available`: 404, "not
  available: no such key, or no access to it", the same body and headers
  by the API and the proxy. The app's own checks after the vault's
  refusal answer the same (`refusedAlike` in `reveal`); a refusal on rows
  whose seals bear out no standing too (`useByName`, the reason in the
  server's log). The audit log keeps each reason, the app's or the
  vault's code, for whoever may read it; the error carries none. Answers
  that tell nothing of the key stay apart: 401 for a credential ended or
  unknown, decided on it before any key; 503 with `Retry-After` from
  admission, before anything is read. After a yes, anything may differ:
  the caller may have the key, and knows it is there. `bulk_limit` stays
  its own answer, as only a use the rules allowed reaches the cap.
- **Fixed work for a `no`.** A named use's first call reads what the
  request names by its names, under the fence: the credential of its
  token's hash, the place of its slugs (a handle's one place, for a stable
  URL), the key of its name there (migration 0045; `v_credential`,
  `v_secret`, `v_place`). Every row it reads is one of those; the ids the
  isolate's map holds, if any, only let that call write the use's entry
  and take the lock, when they are the names' now (`v_right`). Otherwise
  it answers `moved`, writing and locking nothing, with the names' rows
  and ids (`n_*`). So the vault decides the use on what the names name, in
  that one call, whatever the map held: a `no` costs one call, whether the
  map was empty, right or anything else; a yes the map had no ids for is
  made by the ids read, in a second call, and the map keeps them.
  `use_resolve`, B1's read of ids before a use, goes (0045 drops it).
  B1's two calls for a cold name stay two for a yes and become one for a
  no; a warm one stays one.
- **The lock only after a yes.** The `decide` call is decided on the whole
  use, key and all, but the cap; only a use the vault allowed is made, by a
  second call, which takes the lock. Nothing is kept for a later use to
  take it on (`DecideEachLock`): T158's `stood` is gone, with its four
  protections. A standing caller asking for a key they may not have waits
  for no lock either.
- **Standing first, the credential before it.** `decideChecked` decides
  the credential first (its seal, then whether it ended: a revoked token
  is 401 whatever the place's seal says), then the seals of what it reads
  (the key's row among them, as it says where the key is held), then
  0.14's rules where the key is held or sought, a personal config with its
  parent, before anything else of the key's (`standingRefusal`); with one
  answer it decides nothing the caller sees of the key, but keeps the
  vault's reasons in the order a person would give them, and the Lean
  model holds it (`standingFirst`, `refused_by_standing`).
- **A plain value, live and replayed alike.** A named use may answer a
  plain value (`UseRequest.plain`, which the vault sets on a use by name);
  a use by ids never does, live (`use` throws first) or replayed (the
  request carries no `plain`, so `decideChecked` refuses it `bad_claim`).
  That kept a by-id use to one statement, where reading the key's nature
  first would have taken a second (P1 #4 of the design's review).
- **The `no` is the app's to log.** The vault's refusal writes no entry
  and no row of the cap's; the app's path, which authenticates first (401
  before anything), seals a 0.10 token, and writes the request's own
  `secret.read` deny under the credential's actor, with the reason, then
  answers the one `no` (`refusedAlike`).
- **Every single-key read.** The app's own path answers the same `no` for
  one key: by its path, through the proxy (a credential's one key, a
  signer's, a verifier's), whether the key is refused, missing, or read
  without it (`unknown_secret`), on either log. A whole environment's read
  still names what it leaves out, by name, and why.
- **One route, the credential's** (review r2). Whether the app answers a
  named request on the vault's decision or by its own path (the
  credential's check, `access`, a use by ids) is picked by `routeOf`, on
  the credential and its account as their seals bear them out, and on
  nothing else: not the roles, a place, the key's rows, nor the isolate's
  map. Each input's identity is judged on its own (`viewOf`): a key's rows
  not as the isolate's seals of them say (a reference's source pointed
  elsewhere around the log) are a refusal of the key, `stale`, answered
  as every one is. Before, they made the whole view stale, the request
  went to the app's path, and a lock held there answered 503 where a key
  never made answered 404 (`OneRoute` in `Probing.tla`).
- **A use by ids decides before the lock too.** The app's path's use
  answers `decide` as a named one does, and is made by a second call once
  allowed; refused, the vault writes nothing (`number` null) and the app
  logs the request (`UnloggedRefusal`, in `recorded`).
- **A named refusal reads nothing more** (review r3). Once the vault has
  refused a named use, the app answers the one `no` at once and logs it
  with the vault's reason, at the place the vault's own statement read: it
  runs none of its own reads of the key, which cost a broken reference 9
  statements where a key never made cost 5. The app's matrix counts its
  statements too. A refusal a use by ids decided first is logged by the
  app whoever asked (`withRefusals`): a read, a fork's copy, a dry run's
  compare.
- **No path after the vault's decision** (review r4, option b). A named
  request is answered by the vault's call alone: `served: false` only for
  a place the vault serves not by name (none, archived, a fork's, a
  personal config's, one a stable URL does not mean), decided on the
  place. A key that reads an archived place, a reference's source's, is
  the vault's refusal by name (`archived`), where 0044 handed it to the
  app's path (`unnamed`). The refusal's entry takes the place's ids from
  the vault's own rows, on either engine (`NamedUseOutcome.at`). A whole
  environment's read of the keys it lists stays a read of the environment:
  what it leaves out, and why, is its answer. A reference's unlogged
  refusal is logged at its holder's place.
- **What the statement reads first is read without raising.** A handle's
  `places` (`pg_input_is_valid`, and SQLite's `boundOf`): anything but one
  place is none, and the credential's own check answers 401. The places a
  stable URL does not mean (`unless`) are judged against the slugs the
  call reads, never the map's.
- **Names, by two branches.** The statement reads a handle's one place by
  its id, or a path's by its slugs, each a direct predicate on a unique
  index: `use-cost.test.ts` holds a named use's buffers the same at 1k
  places and at 10k, mapped or not.
- **The vault's "authenticated" is the app's** (reviews r6 and r7). The
  app checks a named request's credential after the vault's call, on the
  rows it answered. Two of its checks the vault could not see: a browser
  session whose sign-in provider the deployment no longer configures, and
  any coffre token once the deployment signs in through Cloudflare Access.
  The vault decided the use first, a key the grant covered taking the
  principal's lock (503 under contention) where a key never made answered
  401 at once. Erwin chose the general fix: the named call carries what
  the deployment's config accepts (`NamedUseInput.accepts`: coffre's own
  sign-in, each configured provider's id and issuer hash), and the
  statement holds the credential to it first, right after reading it by
  its token's hash, answering one the app would refuse as a token no
  credential has (`unknown`) before the place, the key or any lock is read
  or taken (`p_signin`, `p_issuers` in 0045; SQLite's twin). Every kind,
  browser sessions included, keeps its one call. `docs/formal.md`,
  "Probing.tla", lists every check the app makes of a credential and why
  each is the vault's too (`AcceptedFirst`). Review r8 found the one that
  hangs on the clock: the vault judged expiry at the use's `at`, the app
  at its own later time, so a token expiring in between got the vault's
  work, then the app's 401. One clock: the app judges expiry at the use's
  `at` too (`OneClock`). A token live when its request began is honoured
  for that request, which the 3 s use deadline bounds; revocation and
  generation stay live checks.
- **A named call does the same work whatever the key's history**
  (Fable's review, review r12). The isolate kept the seals a probe read
  for a later use's cheaper, cached form of the statement. A refusal kept
  them for a key never made and not for a held one; a use allowed kept
  them for a key its caller then lost, which later refusals then ran in
  the cached form plus a re-probe (79 buffers) where a key never made
  probed (45). Erwin's design settles it: a named call never passes
  seals (`known`) and keeps none, so every named call runs the probe's
  form; only a use by ids keeps them. The matrices now hold that form,
  and each refusal's buffers within a few pages of the others' (EXPLAIN
  of its last statement, Postgres). A warm named use reads ~45–51
  buffers where the cached form read ~35–40.
- **What it leaves out: a credential row forged in the database** (D154,
  after review r5). The vault checks a credential's seal; the app checks
  its MAC (`APP_KEY`) after the named call, on the rows that call
  answered, which saves the named path a statement. A row whose seal holds
  and whose MAC does not, which only a database writer can make, is
  decided by the vault first: a held key outside the caller's set takes
  the principal's lock, and its use is made and logged, before the app's
  401; a key never made answers 401 at once. With the lock held
  elsewhere, 503 beside 401. Erwin: "I don't think we should design
  around potentially broken state due to direct DB manipulation."
  Accepted, as such a writer reads key names directly, and documented in
  [Limits](../architecture.md#limits). The request still fails closed,
  401 and no value, for every key; `named-reveal.test.ts` pins the
  behaviour (R64). Neither alternative was taken: the app reading the
  credential before the vault's call (a statement more per named use), or
  splitting the vault's call around the app's check (a round trip more
  per allowed use).

**Model.** `formal/Probing.tla` now compares two runs whose maps are

**The spec first** (`formal/WaysIn.tla`, four scenarios, seven protections each shown necessary in eight removals; docs/formal.md): a use

### 6. Merkle checkpoints (high: crypto)

- **Scope.** W209's tree in W212's shape (#368), behind one seam
  (`append(leaves)` → signed heads; `prove(number)`).
  - **Two growing RFC 9162 trees**, one per retention class: changes (kept
    for good) and uses (dropped by day). Each has its own origin, and a tick
    signs both with the same `upto`.
  - **One pair.** The two heads are one memory record, written in one
    statement, checked as a pair when opened and at each tick, and witnessed
    as a pair. The verifier merges both trees by number.
  - **Tiles partitioned by leaf range,** so that retention drops a table:
    1.16 s and 294 KB of WAL, against 13.8 s and 3 GB for a `DELETE` (W212).
  - **Below a retention cut, one tile per level:** about 5 tiles, against
    10.8 MB a day kept for good.
  - **To decide during the port** (record the call and why in
    hot-path-one.md): no level-0 tiles for the uses tree. That saves 41 B an
    entry (about 16% of storage) and 85% of the tree's WAL; a proof's leaf
    read goes from 0.56 to 2.1 ms p50.
  - **Carry W212's fix:** `tree.ts` tested powers of two with 32-bit
    `n & (n - 1)`, which splits trees past 2^32 leaves wrongly (day 50 at
    1,000/s). Keep its regression tests.
  - A 500 ms tick.
  - The signer's last head kept in core (R54), if its cost stays within the
    budget.
  - The barrier is `close_one`: no lag.
  - **The barrier checks the floor of `at`** (`HotPathOne`,
    BarrierChecksFloor; Fable on PR 1). It requires `at_floor` to be the
    value it last wrote, and alarms otherwise, like RowChecked. A writer who
    lowers the unsigned floor would let a use land where no checkpoint's
    `at` scan reads it: never sealed, deletable without trace.
  - A change waits for its seal, and for the witness for at most 2 s, then
    answers unwitnessed, recorded and alerted (R51).
  - Witnesses (Durable Object, R2) come as R40's plugin.
- **Files.** `packages/core/src/audit` (the leaf hash, which hashes the whole
  entry and its number), `packages/vault/src/checkpoint.ts`, the Workers
  checkpointer's Durable Object, the Node interval.
- **Spec part.** `Seal.tla`.
- **Tests.**
  - W209's tests (Go `sumdb/tlog` byte equality), the change-latency bench,
    the plugin's witness tests.
  - Go's `tlog` on a split log and on one-tile-per-level cuts. W212 could not
    run it (no Go toolchain on that host); this PR must.
  - This PR's review covers W212's fixes from its review r1 (the pair's
    atomicity, P1, and four P2s). They were fixed but never reviewed again.

### 7. Retention (high: migrations, integrity)

- **Scope.**
  - Days made ahead by the checkpointer.
  - W209's five retention steps, with `DETACH … CONCURRENTLY` then `DROP`
    (measured: 3 ms and 26–52 ms under load, no effect on uses). In W212's
    shape a cut touches only the uses tree: no kept-changes digest, no daily
    rebuild (10.4 min/day saved).
  - The tiles below a cut: drop their leaf-range partition, keep one tile
    per level.
  - `prune_bulk`, by the window.
  - One Fable review once built (R54).
- **Spec first** (R45). Retention is not modelled yet. `Seal.tla` has no
  cut, prune or post-retention verifier, and dropping a day is exactly what
  its `SealedDeletionDetected` would flag if read literally. So this PR
  starts by adding them to `Seal.tla`:
  - the cut, sealed and freshness-bounded;
  - the uses tree's partition dropped, keeping one tile per level;
  - the verifier walking from the newest cut.

  Invariants: nothing kept is lost; a dropped use is never sealed again
  (FRESH_MS); the changes tree is untouched. Each protection is shown
  necessary. Then the code follows.

#### As built: PR 7 (W229)

**The spec first** (`formal/Seal.tla`, `SealRetention`, `SealRetentionCrash`;
docs/formal.md has the table). Time is a clock each barrier moves on a step
or not; entries and notes carry `at`, and notes the time of the pair before;
a day is the uses stamped before its end, whatever their numbers. One
retention run chooses a day's end and its cut, the first pair past it on the
signer's history, appends the retention change, and drops the day and the
uses tree's tiles below the cut. The verifier walks the changes tree from
genesis and the uses tree from the newest honoured cut. Every scenario holds
(5.1M and 2.8M states), and each protection is shown necessary:
FreshChecked, DropAfterSeal, FreshBeforeDrop, CutFirst, CutSealed,
CutUsesOnly and KeepCutTiles. Two gaps are `EXPECTED`, both the stragglers the plan accepts:
a next-day use below the cut can be deleted, or copied above it and its
original deleted, unseen once the cut is announced.

**W209's five steps, in `split`'s shape** (`packages/vault/src/retention.ts`):
1. **The cut:** the first pair whose floor of `at` is past the day's end.
   The floor holds a use's `at` (FloorChecked), so every use of the day took
   its number at or below that pair, read from signed pairs by an index
   (`log_checkpoints_floor_idx`), never the uses. It must be the signer's,
   and the first past the day's end by its own note: each pair now signs
   `prev`, the floor of the pair signed before it, which must be below the
   end (CutFirst; review r2: a writer who deleted the first pair's rows
   would otherwise push the cut later, and every kept use between would go
   unwalked). It must be on the signer's history (a consistency proof to its
   head in both trees), unless the newest sealed cut already covers it: then
   the tiles a proof would read may be gone (review r2: a catch-up of two
   days stopped there).
2. **The retention change** naming it, unless the newest sealed one already
   cuts at or past it (a quiet day, a retry): `{op: 'retention', day, cut:
   {upto, at, uses, root}}`, numbered under the fence *shared* (it changes no
   input; no use waits on it), sealed through `sealThrough`.
3. **Freshness:** the pair that sealed it at least two `FRESH_MS` past the
   cut. W209's separate `audit.retention.begin` change is gone: the retention
   change is that entry, since the drop waits for its seal (DropAfterSeal),
   and TLC shows the drop needs nothing more.
4. **The day's partition:** detached, and dropped by the next run
   (`drop_day`, a short transaction each), never right after its DETACH
   (measured below); and one DETACH a run, so a backlog (retention turned
   on over a long log, a lowered `retainDays`) goes a day an hour (Fable's
   review). A crash between any two steps is finished by the next run.
5. **The tiles below the cut** (`drop_tiles`): each leaf-tile range wholly
   below it, detached then dropped; upper tiles wholly below it deleted. The
   tile holding the cut at each level stays (core's exhaustive test of
   `keptAbove`). The store forgets each range it drops (T119's item 2).

Then `prune_bulk`, once a minute, by the policy's window (R52).

**Who runs it.** The checkpointer's host, after each tick (`upkeep` in
`log-checkpointer.ts`): the next days' partitions once a day (yesterday
through `DAYS_AHEAD`, 3, past today), retention hourly when `retainDays` is
set, the bulk prune each minute. Its failures are alarms, said once; a day
that waits (a reader holding the uses past `drop_day`'s lock timeout) is no
alarm until it has waited a day. The days are made even when the
checkpointer cannot open or tick (on Workers over a connection of their own,
on Node before it opens): a use needs its partition whatever the audit's
state.

**What the database checks itself** (migration `0027_retention`). The
vault's login owns nothing, so each function holds it to what a retention
change it can see cuts: `drop_day` drops only a day before yesterday whose
cut is at or below `log_cut()` (the newest retention change at or below the
newest checkpoint); `drop_tiles` nothing past that cut's uses size;
`log_retention` only a cut that is a checkpoint past its day's end. The
signer's checks (the change in its pair, the pair fresh) are the vault's.

**DETACH, not DETACH … CONCURRENTLY.** The plan said CONCURRENTLY. It
cannot run in a function (no transaction block), and needs the table's owner;
the vault's login owns nothing, and reaches Postgres through Hyperdrive,
which pools by transaction, so no `SET ROLE` can stand before it. Measured
(W229's rig: Postgres 16.14 held to 2 vCPU and 2 GB, 1,000 uses a second,
a day of 1M uses, 134 MB):

| how | runs | DETACH | the drop's second, p50 / p99 / max | stalled over 100 ms |
|---|---|---|---|---|
| CONCURRENTLY, then DROP | 9 | 5–36 ms | 12–290 / 146–383 / 226–585 ms when stalled | 7 of 9 |
| plain, `lock_timeout` 100 ms, then DROP | 15 | 3–5 ms | 9–276 / 144–348 / 197–407 ms when stalled | 10 of 15 |
| plain, a reader holding `log_uses` 2 s | 2 | gave up at 103–106 ms | 1.3 / 98 / 110 ms | bounded by the timeout |
| DETACH, then DROP 5 s later (either) | 9 | 3–6 ms | max 8–16 ms (one run 128) | 1 of 9 |

- The two DETACHes behave the same: CONCURRENTLY buys nothing here.
- The stall is not a lock wait (none over 10 ms with lock waits logged):
  every backend replans its plan of `log_uses` at once, on 2 vCPU, when the
  DROP lands before they have. A few seconds apart, it does not. So a run
  detaches, and the next drops.
- No use failed in any run.

**How many days to keep** (`retainDays`, a host setting, null by default:
every day kept, as 0.14 keeps its log). A warm use costs the same with 5,
35 or 95 days attached: 1.06–1.07 ms of CPU, 45 buffers. A generic plan locks
every day (129 locks a use at 95 days, 19 of them fast-path), which did not
show in CPU. Every plan made again does:

| days attached | a new backend's first call | a replan | 40 new backends at once |
|---|---|---|---|
| 5 | 35–39 ms | 7–9 ms | 0.9 s |
| 35 | 47–54 ms | 9 ms | 1.3 s |
| 95 | 66–71 ms | 11–12 ms | 2.0–2.1 s, past the hot login's 2 s statement timeout |

At 95 days the daily `make_day` stalls uses about 460 ms (every plan
invalidated), and so does each autoanalyze of today's partition, frequent
early in a day; at 5 days, neither shows. So the default stays "keep", and PR
10 picks one with this table in hand: a month (35 attached) is the measured
safe side. Longer audit retention would keep days detached, as tables of
their own, rather than attached. A use path whose plan does not list every
day (the cover check reads `log_uses`) is the lasting fix; T112's numbers
decide whether it is needed.

**SQLite** (tests and local development): no partitions and no functions.
A day's uses and the tiles below a cut are deleted rows, one statement each,
and the same steps run around them; days need no making.

**The verifier** (`verifyLog`, `cut`): it takes the newest retention change
at or below the newest checkpoint, requires it sealed (in the walk, or by an
inclusion proof below the start), loads the uses tree's edge at the cut from
the kept tiles, held to the change's head, and requires the checkpoint at the
cut to hold that head. Uses at or below the cut are not walked.

**Numbers.**
- Retention's reads (a day's cut, `log_cut()`, the newest retention change),

- W229's bench found two faults in `bench-use.ts`'s warm-up: pg-pool closes

**For PR 8.** The 0.15 replay reads changes in number order: a retention

**Open.**

**One check, on every visit, nothing kept between calls**
(`packages/vault/src/verifier.ts`, the vault's `verifyTrees`): the newest
signed pair, its signatures and the pairs held outside (the signer's
memory), then every entry above it, by its MAC and its request. No replay,
no row read.

**What was dropped, and why.**
- **The saved replay** (D143 (d)). The first build kept a replay at signed
  pairs (`log_replays`), moved on by the 5-minute job, so that a page could
  say "replayed OK". Every P1 and P2 of review rounds 3 to 8 came from that
  layer: a fault short of the present left an old "ok" standing, two walks
  deleted each other's progress, and the page's check cost about 90 ms at
  1,000 uses a second.
- **The whole walk** (D145, Erwin, 2026-10-28). Rounds 9 to 15 then built a
  walk of the whole log in one request: both trees from the first entry,
  every MAC, the changes replayed, and every input row held to the replay.
  Each round found a P1 or P2 in its cost. A database writer chooses what
  the walk reads (grant counts, byte sizes, pairs over no entry, rows no

  during it, held a Worker's call to its CPU limit. It is gone on Workers

to rows nobody uses, is not detected until an offline scan exists. The
signed checkpoints make that scan possible later without the MAC key: it
rebuilds both trees from the entries and holds each to its signed heads.
Live safety never rested on the walk: every use holds the rows it reads to
their object's newest seal and refuses a row put back, `stale`.

### 9. The cutover from 0.14 (high: migration)

The rows of 0.14 are not sealed to any change of the new log. The first 0.15
vault start does the cutover:

1. **Under the fence.** It takes the 0.15 fence exclusive, and 0.14's head
   lock too, each object's member queue lock first (row, head, fence: PR 4).
   - **Head lock:** not needed for safety (TLC): the fence and the row check
     of step 3 make a racing 0.14 write refuse the cutover. It buys
     progress.
   - **Lock order:** 0.14's head first (PR 4).
2. **Verify.** It verifies 0.14's chain up to its head.
3. **Check, then seal every input.** It checks each row as 0.14's
   `#integrity` does (VerifyRows): its MAC holds, and its `access_seq` names
   the newest authentic entry up to the anchor. Then it writes one `genesis`
   change per object, whose seal is the row's and whose payload is the
   object, and stores the seal on the row. Without the check, genesis seals
   a row a writer put there.
4. **Anchor.** It writes one `cutover` entry naming 0.14's last head (sequence
   and hash), so the new log's first checkpoint vouches for the old chain's
   end.

**Places 0.14 deleted** (T130). 0.14 left a deleted project's
environments `dev`, and the keys under any place it deleted unarchived,
their versions erased. Sealed as they stand, genesis would make each
environment a live one (`deleted: false`), whose erased keys a slug-scoped
grant (`*/dev`) still reaches: allowed, then a wrapped key that is empty,
where the live path and its replay say there is no key. So,
under the same locks, before genesis:
- **Deleted is read from 0.14's verified chain, not the rows.** A project
  is deleted when the chain up to the anchor holds an allowed
  `project.delete` naming it, and its row's slug is that entry's
  `tombstone`; an environment alone, by its `environment.delete`. A
  mismatch either way (an entry without its tombstone, a tombstone without
  its entry) refuses the cutover, as a row VerifyRows refuses: otherwise a
  writer who renames a deleted project back seals its environments live,
  or one who tombstones a live project, its environments deleted.
- **Each standing environment of a deleted project becomes `<slug>~deleted`**
  (`deletedWithProject`), the live deletion's tombstone, and its genesis
  seals it deleted. `coffre audit market~deleted-…/dev` reads the same
  entries before and after (`resolvePath`).
- **Each unarchived key under a deleted place is archived, with no genesis**
  (no object), as the live deletion leaves it: a use reads no key, live and
  replayed.
- **Spec, before the code** (R45): `Migration015.tla` gains a place 0.14
  deleted, the writer's rename of its slug either way, and an invariant,
  `NoneInDeleted` (no use allowed in a place 0.14 deleted), which must
  fail without `DeletedFromChain` (deleted read from the chain, not the
  row).
- **Lock order** (T132, from PR 4's issue lock): the cutover takes each
  object's member row first (`RowFirst`, step 1), then 0.14's head, then
  the issue lock, then the fence. If its transaction appends a 0.14
  entry the trigger fences, the trigger asks for the issue lock while the
  cutover holds the fence, a cycle with the barrier; otherwise its entry
  must be one the trigger lets by.
- **Tests:** a 0.14.5 database with a deleted project (an environment of it
  under a `*/dev` grant, an erased key) and an environment deleted alone:
  after the cutover each environment is sealed deleted, `dev~deleted` for
  the project's, its keys archived, a use refused live as replayed, and
  the old audit path reads the same entries; a project slug renamed back,
  and a live one tombstoned, each refuse the cutover. Postgres and SQLite.

**Cutover is idempotent.** It writes a `cutover` marker under the locks and
does nothing if one exists, so two vaults starting at once, or a restart,
make one cutover. It checks for the marker without a lock first, then again
under the locks, so that each isolate's start does not stall every use.

**Old uses in flight.** Until 0.16 (PR 11), every 0.15 change also advances
0.14's own fence for the object: its audit head, and the member's
`access_seq`. A 0.14 use that read before a 0.15 revoke is then refused or
fenced by 0.14's own checks, as today. Without this, an old isolate could
release a value after a 0.15 revoke answered, with no entry in the new log
(review r1). The alternative is a drain gate: no 0.15 change answers until
old isolates can no longer serve. It is simpler to state, but on Workers it
has no bound we can promise.

**A late 0.14 write.** An old isolate can still serve briefly after the
deploy. If it writes an input after the cutover:
- the row then matches no change of the new log;
- uses of that object are refused `stale` (fail closed).

The vault **adopts** it, at every checkpointer tick until 0.16 removes the
old path, not once (as planned; PR 9b refuses late writes instead, "As
built: PR 9b"):
- it reads 0.14 entries after the cutover's head, skipping 0.15's own mirror
  entries (the dual fencing's);
- it verifies each one (AdoptVerifies): its MAC and its place in the chain;
- it writes an `adopt` change citing each, and seals the *content that entry
  wrote*, not whatever the row holds (AdoptSealsEntry). Otherwise it would
  seal a row a writer put back after a late revoke, and serve it;
- it seals a 0.14 write only if it is numbered after the 0.14 entry that the
  object's newest seal names (AdoptAfterSeal).
  - **Why:** a writer who deletes a 0.15 change's mirror entry from 0.14's
    chain, and puts the old row back, would otherwise make the next adoption
    seal the older 0.14 write after the 0.15 revoke, undoing it in the new
    log (`NewChangesStand`, TLC).
  - **Its basis:** the check uses only 0.15's own signed log;
- it should also verify 0.14's chain links from the anchor and report a gap
  or a failed MAC, so a dropped entry is reported at the next tick. That is
  not modelled.

So the late write is in the new log too, and the object is served again.

- **Spec.** `Migration015.tla`. Invariants:
  - `OneCutover`;
  - `AnchorHolds`: the cutover names an authentic head and precedes every
    0.15 entry;
  - `NewLogFollowsOld`: genesis and every adoption seal what 0.14 wrote;
  - `UsesOnLoggedRows`;
  - `AllowedOnlyWhenGranted`: no use, old or new, is allowed on a state a
    writer made;
  - `EveryOldWriteAdopted`: per tick, every authentic 0.14 write that
    existed is adopted;
  - `NothingAllowedAfterAnswer`, across versions;
  - `NoWaitCycle`.
- **Invariant added:** `NewChangesStand`. However 0.14's chain is changed, no
  0.15 use is allowed on a state a 0.15 change refused.
- **Removals,** each failing as required (15):
  - the cutover's locks, the row check, and the marker;
  - dual fencing, the trigger (OldWritesFence), and the lock order;
  - adoption and its repetition;
  - chain verification, adoption's verification, what it seals, and
    AdoptAfterSeal;
  - UsesSeeOldWrites, and the rejected row marker's alternative.
- **What the seal covers.** The model's seal covers the value and 0.14's
  `access_seq`, so a late 0.14 write leaves the row `stale` until it is
  adopted, even when it writes back the same value. A seal over the object
  only would let such a row be served, and that is harmless: its value is
  the one the newest seal names. Either way, what refuses a row put back
  over a late write is UsesSeeOldWrites, which reads 0.14's newest
  authentic entry, not the row. PR 9 states which it builds.
- **Not covered:** 0.14 uses after the cutover are in no 0.15 checkpoint.
  Adoption cites only writes. Those uses stay in 0.14's own chain, which the
  cutover anchors.
- **Tests.**
  - `pnpm test:compat` both ways.
  - A drill: 0.14.5 serving while 0.15 starts on the same database, with
    writes from both, an old-path use in flight across a 0.15 revoke, and a

#### As built: PR 9a (W257), the cutover

PR 9 is two pull requests. This one is the cutover itself, its spec
first: the first 0.15 start seals what 0.14 left and anchors the new log.
Late 0.14 writes come in 9b: adoption at every tick, the dual fencing
each 0.15 change still owes (below, "Left for 9b"), and the drill.

**Two halves: what the app vouches for, and what the vault holds to it.**
The plan says the vault's start checks each row as 0.14's `#integrity`
does. That holds for a member's row only. 0.14's other rows are
authenticated by the app's key, APP_KEY, which the vault never holds:
- a credential's and a binding's row: its `auth_mac`;
- a place's deletion: the app's `project.delete` or `environment.delete`
  entry, its tombstone in the metadata;
- a binding's end: the app's `token.unbind`.

So the app does its half, and the vault holds the rows to it:

1. **Asks.** The app's door asks `Vault.cutover()` once per configuration,
   before anything else, with no input. The vault reads its marker with
   no lock and answers done, or where 0.14's chain is verified from: its
   newest checkpoint's prefix (R25).
2. **Vouches.** The app walks its own entries from there to the head by
   their MACs (`walkChain`). It then vouches for:
   - each credential 0.14 accepts: its MAC holds, it is live, its
     sign-in account is not unlinked, and no authentic `token.revoke` or
     `sign_out` names it, nor an `account.unlink` its account (an unlink
     ends its sessions with one entry: review r1);
   - each binding: its MAC holds, it is live, no `token.unbind` names it,
     and its row names no `origin` (#417's column, which 0.14 never writes
     and its MAC does not cover: one with it is a writer's, review r2), as
     made on the deployment's public URL;
   - each place an authentic deletion entry deleted, with that entry's
     tombstone.

   An entry of these kinds (a revoke, a sign-out, an unlink, a deletion)
   whose MAC fails is damaged history, and refuses the cutover. It is
   never read as no end (review r4).
3. **Seals.** The vault takes it in one call, `Vault.cutover(input)`:
   - outside any transaction, it rehashes 0.14's chain from its first
     entry to the checkpoint's signed prefix, which must come to the hash
     that checkpoint signed. An entry edited, deleted or moved before it
     refuses the cutover (review r4: an old revoke or `reference.end`
     edited past its MAC would otherwise have been read as absent, the
     token or reference sealed live). Each entry there was MAC'd when that
     checkpoint was signed;
   - it walks the entries since by its own MACs;
   - then one transaction, under every member's row, 0.14's head, the
     issue lock shared, then the fence exclusive;
   - the marker read again; the rest of the chain to the head; the
     app's stretch still the chain's (its last entry's hash), and no
     entry of the app's after it;
   - every row read and checked (`planCutover`), each object's genesis,
     and the cutover's change.

   A 0.14 write between the app's read and the vault's lock answers
   `moved`, and the app vouches again (three times, then the next
   request).

   The model sends the cutover back on any 0.14 entry after the head
   the app checked; the code, on the app's alone. Only the app's
   entries end what it vouches for (`token.revoke`, `sign_out`,
   `account.unlink`, the deletions). Of the vault's, `member.remove`
   is the one that ends credentials, by the member's generation, and
   the cutover reads member rows under its own locks, from which 0.15
   decides a credential's generation. The vault's others (`secret.read`,
   `credential.use`) come with every 0.14 use, so a busy instance would
   otherwise never cut over (Fable's review).

Example. Ada's service token T is revoked under 0.14 (`token.revoke`,
the row's `revoked_at` and a new MAC). A writer puts the row back as it
was, MAC and all, which 0.14's own check takes. The app finds T's revoke
in the chain and does not vouch for it, so it stays unsealed, and every
0.15 use of it is `stale`. TLC found the other way in: the app vouched
for T before the revoke, the revoke landed, and the writer put the
vouched row back. Hence the vault also holds the chain to the head the
app checked (VouchedHeld).

trigger fences `log.cutover`: it asks for the issue lock, then the fence.

without CutoverIssueFirst, once the barrier may run before any vault has

#### As built: PR 9b (W269), the cutover finished

PR 9a sealed what 0.14 left at the cutover. 9b finishes the transition: what
an isolate of 0.14 still serving may do after it, and the restore drill on
the new log.

**Late 0.14 writes are refused, not adopted** (OldWritesRefused,
`OldWritesBeforeAnchor`). Once the cutover's change is in `log_changes`,
the database refuses a 0.14 write:

- every entry a writer under 0.15's log appends carries `log015` (migration
  0047), a column that no MAC covers and that 0.14's code never sets: the
  vault's under its `log` option, the app's once its vault says it keeps
  0.15's log (`keeps015`, asked before any write);
- a trigger refuses an allowed entry without it. Exempt: a read's, a
  use's, and the log's own (`audit.*`, the alarms);
- the refused append fails its transaction, so the rows that write made go
  with it. The old isolate answers an error, and its client asks again,
  this time of 0.15.

Example. Ada saves a value on an old isolate at the moment the first 0.15
request cuts over. Her write took 0.14's head before the cutover, which
then waits for it: her value is in the cutover's genesis. Had the cutover
taken the head first, her write would have waited, then found the
cutover's change: refused whole, nothing written, 500. Her browser retries
on 0.15.

Every 0.14 append holds 0.14's head, and so does the cutover, from before
its marker to its commit. So an append either commits before the cutover
(and is sealed by it) or sees it (and is refused). Sign-ins are refused too
(`sign_in`, `token.exchange`, `device.approve`): a credential made after
the cutover by 0.14's code is one that 0.15 never sealed.

This replaces the plan's adoption at every tick (above, "A late 0.14
write"):

| | adoption (the plan) | refusal (built) |
|---|---|---|
| what a late write does | lands; its object is `stale` until a tick adopts it | fails whole; its client asks again |
| the app's writes | adopted only once the app vouches for them under APP_KEY, which the vault never holds: a second cadence, the app's | the same trigger |
| an unMAC'd row (a key, an environment) | adoption must know the late write came after the object's newest 0.15 change, which 0.15's app payloads do not record (they are MAC'd before 0.14's head is taken) | nothing to order |
| what it costs | a scan of 0.14's log each tick, an `adopt` change per write, and the app's vouching | one probe of `log_changes_object_idx` per 0.14 write entry, before the cutover; none for 0.15's (its WHEN) |
| what it gives up | | an old isolate's writes after the cutover, and with them a gradual rollout of 0.14 to 0.15: deploy 0.15 at once (PR 10's release notes) |

One write of 0.14's has no entry: a session's renewal (`renewSession`).
Renewed by an old isolate after the cutover, the session's row is no longer
its seal's, and its next use is `stale`. Its person signs in again. Last-use
stamps are no part of any object.

The trigger is a database object, which the database's owner can drop.
Then a late write lands, its object `stale`, and a row put back over it is
still refused by the use's probe of 0.14's newest access entry
(UsesSeeOldWrites). Refusal and probe cover for each other (TLC breaks
`AllowedOnlyWhenGranted` only without both), so the probe stays.

**The probe checks the MAC of what it finds** (UsesSeeOldWrites, as the
model reads it: the newest *authentic* write). The statement's probe
(`use_credential`, unchanged) reads the newest access entry in the vault's
name. Only when that entry is past what the principal's newest change
accounts for does the vault read the entries again and check their MACs
(`#oldWrite`), paging back past forged ones. An entry forged in the
vault's name used to make every use of that account `stale`. Now it is
passed over, and the use is decided as its replay decides it. The common
case costs nothing more: nothing to read again. The check is the use's own
work, and bounded as the statement is:

- it reads from the probe's entry down, never above: the use's statement
  has committed by then, and a change's entry since is none the use
  decided on (review r1: read from the newest, a grant committed meanwhile
  made the use `stale`, which its replay allows);
- it runs within the use's place in admission and its deadline's race
  (review r2), and a plain value past its deadline never leaves, as a key
  opened late does not;
- it writes nothing. A report of the forged entry would wait for 0.14's
  head, or for the vault's settling, past the use's deadline (reviews r3,
  r4: an old isolate's write holding the head held a named use past its
  deadline). The next decision about the principal reports it
  (`#integrity`), as it always has.

**Dual fencing: changes that write no 0.14 entry take 0.14's head**
(EntryLessHead, Migration015EntryLess). T149's revoke (`revoke_credential`)
and an unbind's ends (`change_bindings`) write the credential's or the
binding's row under the app's MAC, which 0.14 reads, but no 0.14 entry. A
0.14 use of a credential checks it under 0.14's head (`credentialStill`),
then commits. Without the head, a revoke commits and answers between the
two, and the old use goes on. TLC finds it once the model's 0.14 use of an
app's row takes two steps, its check, then its commit (it was one). Each
now takes 0.14's head first: after the members' rows, before any row of
the app's (row, head, issue lock, fence; Migration015.tla's AppHeadFirst).
Each of 0.15's other changes that write no 0.14 entry:

| change | what 0.14's old code reads | fenced by |
|---|---|---|
| a sign-in through a binding, a token's issue (`sign_in`, `issue_token`) | nothing it can name before the issue commits | none needed (IssueOwnLock) |
| a revoke, an unbind's ends | the credential's or binding's row | 0.14's head, now |
| a session's renewal | its row, `expires_at`, under the app's MAC | none needed: it only extends |
| the bulk cap | `vault_releases`, which 0.15's uses do not write | none: below |

The bulk cap: 0.14 counts its releases in `vault_releases`, and 0.15 its
uses in `log_bulk`, each blind to the other. A principal that reads through
both at the switch may read up to twice the cap within one window, once.
Refused writes do not change this: it is reads. Accepted, as a rate limit
across a deploy, and said in PR 10's release notes.

**`seal_binding` compares the scope.** PR 9a's review (P3): the guard
compared every column of a binding's genesis but its scope. A scope written
past the cutover's read, under its locks, would have been sealed as read,
and its every use refused (`stale`). Now the row's scope must be the
object's, as JSON (`pg_input_is_valid`, then jsonb equality, so key order
does not matter), or the binding is not sealed and the cutover asks the app
again. A stored scope that is no scope at all, which 0.14 never writes, is
left unsealed and reported (`planCutover`); comparing it would otherwise
send the cutover back on every try.

**T144 and T160, end to end.** An archived key gets its object and its
`secret.delete`, and its unarchive through the API restores it, and it
serves (`packages/server/test/cutover.test.ts`, the first case). A binding
made on 0.14 is sealed with the instance it was made on, and a run signs in
through it right after the cutover; one not vouched for, edited since, or
naming another instance signs nobody in
(`packages/vault/test/cutover.test.ts`, T160).

**The restore drill on 0.15's log** (`packages/server/test/restore-015.test.ts`;
`docs/restore.md`, "On 0.15's log"). An instance cut over, writing under
0.15, its checkpointer sealing, is backed up with `coffre backup`, restored
with `coffre restore --keys` and migrated. Then:

- the signer, still remembering a pair signed after the backup, refuses
  the restored log ("the database lost entries the signer sealed"), as it
  refuses a rollback. That refusal is what a restore meets;
- given a new memory, it takes the database's newest pair, and says so;
- the vault finds the log cut over; its trees verify (`verifyTrees`); the
  token serves the value it served at the backup; the log replays to every
  use with no fault; a change on top is sealed;
- the wrong vault key: the signer refuses the log's checkpoints ("not a pair
  signed by this log"), and `coffre verify backup` refuses the backup.

`scripts/restore-drill.sh` drills the Workers example, which runs 0.14's
log until PR 10 wires the checkpointer and flips the default: it moves to
the new log there, as the plan says.

**The spec** (`formal/Migration015.tla`; R45). Adoption, its tick and its
five protections are gone from the model, replaced by OldWritesRefused (git
history has them, before this PR). Each protection, turned off:

| protection | scenario | TLC finds |
|---|---|---|
| OldWritesRefused | Migration015, Migration015App | `OldWritesBeforeAnchor`: a late write lands past the anchor |
| OldWritesRefused + OldWritesFence | Migration015, Migration015App | `NothingAllowedAfterAnswer`: each alone covers a late write across a 0.15 use |
| OldWritesRefused + ExchangeOnlyIssues | Migration015Issue | `NothingAllowedAfterAnswer` |
| OldWritesRefused + UsesSeeOldWrites | Migration015Tamper | `AllowedOnlyWhenGranted`: a row put back over a late write |
| EntryLessHead | Migration015EntryLess | `NothingAllowedAfterAnswer`: a revoke answered between 0.14's check and its commit |

Migration015Marker, the probe's cheaper alternative, now drops the trigger
(OldWritesRefused off), as its premise is a late write that lands.

### 10. The flip (high)

- **Scope.**
  - The default becomes `'0.15'`.
  - The backup and restore drill (`scripts/restore-drill.sh`) runs on the new
    log.
  - The release notes cover the cutover, the switch to `at` days, and the
    bulk cap's change of meaning (decision 4 below).
- **Tests.** The whole suite; `pnpm bench:workers` / `bench:node` at R44's
  1,000/s; conformance on both kinds; the drill.

#### As built: PR 10 (W273)

**The default is 0.15's log.** `VaultOptions.log` defaults to `'0.15'`; the
deployment entries take no `log` at all. Once cut over, the database
refuses 0.14's writes (PR 9b), so a deployment going back to 0.14's log would
only fail. 0.14's path stays, for the suites, until 0.16 removes it:
`COFFRE_TEST_LOG=0.14` runs the suite on it, as CI's job "Tests on 0.14's
log" does beside the default's.

**What a vault under 0.15's log needs, or it is refused, by name** (the
coordinator's steer: a missing binding fails loudly, never a quiet fallback
to 0.14's unwrap, which would hide the hot path's gain):
- `sealThrough` and `heldOutside` (T151): `prepareVault` refuses a vault
  without either, as it refused one without `sealThrough`;
- on Workers, `vault(env => …)` takes `hotDatabase` and `checkpointer`,
  required in its type and checked at the first call
  (`postgres(env.HOT_HYPERDRIVE)`, `env.CHECKPOINTER`);
- on Node, `localVault` and `serveVault` take `hotDatabase` and
  `checkpointer: { memory }`, unless the caller seals through a checkpointer
  of its own (the suites, the benches).

**The checkpointer opens before anything serves.**
- *Workers:* the vault starts its object (`startCheckpointer`) from each
  isolate's first call, before that call goes on, and keeps whether it did,
  a settled value. The object now sets its alarm before it opens, so one
  that refuses to open (a log it cannot take: a restore, another key) still
  ticks, each tick trying to open again and making the next days of uses
  meanwhile, as plan PR 7 left it. A start refused that way counts as
  started; an object out of reach is tried again by a call 10 s later.
  Neither fails the call: a use needs no checkpointer, and a change fails on
  its seal, with why.
- *Node:* `keepCheckpointer` (`checkpointer-node.ts`), which `localVault`
  awaits before it returns: `runCheckpointer`, and while its open is
  refused, an alarm kept once in `<memory>.alarms`, and another try every
  10 s, each making the next days first (PR 7's "keeps making days when the
  open fails", review r4). Meanwhile a change's seal fails with the reason,
  and `heldOutside` reads the memory file as ever. It stops before the
  vault's databases close.
- Either way, no visit meets "no checkpoint row and no pair held outside"
  (review r5 of PR 8): the open writes the genesis pair first.

**One vault process per database on Node.** Two would each run a signer;
the floor's check (the barrier) refuses the second's ticks, alarmed. On
Workers the object is one per instance by construction. Said in the docs
and the example, not enforced.

**The deploy window.** A 0.15 vault decides nothing before the cutover,
which only a 0.15 app asks for. Between the vault Worker's deploy and the
app's, an old app's requests are refused. `pnpm run deploy` now builds the
app first, then deploys the vault and the app back to back, so that window
is one `wrangler deploy`, not a Vite build and a deploy. The release notes
say so, and to deploy both at once.

**The dev loop.** `pnpm dev` starts its checkpointer's memory over
(`dev/start.sh`), and the seed empties 0.15's log with the rest: it runs
before anything asks the vault, which keeps the log it found.

**The restore drill** (`scripts/restore-drill.sh`) runs the Workers
example, now on 0.15's log: before the backup, the sealed log verifies
(`GET /api/audit/trees`); after the restore, under a checkpointer with no
memory (each start's own state), it verifies from the restored newest
checkpoint, and a change written on top is sealed past it.

**Numbers** (`pnpm bench:workers`, before on main's 0.14 log, after on
0.15's with the hot path; Postgres 16.14 on Debian, R62; ms of CPU of both
Workers' workerd, warm median, cold median):

| path | 0.14 | 0.15 |
|---|---|---|
| POST /api/reveals, one key | 16.9, 83.5 | 12.2, 64.5 |
| POST /api/reveals, 30 keys | 18.3, 93.6 | 121.9, 226.5 |
| export: reveals as a service (30 keys) | 20.7, 92.9 | 118.3, 227.7 |
| page: audit | 67.7, 188.5 | 50.1, 188.9 |
| sign-in (GitHub, both legs) | 16.8, 74.0 | 23.2, 84.7 |

The rest (`/readyz`, `/api/me`, the list, the pages, the cron) within
noise. A read of one key, `/use`'s shape, costs about a quarter less. A
read of many keys is one vault call and one statement per key, about
3.5 ms each, where 0.14 opened them in one unwrap: several times 0.14's
CPU for a whole environment, CI's read, until a request's uses go to the
vault together. The examples mount no credential proxy, so the bench has
no `/use` row.

**Not done here, and why.**
- An index with `number` in it for the verifier's planted-use filter (PR 8,
  "PR 10 or later"): a cost under forged rows alone, not a ship blocker
  (R68). Later.
- Witnesses and retention on Node: `runCheckpointer` takes them, the Node
  vault's configuration does not yet; no deployment uses either (R40).
