# 0.15: the implementation plan (W211)

How the hot path of [`hot-path-one.md`](hot-path-one.md) (W208, W211) and the
Merkle checkpoints of W209's `merkle-checkpoints.md` (#365, with W212's tree
shape, #368) become shipped code.
It is a sequence of pull requests, each of which leaves `main` shippable.
Written 2026-10-27, after Erwin's decisions R50 to R55.

## The rules every PR follows

- **The spec comes first (R45).** PR 1 is the TLA+ spec, and every later PR
  names the part of it that it implements. A PR that changes a protection
  changes the spec in the same PR. TLC must fail without each protection.
- **Behind one switch until the end.** The 0.15 path is built next to the 0.14
  path behind one internal setting, `log: '0.14' | '0.15'`. It is not a
  deployment option: the default stays `'0.14'` until PR 10 flips it.
  - Until the flip, a release behaves exactly as 0.14.5, and `pnpm test:compat`
    (0.14.5 against this checkout's schema) stays green.
  - Each PR runs the suite on both settings, so the new path is tested as it
    grows.
  - 0.16 removes the 0.14 path (the contract step).
- **Migrations only add (AGENTS.md, expand then contract).** 0.15's migration
  adds tables, nullable columns, functions and grants. 0.14.5's code keeps
  serving on it until the deploy. What 0.15 stops using is dropped in 0.16.
- **Postgres serves; SQLite is for tests.** The hot path is Postgres-only
  (R50). SQLite (tests, local development) gets the same `decide`, `applyOp`
  and replay, in one `BEGIN IMMEDIATE` transaction per call. SQLite has a single
  writer, so the fence is implicit: every guarantee the model checks holds
  trivially there. One test file runs the same cases on both engines.
- **Reviews (R29).** Muse on every PR. Each PR marked **high** also gets
  Fable, once, after Muse passes.
- **Numbers.** Every PR keeps `pnpm bench:workers` and `request-cost.test.ts`
  within the budgets measured here: about 0.6 ms of Postgres CPU per use, 1
  statement, under 30 buffers, flat as the log grows (R48).

### 3. Seals, decisions and replay as pure code (high: auth, crypto)

- **Scope.** In `packages/vault`, beside `decide.ts`:
  - **The object model.** Every decision input is one object with a seal,
    HMAC-SHA256 cut to 16 bytes under the row key:
    - principal: the member, its grants, its role assignment;
    - credential: a token or binding, with its scopes;
    - secret: a value version, with its nature and wrapped key; a
      reference's holder key carries its `source`;
    - environment: with its slug, protection, parent and owner (forks, `@me`).
      A slug-scoped role decides on the slug, so a rename is a change
      (`environment.rename`), and 0.14's `environment.update` takes the
      0.15 fence during the cutover (PR 2's trigger);
    - roles: the role tables, as one object;
    - policy: the deployment's cap configuration (`bulkLimit`), as one
      object.
    - 0.14's `Policy` value is rebuilt from the roles object and the
      protection of the environments read.
    - **An object's key** is the first 16 bytes of SHA-256('coffre.object.v1\0'
      + kind + '\0' + id), as a uuid (W216).
  - **The use row** (W216) adds what the replay needs:
    - `purpose` and `keepsSensitive` in one smallint: the purpose's code
      (0 reveal, 1 run, 2 compare, 3 copy, 4 use, 5 expose), plus 256 when
      a copy keeps values sensitive (schema 0022; `purposeCode`);
    - `at`, the place, a uuid, or NULL when it is the key's environment.
  - **Pure functions:** `applyOp` (a change applied to a state), `decide`
    (stale and tampered per input, then the 0.14 rules, then the bulk cap),
    `bulkStep`, and the replay.
  - **Cost:** each seal is one probe on a cache miss (measured: about 25 µs
    each, uuid keys about 20% cheaper than the prototype's text keys).
    - A plain use reads about six inputs.
    - A use through a reference reads the holder's secret, its source, and
      up to three environments: up to nine probes.
    - PR 5 measures the worst case against the budget of under 30 buffers
      per use.
  - **The bulk cap:** others counted over `window + refresh + deadline`. That
    is TLC's finding: uses are decided in number order, not by `at`.
- **Files.** `packages/vault/src/decide.ts`, and new modules for the objects,
  replay and bulk; `formal/lean` in the same PR. `pnpm formal:lean` holds
  `decide` to its model, so the Lean model learns stale, tampered and the cap.
- **Spec part.** `HotPathOne`'s `Decide`, `ReplaySound` and the cap rule.
- **The cap's configuration is a sealed input** (review r1, W216).
  - **Where it lives:** every change to the policy object carries the whole
    policy as its `value`, `count` and `windowMs` included.
  - **How a use reads it:** `use_credential` reads the newest policy change's
    `value.bulk`, in the use's own snapshot, never the policy row: the
    statement moves the cap before anyone checks the row's seal, so a row
    put back would move it otherwise than the replay. It is not a call
    parameter either. So during a deploy where two configurations coexist,
    live still equals the replay, and a stale policy row is refused `stale`.
  - **How it changes:** at every vault start, before it serves a use, the
    vault writes a policy change under the fence whenever the log's policy
    differs from its `bulkLimit`. The cutover (PR 9) writes the first one.
  - **Spec:** `HotPathOne` models it as protections `CapFromPolicy` and
    `CapSealed`.
  - **Test:** change the count, restart with two configurations serving at
    once, and hold the replay to live across the change.
- **Tests.** Unit tests; hegel property tests that `decide` over `applyOp`'s
  replay equals `decide` over the rows whenever the rows are the replay's,
  and differs only as `stale` or `tampered` otherwise; `pnpm formal:lean`.

### 4. The change path (high: locking)

- **Scope.** Every vault write to a decision input becomes one call to
  `change_input`:
  - the fence exclusive, a CAS on the object's seal, the payload applied as
    logged, the entry numbered under the lock;
  - **a seal check on the base row** (`HotPathOne`, ChangeChecksSeal; Fable
    on PR 1). Under the lock, `change_input` refuses `stale` unless the
    row's seal equals the object's newest change entry's seal: one probe of
    `log_changes`, as a use makes.
    - **Why the CAS is not enough:** it only compares with what the vault
      read. A row a writer put back passes it, and the change would seal its
      payload applied to the tampered base, re-sealing the rollback.
    - **Example:** revoke B seals {A}; a writer puts back {A,B}; a grant of
      C would seal {A,B,C}, and B would be served.
    - **Who builds it:** PR 2's `change_input` gets the probe too.
  - it answers once the entry is sealed (R51; until PR 6 lands, once
    committed).
  - The app's other audited writes (none of them a decision input) append
    to `changes` under the fence shared, as uses do. They never wait for a
    use.
- **Files.** `packages/vault/src/store.ts`, `vault.ts`, `log.ts`, and the
  server's writes through the vault.
- **Spec part.** `HotPathOne`'s change actions: `ChangeLocks`,
  `ChangeNumberUnderLock`, `LockToCommit`, `CommitBeforeAnswer`, `ChangeCAS`.
- **Lock order: row, head, fence** (`Migration015.tla`, ChangeHeadFirst,
  RowFirst). Until 0.16, a 0.15 change also advances 0.14's fence (PR 9).
  - **Row:** it takes the object's member queue lock first, as 0.14's
    `lockMembers` does: 0.14 takes member rows before its head.
  - **Head:** then 0.14's head.
  - **Fence:** then the 0.15 fence.
  - **Any other order deadlocks:** with a 0.14 write under PR 2's trigger,
    with a 0.14 decision holding a member row, and with a vault start on the
    cutover's slow path. Postgres breaks such a cycle only after 1 s, while
    the fence blocks every use.
- **Tests.**
  - The integration fixture's transaction tracking, kept, so that no vault
    call happens inside an app transaction.
  - fence-one's cases as integration tests: the replay of a change, another
    payload under its request id, two changes to one object.
- Behind the switch.

#### As built: PR 4a (W218), and what waits for 4b

PR 4 is two pull requests (coordinator, 2026-10-27). The vault's own
inputs go first: members, grants, the roles, the bulk cap, an
environment's protection and slug. The app's writes to credentials,
bindings, environments and secrets come in 4b (T117). There are about
40 of them, in `signin.ts`, `workloads.ts`, `services.ts`, `projects.ts`,
`secrets.ts` and `references.ts`. Each runs in an app transaction, which
may not call the vault, and a secret's version carries ciphertext that
no log payload should. Routing them through the vault needs a design of
its own. For example, a CI sign-in that issues a credential would wait
up to a tick (500 ms) for its seal (R51).

What 4a builds:

- **`0023_change_path`** replaces `change_input`, which nothing called.
  - It takes `genesis` and the ops of members, grants, the roles, the
    policy, and an environment's protection, slug and archiving.
  - It writes the rows the vault's login cannot (an environment's,
    `log_config`'s) from `p_value`: the object the vault made with
    `applyOp` and sealed.
  - It refuses a payload that does not name its object (`ref`, below).
  - SQLite runs its twin, `changeOnSqlite` in `store.ts`.
- **The switch:** `VaultOptions.log`, `'0.14'` by default. It is the
  vault's, not a deployment's to set. With `'0.15'` the vault also needs

- **Inside 0.14's decision.** With the switch on, every vault decision
  that changes an input stages the op each of its writes makes
  (`changes.ts`), and logs it in the same transaction:
  - Before the writes, it reads each object and checks its seal: the
    vault's over the row, and the object's newest change's.

#### As built: PR 4b (W220), the app's writes to credentials

4b is two pull requests too. This one routes every write of the app's
that makes or ends a **credential**: sign-ins, tokens, handles, CI and
workload sign-in, renewal, sign-out, revokes, a member's removal and
re-admission, unbinding, the legacy scope seal, and the APP_KEY
rotation's sign-outs. Environments and secrets follow in the next one,
on the same mechanism (below, "As built: PR 4b, part 2").

**The design.** The vault prepares, the app commits, and the vault
answers once sealed:

1. **Before the app's transaction,** the app sends the vault
   (`Vault.prepare`) each row it will write: its columns as it read them,
   with their seal, and as it will write them. The vault reads nothing.
   - It checks the seal is its own over the columns it was given
     (`tampered` otherwise).
   - It works out the ops that turn the before into the after
     (`opsBetween`: `credential.issue`, `.scope`, `.renew`, `.revoke`).
   - It applies them with the replay's `applyOp` and seals each one. It
     refuses any other difference, such as a principal changed or a revoke
     undone.
   - It returns each change sealed and MAC'd.
2. **In the app's transaction** (`audited()`), once its rows and its 0.14
   entries are written, all of the changes go in one round trip of
   `app_change` (migration 0025). It is a definer function that only
   `coffre_app` may run:
   - 0.14's head, which `audited()` already holds, then the fence
     exclusive;
   - a retry finds its entry by request id;
   - ChangeChecksSeal: the row's seal is its object's newest change's;
   - ChangeCAS: the seal moves only from the one read;
   - the entry, numbered under the lock.

   The app writes its rows itself, as 0.14 does, and `app_change` writes
   only the seal.
3. **After the commit,** the app asks `Vault.waitSealed` for the newest
   number (R51), then answers.

The row and its change commit together or roll back together. No vault
call is made inside a transaction: the fixture's guard holds that for
the two new calls too.

**Example.** Ada revokes token T, whose row is (live, seal S1):
- the vault's `prepare` gets (live, S1) before and (revoked) after, and
  returns `credential.revoke` from S1 to S2;
- the transaction sets `revoked_at`, appends 0.14's `token.revoke`, then
  calls `app_change`. Under the fence, the row's seal is S1 and so is
  T's newest change: S2 is written and the entry numbered;
- the commit, then `waitSealed(n)`, then 200.

If a writer had put back T's row from before an earlier revoke, the seal
would be valid (the vault made it once) but not T's newest. `app_change`
refuses it as stale, and the whole write rolls back.

**Sets chosen under the head.** Some writes revoke "every live credential
of X": a member's removal, an earlier membership's, a binding's, an
account's sessions, a rotation step's. The app reads the set before the
transaction to prepare it, and reads it again in the transaction. They
must be the same (`AppChanges.expectRevoked`). Otherwise another write
came between, and the write is prepared again (`retrying`, three tries).
Without that check, a credential issued in between would be revoked with
no change: its row would be revoked while its log said live.

**What a workload's proof decides under the head** (an enrollment's
scope and end, `kind.commit`): the first try prepares with the binding's,
and if the proof decided otherwise, the write is prepared again with what
it decided. Those are database facts, so the second try matches.

**Answers to the brief's questions:**

1. **Atomicity:** as above.
2. **Secrets:** next PR. Ciphertext stays in `secret_versions`: the object
   is W219's `secretObject`, which holds the version id, the nature and
   the wrapped key. It does not need a digest of the ciphertext. Each
   version has a fresh data key, and the envelope's AEAD binds the
   ciphertext to it, so a swapped ciphertext fails to open.
3. **R51's wait on hot paths:** milliseconds, not the 250–500 ms feared.
   `sealThrough` ticks at once, rather than waiting for the 500 ms beat.
   Numbers are below. R51 stands for every change, issuance included,
   and nothing is left for Erwin to decide here.
4. **The gaps W218 found:**
   - `revokePriorMembership` and `removeMember` now log each revoke as a
     change.
   - `renewSession` runs in `audited()` (the head first) with its
     `credential.renew` change. It still writes no 0.14 entry ("the
     session's last use shows it"), and with 0.14's log it is unchanged.
   - A project's deletion, which tombstones its slug but not its
     environments', is the next PR's.

**Bindings are no input of 0.15's.** No decision of 0.15's reads a
binding, so no change of the log is made of one, and its seal stays
unused:
- `use_credential` reads `credentials` only.
- A credential issued through a binding now carries the binding's scope
  in its row: `exchangeToken` copies it with 0.15's log on, which 0.14
  ignores (it reads the binding's).
- A workload's session carries its effective scope, `sessionScope`, the
  binding's reads included.
- A binding's end revokes what it issued, each revoke a change.

**Decisions:**

| decision | instead of | why |
|---|---|---|
| the vault prepares from columns the app hands it, and checks their seal by HMAC | the vault reading the rows itself | It needs no grant on `credentials` and no database round trip. Under the fence, `app_change` holds the seal to the object's newest change, so a valid but stale seal is caught there (ChangeChecksSeal). |
| the app writes its rows; `app_change` writes the seal | the vault writing the app's rows through definer functions | Those rows carry the app's MAC under APP_KEY, which the vault does not hold, and about 40 sites' logic would move into plpgsql. |
| one atomic transaction | the app commits, then the vault seals after | The vault would seal whatever the row holds, a writer's row included, which is the attack ChangeChecksSeal exists for. A crash in between would leave a row the log never covers. |
| `app_change` takes no member lock: head, row, fence | `change_input`'s member, head, fence | The app's transaction holds 0.14's head before any row. Taking a member's lock after it would wait for a 0.14 decision that holds the member and waits for the head: a cycle (Migration015App, `AppHeadFirst`; TLC finds it without). |
| the ops come from the difference of the columns (`opsBetween`) | each site naming its op | One mapping, W219's `credentialObject`, and no op for the app to get wrong. A difference no op makes fails the write. |
| R51 for every change, issuance included | issuance not waiting | It costs about 5 ms alone (below), and the rule stays one rule. |
| ticks shared by the changes waiting at once (`Checkpointer.tick`) | a tick per change | 8 changes at once wait 22 ms at p50 instead of 42 ms, and 32 at once 77 ms instead of 178 ms. Throughput is 300–490 changes/s instead of 150–220. |
| the app learns the switch from `about().log`, once per vault object | a setting of the app's own | One switch, the vault's. The runtime keeps its vault for the isolate, so it is asked once. |

#### As built: PR 4b, part 2 (W222): environments and keys

The rest of the app's writes to the objects a use decides on go through the
same `prepare`, `app_change` and `waitSealed`:
- **environments:** made (a fork's and a personal config's included),
  renamed, archived, restored, deleted;
- **keys:** a value written, marked or restored (a new version each), a
  reference made, archived, unarchived, reset to the parent's in a fork and
  overridden again, and erased with their place;
- **a project's deletion:** each of its environments too.

`prepare` takes three kinds of rows now, each mapped by W219's function
(`credentialObject`, `secretObject`, `environmentObject`), and `opsBetween`
finds the ops between the objects before and after:
- **a key:** `secret.write`, the whole object, value or reference; or
  `secret.delete`. A key's object is small and every write of it replaces
  it, so there is no finer op.
- **an environment:** `environment.create`, with the protection the policy
  gives its id (a protected fork's: `protectIds` protects the id before the
  row exists); then `.rename`, `.archive` (both ways), `.delete`, in that
  order. Its protection stays the vault's (4a's `environment.protect`).
  A change of the app's to it, or to a parent, an owner or a project, fails
  the write.

**What of a key enters the log** (the brief's question 3): the version's id,
its nature, its KEK's ids and its wrapped data key. Never the ciphertext,
the IV or the tag, nor a digest of them (a test holds the payload to that).
That is enough, because each version has a data key of its own and the
envelope's AEAD binds the ciphertext to it:
- a writer who swaps in another version's ciphertext gets a value that
  fails to open with the sealed key: refused, never served;
- a writer who swaps the wrapped key changes the object: `tampered`.

**An archived key is no object.** Archiving is `secret.delete`, whose seal
is none, and `app_change` writes none on the row. `use_credential` reads
only unarchived keys, so the row and the log agree: no key. Unarchiving is a
`secret.write` from no object. Example, key K sealed S1:
- archive: `archived_at` set, `secret.delete` from S1, row seal null;
- a writer clears `archived_at` around the app: the row reads live with no
  seal, and every use is refused (`stale`), as is the next change
  (ChangeChecksSeal: no seal on the row, the log has changes);
- unarchive through the app: `secret.write` from no seal, row seal S2.

**Deletion.** Under the head, in the deletion's own transaction:
- each environment it takes (the one, its personal configs; or a project's
  every standing one) gets its tombstone and `environment.delete`;
- each live key under them has its versions erased, gets `secret.delete`
  and, with 0.15's log, is archived.
- **Why archive:** a use reads unarchived keys. Left unarchived, an erased
  key would read as an object with an empty wrapped key under no seal:
  `tampered` live where the replay says the key is gone. Archived, both say
  no key. With 0.14's log the keys stay unarchived, exactly as 0.14 leaves
  them; a test pins that.
- **A project's environments' tombstones:** with 0.15's log only. 0.15's
  environment is deleted by its own slug (`environmentObject`), while 0.14
  takes a project's tombstone for its environments', and finds a deleted
  project's entries by their slugs under it (`coffre audit
  market~deleted-…/dev`). The cutover (PR 9) must seal the environments of
  a project 0.14 deleted as deleted: by the project's tombstone, not their
  own slug.

**Sets chosen under the head.** A deletion's environments and keys, and the
personal configs an archive or restore takes with their environment, are
read before the transaction to prepare their changes, then read again under
the head (`Erasure.hold`, `patchEnvironment`). A different set is a write
meanwhile: the whole write is prepared again (`retrying`), as part 1's
`expectRevoked`. Example: a personal config's owner writes `LATE` while the
config is being deleted. Without the check, `LATE`'s version would be
erased with no change logged: a live row, its wrapped key emptied, under its
old seal, `tampered` to every use. With it, the deletion reads again and
deletes `LATE` too (tested).

**A key's or an environment's state re-checked under the head.** An archive,
an unarchive or a reset is prepared from the row as read; the transaction
must find it in the same state, archived or not. ChangeCAS already refuses a
row whose seal moved, but only when there is a change to make: if the read
found the key archived already, nothing is prepared, and a key unarchived
between the read and the transaction would be archived with no change.
`setSecrets` and `restoreVersion` re-check the keys under the head against
their first read (`secretHeads`), so the read of the objects they prepare
from must be that state too, or the write is prepared again (review r2's
P1: a key archived and unarchived between the two reads).

**A new environment carries its protection in its row** with 0.15's log (the
app inserts `protected`; it may insert any column, and updates only slug,
name and `archived_at`). `audited` holds the caller's policy to the head
(`policyStill`), so the protection sealed is the one the policy has.

**Lock order, and the spec.** Unchanged: the head, the rows, then the fence,
as in part 1 (Migration015App's AppObject is any of the app's rows,
environments and keys included). A write of many objects, a project's
deletion, takes the head once, writes its rows, and makes all of its
changes in one round trip of `app_change`, under the fence once. The
re-reads of a set or a state under the head are app-level guards of the
same kind as part 1's `expectRevoked`, not a lock or a re-check of the
change path's, so `formal/` is unchanged; tests hold each one (below).

Decisions:

| decision | instead of | why |
|---|---|---|
| a key's change is the whole object (`secret.write`), or `secret.delete` | an op per field | Every write of a key replaces its object, and the replay applies one op. |
| archiving a key is `secret.delete`, its row's seal none | the object keeping an `archived` flag | `use_credential` (0024) already reads an archived key as none, and so does the replay; a flag would need a new use statement. |
| erasure archives the keys, with 0.15's log only | leaving them as 0.14 does; logging the erased version as a `secret.write` | Left live, the use reads a key the log says is gone. A `secret.write` of an empty wrapped key would agree, but log a key that no longer exists. Under 0.14 nothing changes, as the coordinator asked. |
| a project's deletion tombstones its environments' slugs with 0.15's log only | with either log | 0.14 finds a deleted project's entries by its environments' slugs (`coffre audit market~deleted-…/dev`); with 0.15's log, that path takes their tombstones too. |
| sets and states re-read under the head, the write prepared again when they differ | locking the rows before `prepare` | `prepare` is a vault call, which no transaction may hold (AGENTS.md). |

**Left out, recorded as tasks before the flip (PR 10):**
- **an ended reference keeps serving.** A reference's end is 0.14's vault

### 6. Merkle checkpoints (high: crypto)

- **Scope.** W209's tree in W212's shape (#368), behind one seam
  (`append(leaves)` → signed heads; `prove(number)`).
  - **Two growing RFC 9162 trees**, one per retention class: changes (kept
    for good) and uses (dropped by day). Each has its own origin, and a tick
    signs both with the same `upto`.
  - **One pair.** The two heads are one memory record, written in one
    statement, checked as a pair when opened and at each tick, and witnessed
    as a pair. The verifier merges both trees by number.
  - **Tiles partitioned by leaf range,** so that retention drops a table:
    1.16 s and 294 KB of WAL, against 13.8 s and 3 GB for a `DELETE` (W212).
  - **Below a retention cut, one tile per level:** about 5 tiles, against
    10.8 MB a day kept for good.
  - **To decide during the port** (record the call and why in
    hot-path-one.md): no level-0 tiles for the uses tree. That saves 41 B an
    entry (about 16% of storage) and 85% of the tree's WAL; a proof's leaf
    read goes from 0.56 to 2.1 ms p50.
  - **Carry W212's fix:** `tree.ts` tested powers of two with 32-bit
    `n & (n - 1)`, which splits trees past 2^32 leaves wrongly (day 50 at
    1,000/s). Keep its regression tests.
  - A 500 ms tick.
  - The signer's last head kept in core (R54), if its cost stays within the
    budget.
  - The barrier is `close_one`: no lag.
  - **The barrier checks the floor of `at`** (`HotPathOne`,
    BarrierChecksFloor; Fable on PR 1). It requires `at_floor` to be the
    value it last wrote, and alarms otherwise, like RowChecked. A writer who
    lowers the unsigned floor would let a use land where no checkpoint's

  - A change waits for its seal, and for the witness for at most 2 s, then
    answers unwitnessed, recorded and alerted (R51).

### 9. The cutover from 0.14 (high: migration)

The rows of 0.14 are not sealed to any change of the new log. The first 0.15
vault start does the cutover:

1. **Under the fence.** It takes the 0.15 fence exclusive, and 0.14's head
   lock too, each object's member queue lock first (row, head, fence: PR 4).
   - **Head lock:** not needed for safety (TLC): the fence and the row check
     of step 3 make a racing 0.14 write refuse the cutover. It buys
     progress.
   - **Lock order:** 0.14's head first (PR 4).
2. **Verify.** It verifies 0.14's chain up to its head.
3. **Check, then seal every input.** It checks each row as 0.14's
   `#integrity` does (VerifyRows): its MAC holds, and its `access_seq` names
   the newest authentic entry up to the anchor. Then it writes one `genesis`
   change per object, whose seal is the row's and whose payload is the
   object, and stores the seal on the row. Without the check, genesis seals
   a row a writer put there.
4. **Anchor.** It writes one `cutover` entry naming 0.14's last head (sequence
   and hash), so the new log's first checkpoint vouches for the old chain's
   end.

**Cutover is idempotent.** It writes a `cutover` marker under the locks and
does nothing if one exists, so two vaults starting at once, or a restart,
make one cutover. It checks for the marker without a lock first, then again
under the locks, so that each isolate's start does not stall every use.

**Old uses in flight.** Until 0.16 (PR 11), every 0.15 change also advances
0.14's own fence for the object: its audit head, and the member's
`access_seq`. A 0.14 use that read before a 0.15 revoke is then refused or
fenced by 0.14's own checks, as today. Without this, an old isolate could
release a value after a 0.15 revoke answered, with no entry in the new log
(review r1). The alternative is a drain gate: no 0.15 change answers until
old isolates can no longer serve. It is simpler to state, but on Workers it
has no bound we can promise.

**A late 0.14 write.** An old isolate can still serve briefly after the
deploy. If it writes an input after the cutover:
- the row then matches no change of the new log;
- uses of that object are refused `stale` (fail closed);
- the row audit names it.

The vault **adopts** it, at every checkpointer tick until 0.16 removes the
old path, not once:
- it reads 0.14 entries after the cutover's head, skipping 0.15's own mirror
  entries (the dual fencing's);
- it verifies each one (AdoptVerifies): its MAC and its place in the chain;
- it writes an `adopt` change citing each, and seals the *content that entry
  wrote*, not whatever the row holds (AdoptSealsEntry). Otherwise it would
  seal a row a writer put back after a late revoke, and serve it;
- it seals a 0.14 write only if it is numbered after the 0.14 entry that the
  object's newest seal names (AdoptAfterSeal).
  - **Why:** a writer who deletes a 0.15 change's mirror entry from 0.14's
    chain, and puts the old row back, would otherwise make the next adoption
    seal the older 0.14 write after the 0.15 revoke, undoing it in the new
    log (`NewChangesStand`, TLC).
  - **Its basis:** the check uses only 0.15's own signed log;
- it should also verify 0.14's chain links from the anchor and report a gap
  or a failed MAC, so a dropped entry is reported at the next tick. That is
  not modelled.

So the late write is in the new log too, and the object is served again.

- **Spec.** `Migration015.tla`. Invariants:
  - `OneCutover`;
  - `AnchorHolds`: the cutover names an authentic head and precedes every
    0.15 entry;
  - `NewLogFollowsOld`: genesis and every adoption seal what 0.14 wrote;
  - `UsesOnLoggedRows`;
  - `AllowedOnlyWhenGranted`: no use, old or new, is allowed on a state a
    writer made;
  - `EveryOldWriteAdopted`: per tick, every authentic 0.14 write that
    existed is adopted;
  - `NothingAllowedAfterAnswer`, across versions;
  - `NoWaitCycle`.
- **Invariant added:** `NewChangesStand`. However 0.14's chain is changed, no
  0.15 use is allowed on a state a 0.15 change refused.
- **Removals,** each failing as required (15):
  - the cutover's locks, the row check, and the marker;
  - dual fencing, the trigger (OldWritesFence), and the lock order;
  - adoption and its repetition;
  - chain verification, adoption's verification, what it seals, and
    AdoptAfterSeal;
  - UsesSeeOldWrites, and the rejected row marker's alternative.
- **What the seal covers.** The model's seal covers the value and 0.14's
  `access_seq`, so a late 0.14 write leaves the row `stale` until it is
  adopted, even when it writes back the same value. A seal over the object
  only would let such a row be served, and that is harmless: its value is
  the one the newest seal names. Either way, what refuses a row put back
  over a late write is UsesSeeOldWrites, which reads 0.14's newest
  authentic entry, not the row. PR 9 states which it builds.
- **Not covered:** 0.14 uses after the cutover are in no 0.15 checkpoint.
  Adoption cites only writes. Those uses stay in 0.14's own chain, which the
  cutover anchors.
- **Tests.**
  - `pnpm test:compat` both ways.
  - A drill: 0.14.5 serving while 0.15 starts on the same database, with
    writes from both, an old-path use in flight across a 0.15 revoke, and a
    late old write after the first adoption. It ends with every object in
    the new log and live equal to replay.
