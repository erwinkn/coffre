# 0.16: a smaller vault

The design for 0.16, written on 2026-11-13 before any of its code. It
replaces the vault, the contract between the app and the vault, and the
database schema. It is built on the 0.14 line, and a deployment upgrades
straight from 0.14: no deployment ever ran 0.15, whose design this replaces.

0.15 tried to refuse, on every use, anything a database writer had tampered
with. That cost a 1,164-line stored function with 31 arguments, a seal on 13
tables checked against the log on each use, and three generations of audit
tables. 0.16 promises less, on purpose, and gets most of it for a fraction of
the code.

The decisions are Erwin's, recorded as D215 to D226 in the Coffre Initiative.
The [list](#decisions) is at the end.

## In short

- **25 tables**, against 21 in 0.14.5 and 39 on the abandoned 0.15 line.
- **Two request shapes**, a use and a change. Every API operation is one or
  the other.
- **One background job**, the signer, which runs outside the database.
- **No stored function, and no lock on a use.** SQL is plain selects, inserts
  and updates. Each decision is one TypeScript function.
- **A use costs 0 to 2 database calls and a change 2**, however large the log.

## What it promises

The adversary can write any row of any table. They hold neither the vault's
keys nor the signer's storage.

**Never honoured.** A forged or edited access row, since its MAC fails. A
value moved under another key, since each version's encryption names its
secret, its version number and its sensitivity.

**Detected within about a minute.** A genuine old row put back, a row
deleted, a log entry edited, deleted or replayed, a log cut short. The signer
alerts and coffre keeps serving (D216).

Until someone acts on the alert, a restored row works. Example: Ada revokes
Bo's grant, and a database writer puts the grant row back with its genuine
MAC. Bo's next use succeeds. Within a minute the signer sees a row its own
record says is gone, and alerts. An ordinary revocation, with nobody writing
to the database behind coffre's back, takes effect within the vault's short
memory, 2 seconds by default.

**Not caught within the minute.**

- An entry deleted deep in old history. The signer re-checks a fixed slice of
  old entries each minute, and `coffre verify --full` walks all of them.
- An entry whose wake-up never left the vault, because the vault died between
  its commit and the call, and which the writer deletes within the second
  before signing. That one change can be undone silently.

**Four smaller relaxations** (D217).

1. A use already running when its credential is revoked may finish.
2. Refusals give the same answer whether or not the key exists. They no longer
   take the same time. An invalid credential is still one uniform 401, before
   any lookup.
3. The bulk cap, 1,000 distinct keys per principal per 15 minutes, sliding and
   configurable, may be overshot by the requests in flight when it is reached.
4. A use is no longer one database call. The first use of a key in a minute is
   two, and its repeats are one or none.

## Four rules

1. **The vault writes every row that turns into access, and puts a MAC on
   it.** The app never writes those tables.
2. **No request reads the log.** Requests only append to it.
3. **The signer, outside the database, holds what the database is held to:**
   the log's signed head, and its own copy of every access row's MAC.
4. **Every decision is one TypeScript function.** The same function decides a
   use and a change, and nothing in SQL repeats its rules.

## Tables

A starred table carries a MAC on each row, and the signer keeps a copy of it.

| Group | Tables |
|---|---|
| Secrets (5) | `projects`, `environments`*, `secrets`*, `secret_versions`, `dismissed_keys` |
| Access (5) | `principals`*, `grants`*, `roles`*, `policy`* (one row), `proxy_routes`* |
| Sign-in (4) | `identities`*, `passkeys`*, `bindings`* (CI trust), `credentials`* (sessions, tokens, MCP connections) |
| One-shot (5) | `device_logins`, `enrollment_codes`, `spent_id_tokens`, `oauth_clients`, `mcp_approvals` |
| Log (6) | `log_pending`, `log`, `log_index`, `log_tiles`, `log_head` (one row), `exposures` |

- **Forks, personal configs and references are three columns**, not tables:
  `environments.parent_id`, `environments.owner` and `secrets.source_id`.
  TypeScript resolves them.
- **A restriction lives in the row it restricts.** "Protected" is a field of
  the environment's row. So deleting a row can only remove access, never add
  it.
- **Versions carry no MAC.** Their encryption already binds them.
- **`exposures` is the one summary kept beside its source.** It holds one row
  per principal and key: who has seen what, and when last. Requests may not
  read the log, and the cap, "last used" and the offboarding report all ask
  that question. It is bounded by principals times keys.
- **0.14's audit history** becomes a frozen `audit_archive` table without its
  17 indexes, exportable from the CLI. The new log's first entry records the
  old chain's last hash. Pages show the new log only.

## Data structures

**Row MAC.** An HMAC over the table's name, the row's id and its content,
under a key derived from the vault's. The vault checks it on every read and
refuses a row that fails.

**The log.** Requests insert into `log_pending`, each entry with its own MAC.
About a second later the signer moves the waiting entries into `log` and
numbers them. It is the only writer of `log`, so numbering takes no lock.

- `log_tiles` holds the hashes of a Merkle tree over the entries (RFC 9162),
  stored 256 to a row. Proving one entry reads at most 8 rows, whatever the
  log's size.
- `log_index` holds one row per object an entry mentions: project,
  environment, key, principal, credential. Every filtered audit page reads
  that one index.
- `log_head` holds the tree's size and root with a MAC. It is a copy for the
  pages. The signer's own copy is the one that counts.

**The signer's mirror.** The signer keeps, in its own storage, the MAC of
every starred row. Each change entry records the MAC it replaced and the MAC
it wrote, and the signer takes an entry only if the MAC it replaced is the
one the mirror holds. Once a minute it reads the rows and compares them with
the mirror.

A running hash over the rows was the first design, and the model broke it:

1. Ada grants Bo access, and the writer deletes the grant row.
2. Ada sees Bo missing and grants again. That entry says "was: nothing",
   which is false history. A sum cannot tell.
3. Ada later revokes Bo, and the writer puts the row back.
4. Two grants less one revoke leave one grant, the rows show one grant, and
   the check passes.

With the mirror, step 2 alerts at signing, because the mirror still holds the
first grant's MAC. The mirror costs one MAC per access row in the signer's
storage, a few megabytes at 100,000 rows.

**The wake-up** (D223). After a commit, the vault calls the signer with the
hash of the entry it wrote. The call does not hold the reply. It wakes the
signer, which otherwise would poll an idle database, and it tells the signer
which entries to expect, so one deleted before signing is missed. Without it,
a trigger in the database could undo every revocation of Bo and delete its
entry, and nothing would ever differ from the last signed state.

**The vault's short memory.** An instance keeps a credential's rows and a
key's unwrapped value for a configurable number of seconds, 2 by default, 0
for never (D218). It dates them when it read the rows, not when it answered.
It also remembers which principal and key it logged in the last 60 seconds.
0.14.5 already has a `cacheSeconds`, which Equisafe sets to 330.

## Operations

**A use** is a reveal, `coffre run`, an export, a proxied request, a
signature, an MCP read.

1. If the rows in memory are fresh and this principal and key were logged in
   the last 60 seconds, answer from memory. No database call.
2. Otherwise, one read: the credential, its principal, grants and role, the
   environment and its parents, the secret and its reference, its current
   version, the policy. Check each MAC.
3. Decide.
4. If this principal and key were not logged in the last 60 seconds, one
   statement: update `exposures`, count this principal's keys in the cap's
   window, insert the log entry.
5. Decrypt and answer.

A batch of up to 1,000 keys is the same two statements.

**A change** is anything that writes: secrets, places, members, grants, roles,
the policy, tokens, bindings, a sign-in.

1. One read: the caller's rows and the rows to change.
2. Check the MACs, decide with the same function, build the new rows and the
   log entry.
3. One write: take the change lock, update each row only if its MAC is still
   the one read, insert the log entry. If a row moved, start again.
4. Reply at commit (D221), then wake the signer.

The lock is one lock that only changes take, for that one statement. The
write compares every row the decision read, including rows it only counted.
Example: three Owners each demote themselves at once. Each read three Owners
and each decision is right alone. The first write changes an Owner row the
other two counted, so they start again, and the last one is refused.

At sign-in the app verifies GitHub or OIDC, and the vault checks the passkey
itself, since only it can trust the passkey's row. Issuing the session is
then an ordinary change.

**The signer** runs in a Durable Object on Workers. Equisafe's deployment
already has that object.

- **Each second, while entries wait:** move and number them, hold each change
  to the mirror, extend the tree, sign the head. A run that dies midway is
  finished by the next.
- **Each minute:** compare the rows with the mirror and the log's size with
  the signed size, and re-check a slice of old entries.
- **On a finding:** alert.

## Pages

A request asks the vault once who its caller is and what they hold. The app
scopes its queries with the answer.

| Page | Queries |
|---|---|
| Projects | The projects the caller holds, with their environment counts |
| Project | Its environments, with key counts |
| Environment | Its keys with current version, sensitivity and last use, no values |
| Key | Its last 20 versions, and its last 10 log entries through `log_index` |
| Proxy tab | The environment's `proxy_routes` row |
| A project's users and service accounts | Grants joined with principals |
| Users, service accounts | Principals, paged |
| One user or service account | Principal, identities, grants, tokens and bindings, activity through `log_index` |
| Settings | `policy`, `roles`, `log_head` and the last check's result |
| Audit | The newest 50 of `log`, or of `log_index` for one filter, and the tiles that prove them |
| Account | Own identities, passkeys, sessions and connected apps |
| Device login, OAuth consent, MCP approval | The one row being decided |

An audit page checks each entry it shows against the tree, so an edited entry
is caught when someone looks at it.

## What grows with what

| Operation | Cost |
|---|---|
| Use | 0 to 2 database calls |
| Change | 2 calls |
| Page | 1 to 3 indexed queries of 50 rows |
| Signing | The entries written since the last run |
| Minute check | One pass over the starred rows |
| `coffre verify --full` | The whole log, and only when asked |

Nothing but the full verify grows with the log. The minute check grows with
the instance: principals, grants, credentials, keys. That is fine to about
100,000 rows, and past that it would be split by table.

Measured on a Postgres capped at 2 CPUs and 2 GB, with a 2-million-row log
and five services each hammering ten keys:

| One use | Database CPU | Ceiling on 2 CPUs |
|---|---|---|
| Repeat, one plain read | 67 µs | 30,000/s |
| Repeat, one lean stored function | 61 µs | 33,000/s |
| First in its minute, read then insert | 165 µs | 12,000/s |
| First in its minute, one stored function | 141 µs | 14,000/s |

So leaving the stored function costs about 10% on a repeat and 15% on a first
use, both far under what 1,000 uses a second need. The 0.15 line measured
0.74 to 0.85 ms per repeat on another bench, roughly five times more. Not
measured yet: the round trip through Workers and Hyperdrive, the vault's own
CPU for MACs and decryption, and the wake-up call.

## What the models hold

Two models in [Quint](https://quint.sh), checked exhaustively by TLC and
sampled by Quint's simulator (D224). They are in `formal/quint/`.

`change.qnt` covers a change, "always an Owner", and revocation against the
short memory. TLC explores 25,966,984 states with no violation. Two variants
must fail and do: a write that compares only the row it writes, and a memory
dated when the use answers.

`log.qnt` covers commits, the wake-up, the signer and its mirror, and a
writer who can put back any MAC the vault once made, delete or replay any
entry, and cut the log. TLC explores 52,048,877 states with no violation. The
bounds are small: one row, three entries, two moves by the writer. Nine
variants, each with one protection off, must fail and do. They are the
signer's requirements.

| Protection | Without it |
|---|---|
| The vault tells the signer of each entry | A deleted entry is never missed |
| A change must replace the MAC the mirror holds | False history sums to a true state |
| The log's size is compared with the signed size | A cut tail passes |
| An entry already signed is refused | A replayed entry is signed twice |
| An entry past its date is refused | An old entry is replayed later |
| A wake-up for a signed entry is dropped | A false alert |
| What is expected is noted before the read | A false alert |
| Rows and waiting entries come from one read | A false alert |
| What was signed is kept until it is moved | A false alert |

The false alerts matter because a finding only alerts. An alert nobody trusts
is worth nothing.

Trace replay holds the code to the model. Quint writes its simulated runs as
JSON, and a harness replays each step against the TypeScript vault and
compares what each answers. A trial against a 56-line stand-in replayed 2,000
runs, 82,000 steps, in 2.5 seconds and caught three planted faults. The model
must write each refusal as a step of its own, or nothing holds the code to
refusing.

## Upgrade from 0.14

One migration from 0.14.5's schema. It builds the new tables from the old
rows, MACs them, seeds the signer's mirror and freezes the old audit log as
`audit_archive`. It replaces the schema, so it cannot be the usual
expand-then-contract. The runbook is not designed yet. It will be rehearsed
on a copy of Equisafe's database before any release.

## Build order

0.16 starts from `release/0.14`, the code Equisafe runs. The 0.15 line stays
on `main` as the source to port from, and nothing merges from it.

1. **A smaller base.** Postgres as the only database, which deletes SQLite's
   schema, migrations and test engine. One Postgres driver, postgres.js. Local
   checks and a release gate in place of CI on every pull request. Each of
   these halves what the next steps must build or test.
2. **The core.** The schema and its migration, the vault's two shapes, the
   signer, the models in `pnpm formal`, trace replay in the tests, and the
   server's calls moved to the new contract. 0.14's audit chain and its TLA+
   models go.
3. **The features 0.15's line added**, each written once against the new
   contract: passkeys at sign-in, proxy routes saved per environment with
   their Proxy tab, the Terraform provider, the pages' rework. Then the small
   fixes, each checked against 0.14's code first, since some fixed bugs 0.14
   never had.

The source for step 3 is main's changelog since 0.14.5, 136 entries. Those
that begin "0.15's" describe the design this replaces and are not ported.

## Still to design

- How long the log keeps its entries.

- The signer on Node. 0.16.0 is tested on Workers only.
- The minute check past 100,000 rows.

## Decisions

| | Decision |
|---|---|
| D215 | Against a database writer without the key, detection within about a minute is enough. A use does not check the log. |
| D216 | A finding alerts. Coffre keeps serving. |
| D217 | The four relaxations above. |
| D218 | The vault's short memory is configurable, 2 seconds by default. |
| D221 | A change replies at its commit. It does not wait for the signature. |
| D222 | Old history deleted in depth is caught by the rolling re-check or a full verify, not within the minute. |
| D223 | The wake-up carries the entry's hash, for changes and for uses. |
| D224 | Models in Quint, checked exhaustively with TLC. |
| D225 | Built on the 0.14 line, with the 0.15 line's features ported over. |

Decided before this design and kept: Postgres is the only database, 0.16.0 is
tested on Workers only, and the bulk cap is 1,000 distinct keys per principal
per 15 minutes, sliding and configurable.
