# 0.16: a smaller vault

The design for 0.16, written on 2026-11-13 before any of its code. It
replaces the vault, the contract between the app and the vault, and the
database schema. It is built on the 0.14 line, and a deployment upgrades
straight from 0.14: no deployment ever ran 0.15, whose design this replaces.

0.15 tried to refuse, on every use, anything a database writer had tampered
with. That cost a 1,164-line stored function with 31 arguments, a seal on 13
tables checked against the log on each use, and three generations of audit
tables. 0.16 promises less, on purpose, and gets most of it for a fraction of
the code.

The decisions are Erwin's, recorded as D215 to D231 in the Coffre Initiative.
The [list](#decisions) is at the end.

## In short

- **25 tables**, against 21 in 0.14.5 and 39 on the abandoned 0.15 line.
  0.16.0 ships 23 of them: `passkeys` and `proxy_routes` come with their
  features, in later releases (D227). They are `packages/db/src/schema.ts`.
- **Two request shapes**, a use and a change. Every API operation is one or
  the other.
- **One background job**, the signer, which runs outside the database.
- **No stored function, and no lock on a use.** SQL is plain selects, inserts
  and updates. Each decision is one TypeScript function.
- **A use costs 0 to 2 database calls and a change 2**, however large the log.

## What it promises

The adversary can write any row of any table. They hold neither the vault's
keys nor the signer's storage.

**Never honoured.** A forged or edited access row, since its MAC fails. A
value moved under another key, since each version's encryption names its
secret, its version number and its sensitivity.

**Detected within about a minute.** A genuine old row put back, a row
deleted, a log entry edited, deleted or replayed, a log cut short. The signer
alerts and coffre keeps serving (D216).

Until someone acts on the alert, a restored row works. Example: Ada revokes
Bo's grant, and a database writer puts the grant row back with its genuine
MAC. Bo's next use succeeds. Within a minute the signer sees a row its own
record says is gone, and alerts. An ordinary revocation, with nobody writing
to the database behind coffre's back, takes effect within the vault's short
memory, 2 seconds by default.

**Not caught within the minute.**

- An entry deleted deep in old history. The signer re-checks a fixed slice of
  old entries each minute, and `coffre verify --full` walks all of them.
- An entry whose wake-up never left the vault, because the vault died between
  its commit and the call, and which the writer deletes within the second
  before signing. That one change can be undone silently.

**Four smaller relaxations** (D217).

1. A use already running when its credential is revoked may finish.
2. Refusals give the same answer whether or not the key exists. They no longer
   take the same time. An invalid credential is still one uniform 401, before
   any lookup.
3. The bulk cap, 1,000 distinct keys per principal per 15 minutes, sliding and
   configurable, may be overshot by the requests in flight when it is reached.
4. A use is no longer one database call. The first use of a key in a minute is
   two, and its repeats are one or none.

## Four rules

1. **The vault writes every row, and puts a MAC on each one that turns into
   access.** The app's database login only reads.
2. **No request reads the log.** Requests only append to it.
3. **The signer, outside the database, holds what the database is held to:**
   the log's signed head, and its own copy of every access row's MAC.
4. **Every decision is one TypeScript function.** The same function decides a
   use and a change, and nothing in SQL repeats its rules.

## Tables

A starred table carries a MAC on each row, and the signer keeps a copy of it.

| Group | Tables |
|---|---|
| Secrets (5) | `projects`, `environments`*, `secrets`*, `secret_versions`, `dismissed_keys` |
| Access (5) | `principals`*, `grants`*, `roles`*, `policy`* (one row), `proxy_routes`* |
| Sign-in (4) | `identities`*, `passkeys`*, `bindings`* (CI trust), `credentials`* (sessions, tokens, MCP connections) |
| One-shot (5) | `device_logins`*, `enrollment_codes`*, `spent_id_tokens`, `oauth_clients`*, `mcp_approvals` |
| Log (6) | `log_pending`, `log`, `log_index`, `log_tiles`, `log_head` (one row), `exposures` |

- **Forks, personal configs and references are three columns**, not tables:
  `environments.parent_id`, `environments.owner` and `secrets.source_id`.
  TypeScript resolves them.
- **A restriction lives in the row it restricts.** "Protected" is a field of
  the environment's row, a freeze a field of the row it stops, and a role
  with no row is no role. So deleting a row can only remove access, never add
  it.
- **Three of the one-shot tables are starred**, because a row of theirs turns
  into access: an approved device login becomes a session, an enrollment code
  a workload's session, and a registered client's redirects are where a
  person's approval is sent.
- **Versions carry no MAC.** Their encryption already binds them.
- **A secret says how many versions it has had, and which one is its value:**
  the newest, or none. A reference has no value of its own, and neither does
  a secret whose reference ended, until someone writes one. Example: a key
  with versions 1 and 2 is made a reference, and the reference is later
  broken. It has no value, its version 2 is history, and the next write is
  version 3.
- **`exposures` is the one summary kept beside its source.** It holds one row
  per principal and key: who has seen what, and when last. Requests may not
  read the log, and the cap, "last used" and the offboarding report all ask
  that question. It is bounded by principals times keys.
- **0.14's audit history** becomes `audit_archive` at the
  [upgrade](#upgrade-from-014): the same rows, without their indexes but
  one, never written again, exportable from the CLI. The new log's first
  entry records the old chain's last hash. Pages show the new log only.

## Data structures

**Row MAC.** An HMAC-SHA256 over the table's name, the row's id and its
content, under a key derived from the vault's. The vault checks it on every
read and refuses a row that fails. A MAC starts with four bytes that name its
key, so the vault knows which key to check and a
[rotation](#rotating-the-vaults-key) knows which rows are left: 36 bytes in
all.

- **It leaves out what only says when a row was last seen:** a credential's
  and a binding's last use, an identity's last sign-in. A use moves those on
  with no change, so a database writer can falsify them and nothing else. A
  change does not write them either: it would put back the time it read.
- **It leaves out a column that holds null.** So a nullable column added in
  a later release leaves every MAC made before it good.
- **Every time is a `timestamptz(3)`,** milliseconds, which the vault
  supplies. So a row reads back exactly as the vault wrote it, and no
  database default decides a value a MAC covers.

**The log.** Requests insert into `log_pending`, each entry with its own MAC.
About a second later the signer moves the waiting entries into `log` and
numbers them. It is the only writer of `log`, so numbering takes no lock.

`log` has four columns: an entry's place in the log's order, which tree it is
under, its place in that tree, and its body, the canonical JSON its hash
covers. It has no MAC, since the tree vouches for it once signed, and no time
of its own: an entry's time is in its body, and the signer reads it there
before it prunes, so a time edited in a column could not make it prune early.

The entries are one table and one order, under two Merkle trees (RFC 9162):
one over the entries kept for good, the changes, and one over those that
[age out](#how-long-the-log-is-kept), the uses (D229). A tree prunes cleanly
only from its start, hence two. An entry has its place in the log's order and
its place in its tree.

- `log_tiles` holds each tree's hashes, stored 256 to a row. Proving one
  entry reads at most 8 rows, whatever the log's size.
- `log_index` holds one row per object an entry mentions: project,
  environment, key, principal, credential, as `secret:<id>` and the like.
  Every filtered audit page reads that one index, its primary key.
- `log_head` holds both trees' sizes and roots under one MAC, written in one
  statement, so the two never disagree about when. It is a copy for the
  pages. The signer's own copy is the one that counts.

**The signer's mirror.** The signer keeps, in its own storage, the MAC of
every starred row. Each change entry records the MAC it replaced and the MAC
it wrote, and the signer takes an entry only if the MAC it replaced is the
one the mirror holds. Once a minute it reads the rows and compares them with
the mirror.

A running hash over the rows was the first design, and the model broke it:

1. Ada grants Bo access, and the writer deletes the grant row.
2. Ada sees Bo missing and grants again. That entry says "was: nothing",
   which is false history. A sum cannot tell.
3. Ada later revokes Bo, and the writer puts the row back.
4. Two grants less one revoke leave one grant, the rows show one grant, and
   the check passes.

With the mirror, step 2 alerts at signing, because the mirror still holds the
first grant's MAC. The mirror costs one MAC per access row in the signer's
storage, a few megabytes at 100,000 rows.

**The wake-up** (D223). After a commit, the vault calls the signer with the
hash of the entry it wrote. The call does not hold the reply. It wakes the
signer, which otherwise would poll an idle database, and it tells the signer
which entries to expect, so one deleted before signing is missed. Without it,
a trigger in the database could undo every revocation of Bo and delete its
entry, and nothing would ever differ from the last signed state.

**The vault's short memory.** An instance keeps a credential's rows and a
key's unwrapped value for a configurable number of seconds, 2 by default, 0
for never (D218). It dates them when it read the rows, not when it answered.
It also remembers which principal and key it logged in the last 60 seconds.
0.14.5 already has a `cacheSeconds`, which Equisafe sets to 330.

## Operations

**A use** is a reveal, `coffre run`, an export, a proxied request, a
signature, an MCP read.

1. If the rows in memory are fresh and this principal and key were logged in
   the last 60 seconds, answer from memory. No database call.
2. Otherwise, one read: the credential, its principal, grants and role, the
   environment and its parents, the secret and its reference, its current
   version, the policy. Check each MAC.
3. Decide.
4. If this principal and key were not logged in the last 60 seconds, one
   statement: update `exposures`, count this principal's keys in the cap's
   window, insert the log entry.
5. Decrypt and answer.

A batch of up to 1,000 keys is the same two statements.

**A change** is anything that writes: secrets, places, members, grants, roles,
the policy, tokens, bindings, a sign-in.

1. One read: the caller's rows and the rows to change.
2. Check the MACs, decide with the same function, build the new rows and the
   log entry.
3. One write: take the change lock, update each row only if its MAC is still
   the one read, insert the log entry. If a row moved, start again.
4. Reply at commit (D221), then wake the signer.

The lock is one lock that only changes take, for that one statement. The
write compares every row the decision read, including rows it only counted.

It compares by reading again. An operation names the rows it depends on as a
few conditions ("the principal with this id", "every active Owner"). The
write runs the same conditions under the lock and requires the same MACs, no
more and no fewer. So a row that came since the read stops the write as
surely as one that changed or went: two people admitting Bo at once both read
"nobody is named Bo", and the second write finds one.

The lock is taken by a statement of its own, in one transaction with the
write. A statement sees the database as of when it starts, so a write that
took the lock itself would compare against rows from before it waited, and
the three Owners below would all pass. With a driver that sends a
transaction's statements together (postgres.js, step 1 of the build order)
the two are one round trip. On node-postgres they are four.

An operation is two things: the conditions it reads by, and its decision, a
function from those rows to the rows to write and the log entry. It has no
database in hand. Reading, comparing, sealing each row, logging the MAC each
write replaced and starting again are written once, in
`packages/vault/src/change.ts`. A change that loses five times in a row
answers 503, and so does one that waits two seconds for the lock or for a
row another session holds.

Nothing but a change writes what a MAC covers. A use moves a row's last-seen
columns on, one row a statement, and takes no lock. The signer's upkeep
deletes rows through changes like any other.
Example: three Owners each demote themselves at once. Each read three Owners
and each decision is right alone. The first write changes an Owner row the
other two counted, so they start again, and the last one is refused.

At sign-in the app verifies GitHub or OIDC, and the vault checks the passkey
itself, since only it can trust the passkey's row. Issuing the session is
then an ordinary change.

**The signer** runs in a Durable Object of the vault Worker, since it needs
the vault's keys to check an entry's MAC. It is a new object: the one 0.14
deployments have, `CoffreAnchor`, belongs to the app Worker and goes.

- **Each second, while entries wait:** move and number them, hold each change
  to the mirror, extend the tree, sign the head. A run that dies midway is
  finished by the next.
- **Each minute:** compare the rows with the mirror and each tree's size
  with its signed size, and re-check a slice of old entries. Then the upkeep,
  a bounded batch of each: uses past their keep, credentials a day past
  their expiry, one-shot rows that lapsed.
- **On a finding:** alert.

## Pages

A request asks the vault once who its caller is and what they hold. The app
scopes its queries with the answer.

| Page | Queries |
|---|---|
| Projects | The projects the caller holds, with their environment counts |
| Project | Its environments, with key counts |
| Environment | Its keys with current version, sensitivity and last use, no values |
| Key | Its last 20 versions, and its last 10 log entries through `log_index` |
| Proxy tab | The environment's `proxy_routes` row |
| A project's users and service accounts | Grants joined with principals |
| Users, service accounts | Principals, paged |
| One user or service account | Principal, identities, grants, tokens and bindings, activity through `log_index` |
| Settings | `policy`, `roles`, `log_head` and the last check's result |
| Audit | The newest 50 of `log`, or of `log_index` for one filter, and the tiles that prove them |
| Account | Own identities, passkeys, sessions and connected apps |
| Device login, OAuth consent, MCP approval | The one row being decided |

An audit page checks each entry it shows against the tree, so an edited entry
is caught when someone looks at it.

## What grows with what

| Operation | Cost |
|---|---|
| Use | 0 to 2 database calls |
| Change | 2 calls |
| Page | 1 to 3 indexed queries of 50 rows |
| Signing | The entries written since the last run |
| Minute check | One pass over the starred rows |
| Pruning | At most 40 blocks of 256 uses a minute |
| Key rotation | Once over the starred rows and the versions, and only when asked |
| `coffre verify --full` | The whole log that is kept, and only when asked |

Nothing but the full verify grows with the log. The minute check grows with
the instance: principals, grants, credentials, keys. That is fine to about
100,000 rows, and past that it would be split by table.

Measured on a Postgres capped at 2 CPUs and 2 GB, with a 2-million-row log
and five services each hammering ten keys:

| One use | Database CPU | Ceiling on 2 CPUs |
|---|---|---|
| Repeat, one plain read | 67 µs | 30,000/s |
| Repeat, one lean stored function | 61 µs | 33,000/s |
| First in its minute, read then insert | 165 µs | 12,000/s |
| First in its minute, one stored function | 141 µs | 14,000/s |

So leaving the stored function costs about 10% on a repeat and 15% on a first
use, both far under what 1,000 uses a second need. The 0.15 line measured
0.74 to 0.85 ms per repeat on another bench, roughly five times more. Not
measured yet: the round trip through Workers and Hyperdrive, the vault's own
CPU for MACs and decryption, and the wake-up call.

## Rotating the vault's key

A key is replaced because someone who should not hold it may: it leaked, or a
person who had it left. So a rotation must end with the old key good for
nothing. 0.14 never gets there. Its old vault key stays configured for good,
to open what it wrapped and to verify what it signed.

What is under the vault's key, and what a rotation does with it:

| Under the key | How many | At a rotation |
|---|---|---|
| The MAC of a starred row | One per access row | Computed again |
| The wrapped data key of a version | One per version | Unwrapped and wrapped again. The value is not touched |
| The MAC of an entry in `log_pending` | A second's worth | Signed out within the second |
| `log_head`'s MAC | One | Written again at the next signing |
| An entry in `log` | The whole log | Nothing |

The last line is what lets the old key go. An entry's MAC is checked once,
when the signer takes it. From then on the tree vouches for it, and the
tree's head is in the signer's storage. A full verify computes the tree again
and needs no key.

**One rule: an instance's key is the key its policy row is under.** A vault
writes rows and entries under the key of the policy row it read, whatever key
its configuration lists first. Every use and every change reads that row
already.

For the operator it is three steps.

1. `coffre keys` makes the new key. It becomes `kek`, and the old one moves to
   `previousKeks`. Deploy.
2. Wait. The signer does the rest, and says where it is on `/readyz`, in
   Settings and in `coffre verify keys`: "rotating, 1,240 of 3,100 rows", then
   "vault-2026-10-11-hbvenp is retired, remove it".
3. Remove the old key from the configuration. Deploy.

For the signer it is three steps too.

1. **The fence.** Under the change lock, in one transaction, it signs every
   change that waits, writes the policy row's MAC under the new key, and logs
   `key.rotate`. From there on:
   - A vault with the new configuration reads the policy row under the new
     key, and writes under it.
   - A vault not yet replaced meets a row under a key it does not hold, and
     answers 503 until its deployment goes. For 2 seconds it can still answer
     uses from memory.
   - A change that read the policy row before the fence compares it at its
     write, as it compares every row it read, and starts again.
2. **The sweep.** 500 rows at a time, in primary-key order. Each batch is an
   ordinary change: it writes a row's new MAC only if the old one is still
   there, and its one entry carries both MACs of every row, so the mirror
   follows as for any change. A version's data key is unwrapped and wrapped
   again, with no entry, since versions are not in the mirror. The sweep
   keeps no cursor. Started again, it skips what has moved.
3. **Retirement.** When a pass finds nothing under the old key, no entry
   under it waits, and the fence is older than the vault's memory plus a
   minute, the signer records the old key as retired, in its own storage.

What someone can do who holds the old key and writes the database:

| When | What they can do |
|---|---|
| Before the fence | Everything. The old key is the vault's key, which is the leak itself. |
| From the fence to step 3 | A row of their own, or the old policy row put back, is served, and alerted within the minute. The signer takes no change under the old key, so the mirror never follows them. Two things are not caught: a value swapped in place and wrapped under the old key, since versions carry no MAC, and false uses added to the log, until retirement. |
| After step 3 | Nothing. A row under a key the vault does not hold is refused, and a data key that key wrapped does not open. |

So after a leak, step 3 follows step 2 at once.

**Cost.** One pass over the starred rows and the versions. 100,000 rows are
200 batches. With AWS KMS, the wrapping key rotates inside KMS and coffre
does nothing. The MAC key is then `signingKey`, which rotates as above (0.14
could never change it). Moving from a local key to KMS costs one Encrypt per
version.

**What goes with 0.14's way.**

- The old vault key configured for good.
- A rewrap command that 0.14's roadmap still owes. The sweep is that command.
- The app key's rotation. 0.14 signs every sign-in row again and signs
  everyone out. In 0.16 the app key signs no row and no entry, since the
  vault MACs them. It keeps the sign-in state and MCP's tokens, and how it
  rotates is designed with the server's move to the new contract.

## How long the log is kept

Changes are kept for good. Uses are pruned after 90 days by default (D229).

Uses fill the log: at most one entry per principal and key per minute. That
window is a setting, 60 seconds by default and 0 to 3,600, as 0.15's plan had
it. Equisafe wrote about 440,000 entries in its first month on 0.14, uses
and changes together, not yet counted apart. An entry with its index rows is
an estimated 0.5 to 1 KB, not measured yet. So 90 days of entries are about
1 GB there, and what ages out stays about that size.

**Sign-ins age out with the uses** (D231). A sign-in is a
change, since it writes a credential's row, and the mirror follows it like
any change. But every CI run signs in and every sidecar renews its
credential, so kept for good they would be the part of the log that never
stops growing. So the two trees are named for what happens to their entries,
not for the request's shape: one is kept, one ages out. The second holds the
uses, and a session's or a workload credential's coming and going. A token a
person makes is kept.

One setting, `log.keepUsesDays`: 90 by default, `null` to keep every use.
There is none for changes.

**Pruning** removes the oldest uses 256 at a time, which is one row of their
tree's lowest level: the 256 entries, their `log_index` rows and that
`log_tiles` row. The upper levels stay, and their rows hold the hash of each
pruned block. So:

- The signed head still covers every use ever logged.
- A use that is kept proves as before, from rows that are all kept.
- A full verify computes each kept block again from its entries, takes each
  pruned block's hash as stored, and must arrive at the signed root. An entry
  deleted behind the signer's back still breaks it.

A pruned use leaves 1/8 of a byte behind. `@coffre/core/log` holds the tree
and this property: with every lowest-level row below a cut deleted, the head
is unchanged, and every kept entry and every later size still prove.

The signer prunes in its minute job, at most 40 blocks a run, about 10,000
uses, so a run costs the same whatever the backlog. It records the first use
it kept in its own storage, and in `log_head` for the pages.

**What outlives a pruned use.** `exposures`, which says who has seen which
key and when last: the offboarding report and the bulk cap read it, never the
log. Example: Bo read `STRIPE_KEY` every day for a year and leaves. The log
has his last 90 days of reads, and `exposures` says he saw `STRIPE_KEY`, last
on the day he left. That is what decides which keys to rotate.

**What is lost.** When and how often a key was read, and who signed in when,
past 90 days.
`coffre log export --uses --before <date>` writes uses to a file, one JSON
line each, for whoever must keep them longer.

**What is never lost.** Who granted Bo `prod` two years ago, who changed a
value, who made a token: every change, with its proof.

**The same job bounds three more things.**

- A credential is deleted a day after it expires, in batches, each an
  ordinary change, so the mirror follows. Without this, the minute's check
  would grow with every CI run that ever signed in.
- One-shot rows are deleted when they lapse. Device logins and enrollment
  codes carry a MAC, so they go as credentials do, in changes. Spent ID
  tokens and MCP approvals carry none and are deleted with no entry: nothing
  reads them after.
- `audit_archive`, 0.14's history, is kept until the operator drops it.

## What the models hold

Three models in [Quint](https://quint.sh), checked exhaustively by TLC and
sampled by Quint's simulator (D224). They are in `formal/quint/`.

`change.qnt` covers a change, "always an Owner", and revocation against the
short memory. A change of a role reads the caller, the target and every
Owner, and its write compares all of them. A row's MAC is a function of its
content: a row changed and changed back compares equal, and the change that
read it lands, since its decision holds for that content. TLC explores
24,627,382 distinct states with no violation. Two variants must fail and do:
a write that compares only the row it writes, and a memory dated when the
use answers.

`log.qnt` covers commits, the wake-up, the signer and its mirror, and a
writer who can put back any MAC the vault once made, delete or replay any
entry, and cut the log. It has one tree. The two trees follow the same steps
and are signed together, so it stands for each; pruning is not modelled. TLC explores 52,048,877 states with no violation. The
bounds are small: one row, three entries, two moves by the writer. Nine
variants, each with one protection off, must fail and do. They are the
signer's requirements.

| Protection | Without it |
|---|---|
| The vault tells the signer of each entry | A deleted entry is never missed |
| A change must replace the MAC the mirror holds | False history sums to a true state |
| The log's size is compared with the signed size | A cut tail passes |
| An entry already signed is refused | A replayed entry is signed twice |
| An entry past its date is refused | An old entry is replayed later |
| A wake-up for a signed entry is dropped | A false alert |
| What is expected is noted before the read | A false alert |
| Rows and waiting entries come from one read | A false alert |
| What was signed is kept until it is moved | A false alert |

The false alerts matter because a finding only alerts. An alert nobody trusts
is worth nothing.

`rotate.qnt` covers a key rotation: a vault not yet replaced and a new one,
both changing and using through the fence, the sweep and the retirement, and
a writer who holds the old key. TLC explores 12,294,943 distinct states with
no violation: a rotation with nobody writing behind the vault raises no
alert, and the mirror never takes a row the writer made. Five variants must
fail and do.

| Protection | Without it |
|---|---|
| A change compares the policy row it read | A change read before the fence lands under the old key after it, and is refused: a false alert |
| A vault writes under the policy row's key | A new vault writes under the new key before the fence, and is refused: a false alert |
| The fence signs the changes that wait | One still waiting is refused after it: a false alert |
| Retirement waits out the vault's memory | A use answered from memory logs under a retired key: a false alert |
| After the fence, the signer takes no change under the old key | The mirror follows a forged row, and nothing ever alerts |

Trace replay holds the code to the model. Quint writes its simulated runs as
JSON, and a harness replays each step against the vault and compares the rows
after each one. `packages/vault/test/replay-change.ts` does it for a change,
on Postgres: 1,000 runs of `change.qnt`, 41,000 steps with 880 writes that
lost, in under two minutes, and it caught both faults planted in the write (one
that compares only the row it writes, one that always lands). The model must
write each refusal as a step of its own, or nothing holds the code to
refusing. The uses in those runs are replayed once the use is built.

## Upgrade from 0.14

In place, with coffre offline, and a backup as the way back (D230, as D197
had it for the 0.15 plan). No second set of tables and no switch to build:
the upgrade runs once per deployment, and Equisafe's can be down for
minutes.

Three facts about 0.14 shape it.

1. **`coffre migrate` holds no vault key.** It runs in the deployment's
   pipeline with the database owner's URL. It cannot MAC a row or open a
   value, so the vault must, at its first start.
2. **0.14 keeps some state only in its audit log:** the roles and the
   protected environments (the newest `policy.change`), revoked bindings
   (`token.unbind`), workload freezes, superseded enrollments, ended
   references.
3. **0.14's code cannot run on 0.16's tables.** So this one migration breaks
   the rule that a migration only adds, as 0.4.0's did, and `pnpm
   test:compat` is off for 0.16.0.

So the work is split in two. **The migration** does everything SQL can do
without a key. **The adoption**, in the vault at its first call, does what
needs the vault's key or the access rules' code.

### The steps

1. **Verify.** `coffre verify log`, on 0.14.7.
2. **Take coffre offline, then back up.** As the database's administrator,
   set the two runtime logins `NOLOGIN` and end their sessions. Nothing coffre
   runs can reach the database from here on. Then `pg_dump`. The backup holds
   every write 0.14 ever made.
3. **Migrate and deploy** 0.16.0, through the pipeline as for any release:
   `coffre migrate`, the vault, the app.
   - The migration is one transaction. It reshapes 0.14's tables into
     0.16's, creates the new ones, renames `audit_log` to `audit_archive` and
     drops its indexes. It turns what 0.14 kept in its log into rows, while
     the log's indexes are still there to find it: live references, revoked
     bindings, freezes, superseded codes, the run a credential was issued
     for, and who has seen which key. It leaves every starred row with an
     empty MAC, which verifies under no key.
   - It refuses a database that holds an instance while a login of the
     app's or the vault's group can still log in or has a session open. So
     a pipeline run without step 2 changes nothing, fails, and the deploy
     does not happen. A login that administers roles does not count: coffre
     never runs as one.
   - It refuses one where 0.14's vault reported a member's row changed around
     it and that report still stands, and names them: 0.16 would take the row
     as it is. Each is removed on 0.14.7 first, and added again if they
     should stay. The member may well be healthy, their genuine row put
     back: 0.14 keeps the report standing all the same.
4. **Bring it back.** Set the two logins `LOGIN`. At its first call the vault
   finds no log head and its signer's storage empty, and the signer adopts
   the database, in one transaction:
   - It writes the roles, the policy row and which environments are
     protected, from the newest `policy.change` and `settings.change` the
     vault logged in `audit_archive`, each checked against the vault's MAC,
     and whether the instance is frozen. The roles as they ship are in the
     code, not in SQL, which is why this part is the vault's.
   - It encrypts each value again, so that it names its version number and
     sensitivity. The data key is kept. It skips a version 0.14 erased, whose
     ciphertext and data key are empty: a deleted place's, a deleted personal
     config's. Such a version can still be its secret's current one, in a
     deleted place: it opens as nothing, and a use of it is refused.
   - It MACs every starred row.
   - It writes the log's first entry, which records 0.14's last hash and
     entry number, and how many rows of each table it adopted.
   - It commits. Then it fills its mirror from the rows and signs that first
     entry. A signer that dies in between finds the entry unsigned and does
     this last part again.

   Until it commits, requests answer 503 `adopting`. If anything fails (a
   policy entry whose MAC is wrong, a value that does not open), the
   transaction is undone, the 503 stays, and `/readyz` says what failed.
5. **Watch** `/readyz`, the first signed head and the first minute's check.

A fresh install runs the same code: the migration creates the tables, and
the signer adopts an empty database and the Owners its configuration names.

The adoption reads no 0.14 table but `audit_archive`: the migration leaves no
other.

### What becomes what

| 0.14.5 | 0.16.0 |
|---|---|
| `projects`, `dismissed_keys`, `identities`, `oauth_clients`, `mcp_approvals` | Kept |
| `environments` | Kept, with `protected` from the newest `policy.change`, and the upstream credentials frozen in it |
| `secrets`, `secret_references` | `secrets`. A reference still live becomes `source_id`. `current_version` becomes `versions`, how many it has had, and `current_version_id` becomes `current_version`, a number: the newest, or none |
| `secret_versions` | Kept, each value encrypted again so that it names its version number and sensitivity |
| `vault_members` | `principals`. A frozen service account says so in its row |
| `vault_grants` | `grants`, each with an id of its own, for its MAC |
| The newest `policy.change` entry | `roles` and `policy` |
| `service_bindings` | `bindings`. One the log unbound is revoked in its row, and a freeze is a field of the row |
| `credentials` | Kept, but for those a day past their expiry. A frozen session says so in its row |
| `mcp_connections` | `credentials` of kind `mcp`, the live ones only, with their approvals |
| `enrollments` | `enrollment_codes`. A superseded code says so in its row |
| `consumed_tokens` | `spent_id_tokens`, those spent in the last two hours |
| `vault_releases` | `exposures`, built again from every read in the log: 0.14 kept a day of them |
| `device_authorizations` | Dropped. A device login under way starts again |
| `capped_alerts` | Dropped. The signer keeps what it alerted |
| `audit_log` | `audit_archive`, with one of its indexes, by action, which finds the adoption what it reads |
| `audit_chain_head` | Dropped. Its last hash and number are in the log's first entry |

One fact 0.14's pages read from the log moves into the credential's row: the
CI run that issued it.

The migration is `0022_smaller_vault.sql`. `pnpm test:upgrade` holds it to
this table: it upgrades a 0.14 database with a row of every kind, on a
cluster of its own, and requires that database, one migrated from nothing and
one made from `schema.ts` alone to have the same schema, line for line.

### What does not change for anyone

- **Tokens and sessions.** A token is found by its SHA-256, as before, so
  every live session, service token, personal token and workload credential
  keeps working. Nobody signs in again, and no sidecar enrolls again.
- **Clients.** 0.16.0's HTTP API takes 0.14.7's CLI, Action, sidecar image
  and client package. This is a requirement on the build, and conformance
  must hold it: the clients are upgraded after the server, not with it.
- **Keys.** The vault key and the app key stay as configured.

### Going back

- **Before the migration:** set the two logins `LOGIN`. Nothing changed.
- **After it:** restore the backup, deploy 0.14.7, set the two logins
  `LOGIN`. A login's `NOLOGIN` is the cluster's, not the database's, so the
  restore leaves it as it is. What was written on 0.16 since is lost.
- **To upgrade again after going back:** empty the signer's storage first. A
  signer adopts only a database with no log head, and only with its own
  storage empty.

### What it trusts

The adoption takes the database as it finds it. It checks that every value
opens, and the MAC of the two log entries it reads. It does not check 0.14's
seal on a member's row. That check would close nothing: the vault cannot
check the rows 0.14's app signed with the app key, which it does not hold,
so a writer refused a forged member would forge a session for a real Owner
instead. So the runbook verifies the log on 0.14.7 first, and the stretch
from that verification to the adoption, minutes, is the one where a database
writer's edit would be adopted as genuine.

### Downtime

From step 2 to the adoption's commit: the backup, the pipeline's run (the
migration and two deploys), then the adoption. For Equisafe I expect a few
minutes, most of them the pipeline's, and the rehearsal measures it.

### Refused

- A database below 0.14.5's last migration: upgrade to 0.14.7 first.
- A deployment that never ran 0.14: there is no path from an earlier
  release.

### Rehearsal, before any release

On a copy of Equisafe's database, in a throwaway deployment. The copy only
adopts with Equisafe's real vault key, so Erwin puts that key into the
throwaway vault himself. It runs the steps above as written, measures the
migration, the adoption and the downtime, compares the row counts with the
table above, runs 0.14.7's sidecar against the result, and goes back once
from the backup.

### At Equisafe

- `vault/wrangler.jsonc` gains the signer's Durable Object binding and its
  migration. `coffre update` writes both.
- `app/wrangler.jsonc` keeps `CoffreAnchor` until the release after, so that
  going back finds its storage.
- The deploy workflow is unchanged: it migrates, then deploys the vault,
  then the app.
- The backend's sidecar stays on its 0.14 image until the Workers have run
  0.16.0 for a while.

## Build order

0.16 starts from `release/0.14`, the code Equisafe runs. The 0.15 line stays
on `main` as the source to port from, and nothing merges from it.

The base work merges into `0.16`, which stays green. The core is built on
`0.16-core`, which is not: its first commit replaces the schema, and 0.14's
vault and server do not build on it. Each piece of the core is held to its
own tests there, and `0.16-core` merges into `0.16` once the server has moved
and everything is green again.

1. **A smaller base.** Postgres as the only database, which deletes SQLite's
   schema, migrations and test engine. One Postgres driver, postgres.js. Local
   checks and a release gate in place of CI on every pull request. Each of
   these halves what the next steps must build or test.
2. **The core.** The schema and its migration, the vault's two shapes, the
   signer, the models in `pnpm formal`, trace replay in the tests, and the
   server's calls moved to the new contract. 0.14's audit chain and its TLA+
   models go.
3. **The features 0.15's line added**, each written once against the new
   contract: passkeys at sign-in, proxy routes saved per environment with
   their Proxy tab, the Terraform provider, the pages' rework. Then the small
   fixes, each checked against 0.14's code first, since some fixed bugs 0.14
   never had.

The source for step 3 is main's changelog since 0.14.5, 136 entries. Those
that begin "0.15's" describe the design this replaces and are not ported.

## Still to design

- The signer on Node. 0.16.0 is tested on Workers only.
- The minute check past 100,000 rows.
- The app key's rotation, now that it signs no row.
- The offboarding report after a restore. `exposures` says when someone last
  saw a key, not which version. 0.14's report followed restores: Bo saw
  version 1, version 3 restores version 1's value, so Bo knows the current
  value. A rule that compares his last read with the current version's date
  would call it rotated. Settled with the report's page.
- Losing the signer's storage: how an Owner tells the signer to take the
  database as it is, and what that is logged as. 0.14 has the same question
  for its anchor.

## Decisions

| | Decision |
|---|---|
| D215 | Against a database writer without the key, detection within about a minute is enough. A use does not check the log. |
| D216 | A finding alerts. Coffre keeps serving. |
| D217 | The four relaxations above. |
| D218 | The vault's short memory is configurable, 2 seconds by default. |
| D221 | A change replies at its commit. It does not wait for the signature. |
| D222 | Old history deleted in depth is caught by the rolling re-check or a full verify, not within the minute. |
| D223 | The wake-up carries the entry's hash, for changes and for uses. |
| D224 | Models in Quint, checked exhaustively with TLC. |
| D225 | Built on the 0.14 line, with the 0.15 line's features ported over. |
| D226 | 0.14.7 carries the last 0.14 features, and is the release 0.16.0 matches. |
| D227 | 0.16.0 is the new core under 0.14.7's features. The 0.15 line's features follow as 0.16.x. |
| D228 | At most two workers, on the base work only. The core has one author. |
| D229 | Changes are kept for good. Uses are pruned after 90 days by default, configurable. |
| D230 | The upgrade from 0.14 converts in place, with coffre offline and a backup as the way back. |
| D231 | Sign-ins age out with the uses. A token a person makes is kept. |

Decided before this design and kept: Postgres is the only database, 0.16.0 is
tested on Workers only, and the bulk cap is 1,000 distinct keys per principal
per 15 minutes, sliding and configurable.
