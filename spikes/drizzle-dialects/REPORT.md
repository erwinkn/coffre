# One set of Drizzle queries across PostgreSQL, MySQL, and SQLite

## Recommendation

Use one typed query module, three concrete Drizzle schemas, and a small dialect
adapter. Type the query module against one canonical schema and database type
(PostgreSQL in this prototype), then adapt each real database and schema at one
audited boundary. At runtime the database and table objects always come from the
same dialect.

This is the only option I found that meets all three constraints at once:

- a query is written once;
- normal query code retains Drizzle's input and result inference;
- dialect differences stay in one small module.

Drizzle does not publish a dialect-neutral database or table type. The cost of
this pattern is therefore an intentionally unsound boundary cast. In the
prototype, all three casts are in `src/portable.ts`. That boundary must be
guarded by two tests: a compile-time comparison of selected row types, and a
runtime comparison of table names, columns, nullability, and primary keys.
Every shared query must also run against every supported engine in CI.

Do not generate three repositories or use `any` throughout the adapter. The
former makes roughly 100 query sites three-way maintenance; the latter loses the
type safety this work is meant to buy. Also do not build a new cross-dialect
query AST on top of Drizzle. That would amount to maintaining a small ORM.

Here is a real query from the prototype. This exact builder chain ran unchanged
on all three databases and inferred the same result type:

```ts
const rows = await database
  .select({
    project: schema.projects.slug,
    environment: schema.environments.slug,
    key: schema.secrets.key,
    version: schema.secretVersions.version,
    ciphertext: schema.secretVersions.ciphertext,
  })
  .from(schema.projects)
  .innerJoin(schema.environments, eq(schema.environments.projectId, schema.projects.id))
  .innerJoin(schema.secrets, eq(schema.secrets.environmentId, schema.environments.id))
  .innerJoin(
    schema.secretVersions,
    eq(schema.secretVersions.id, schema.secrets.currentVersionId),
  )
  .where(and(
    eq(schema.projects.slug, projectSlug),
    eq(schema.environments.slug, environmentSlug),
    eq(schema.secrets.key, key),
    isNull(schema.projects.archivedAt),
    isNull(schema.environments.archivedAt),
    isNull(schema.secrets.archivedAt),
  ));
```

IDs should be generated by the application before inserts. This removes the
largest routine difference: MySQL has no `INSERT ... RETURNING`. Operations
whose builder API genuinely differs, such as upsert and locking, are semantic
methods on the dialect adapter rather than branches in service code.

## What I inspected

### Drizzle 0.45.2

I inspected the installed package, not just the documentation. It has separate
`PgDatabase`, `MySqlDatabase`, and `BaseSQLiteDatabase` classes and separate
table families. PostgreSQL and SQLite inserts expose `returning()` and
`onConflictDoUpdate()`. MySQL exposes `onDuplicateKeyUpdate()` and does not
expose `returning()`. PostgreSQL and MySQL select builders expose row locking;
SQLite does not.

The installed package exports drivers for `better-sqlite3`, libSQL, D1, and
Durable Object SQLite. It does not export a `node:sqlite` driver. I used
`@libsql/client` 0.18.0 because it works without a native install script.
`better-sqlite3` would require allowing its native build in a workspace that
currently has `ignoreScripts`, and Durable Object SQLite only exists in the
Workers runtime.

The public docs confirm the split upsert APIs: PostgreSQL and SQLite use
`onConflictDoUpdate`, while MySQL uses `onDuplicateKeyUpdate`
([Drizzle upsert guide](https://orm.drizzle.team/docs/guides/upsert)). The
insert documentation also scopes returning support by dialect
([Drizzle insert documentation](https://orm.drizzle.team/docs/insert)).

### Drizzle v1

I downloaded and inspected `drizzle-orm@1.0.0-beta.22`, the `beta` tag on
2026-09-27. It adds a `node-sqlite` driver, but it does not solve this problem:
MySQL and SQLite still have separate database classes and their insert builders
still expose `onDuplicateKeyUpdate` versus `onConflictDoUpdate`. The newer
PostgreSQL API is separately rooted at `PgAsyncDatabase`. The published v1
upgrade is about the migration-folder redesign and relational query API changes,
not a common dialect type
([Drizzle v1 upgrade guide](https://orm.drizzle.team/docs/upgrade-v1)).

There is therefore no reason to adopt a beta or release candidate merely for
cross-dialect queries. Re-evaluate the stable v1 release for its `node:sqlite`
driver when coffre is ready to upgrade.

### Better Auth

Better Auth's Drizzle adapter supports a runtime `provider` of `pg`, `mysql`, or
`sqlite`, but it is not a type-safe precedent for coffre. Its schema is
`Record<string, any>`, its database abstraction is broad, and it branches at
runtime for differences such as MySQL's missing `RETURNING`. Its current warning
also recommends application-generated IDs for reliable MySQL behavior. This is
the same runtime shape as the recommended adapter, but coffre should keep the
unsoundness in three explicit boundary functions rather than allow it through
the implementation
([Better Auth adapter source](https://github.com/better-auth/better-auth/blob/main/packages/drizzle-adapter/src/drizzle-adapter.ts)).

### Other patterns considered

| Pattern | Result |
| --- | --- |
| Canonical typed query module plus boundary adapter | Recommended. One query body and useful inference; requires a narrow cast and strong three-engine tests. |
| Three repositories behind one interface | Fully honest to Drizzle's types, but repeats each query and makes behavioral drift likely. It fails the “write once” requirement. |
| One generic schema factory | Can share small column helpers, but cannot erase dialect-specific table, constraint, index, and foreign-key types without moving the casts into a more complicated place. Drizzle Kit still needs three concrete exported schemas. |
| Swap table objects under queries written for one dialect | This is the recommended pattern only when the database object is swapped with the tables and all casts are centralized. Swapping tables alone is unsafe. |
| Dynamic schema plus `any`, as in general-purpose adapters | Compact, but query results and inputs stop being checked. Not suitable for coffre. |
| A custom dialect-neutral DSL | Could be sound, but would duplicate Drizzle's query builder and require its own compiler and test matrix. Disproportionate to this library. |

## Prototype

The prototype covers six tables:

- `projects` and `environments`;
- `secrets` and `secret_versions`, including ciphertext and wrapped-DEK bytes;
- `audit_chain_head` and `audit_log`, including typed JSON metadata and hashes.

It runs these operations through Drizzle builders, with no driver `.query()`
calls and no handwritten query fragments:

- an application-ID project insert without `RETURNING`;
- a transaction that inserts an environment, secret, and version, then points
  the secret at its current version;
- a four-table filtered join returning a 70 KiB ciphertext (large enough to
  prove that MySQL `BLOB` would be wrong and `LONGBLOB` works);
- a count aggregate;
- an upsert;
- JSON insertion and retrieval;
- an audit append that locks a head row, reads the previous hash, computes the
  next hash over canonical JSON in the application, inserts the row, and
  advances the head;
- 24 audit appends started concurrently, followed by a complete sequence and
  hash-chain verification.

The important audit design change is the permanent singleton
`audit_chain_head` row. PostgreSQL and MySQL both lock it with `FOR UPDATE`.
This is more portable than a PostgreSQL advisory lock, and unlike locking the
latest audit row it also works when the log is empty. Local SQLite/libSQL uses
the same query body but its adapter serializes writer transactions with a FIFO
promise queue.

The prototype's hash function is deliberately small and exists to verify chain
ordering; production conversion should keep using `packages/core`'s keyed,
canonical audit-chain implementation.

The first SQLite concurrency run is useful negative evidence: launching 24
libSQL transactions directly produced `SQLITE_BUSY`. Relying on “SQLite has one
writer” does not mean the driver queues writers for the application. After the
queue was added to the SQLite adapter, all 24 appends passed and the chain was
linear. A production SQLite adapter should own this queue for the whole database
instance, not create one per repository.

The only deliberately unsafe code is in `src/portable.ts`:

```ts
export function asLogicalDatabase(database: unknown): LogicalDatabase {
  return database as LogicalDatabase;
}
```

The MySQL and SQLite connectors pass their actual database and their matching
actual schema through that boundary. Query execution is compiled by the actual
database's dialect; the canonical type exists only for TypeScript.

## Migrations and schema parity

Drizzle Kit is dialect-specific. Keep three configs and three migration trees:

```text
drizzle.postgres.config.ts -> schema.postgres.ts -> migrations/postgres
drizzle.mysql.config.ts    -> schema.mysql.ts    -> migrations/mysql
drizzle.sqlite.config.ts   -> schema.sqlite.ts   -> migrations/sqlite
```

`drizzle-kit generate` reads a schema and its last snapshot, computes a diff,
and writes dialect SQL. Its docs explicitly support multiple config files
([generate](https://orm.drizzle.team/docs/drizzle-kit-generate),
[migrate](https://orm.drizzle.team/docs/drizzle-kit-migrate)). Production
release tooling should require all three generated trees to change together.

`schema-parity.test.ts` checks two different contracts:

1. at compile time, every selected table row has exactly the same TypeScript
   shape in all three schemas;
2. at runtime, the three Drizzle schemas expose exactly the same tables,
   columns, nullability, and primary keys.

The test intentionally does not require inferred insert types to be identical.
Drizzle marks SQLite integer primary keys optional on insert because SQLite may
generate a rowid, even when coffre always supplies the value. Shared application
DTOs such as `NewProject` are the authoritative insert contracts.

For the full schema, extend the runtime contract to compare foreign-key targets,
unique constraints, and indexes by logical purpose. Do not compare physical SQL
types literally: `uuid`/`varchar(36)`/`text` and
`bytea`/`blob`/`blob` are deliberately different representations of the same
application type.

## Dialect differences and where they belong

| Difference | PostgreSQL | MySQL | SQLite | Home |
| --- | --- | --- | --- | --- |
| Table/database types | `pgTable`, `PgDatabase` | `mysqlTable`, `MySqlDatabase` | `sqliteTable`, `BaseSQLiteDatabase` | Three schema files and connector casts |
| IDs | `uuid` | `varchar(36)` | `text` | Schema files; generated in application |
| Encrypted bytes/hashes | `bytea` | `longblob` | `blob` | Schema files/custom column types; `BLOB` is too small for coffre's maximum plaintext plus encryption overhead |
| JSON | `jsonb` | `json` | JSON-mode `text` | Schema files; shared app type |
| Timestamps | `timestamptz` | `datetime(3)` | integer milliseconds | Schema files; application uses `Date`; MySQL connector fixes its timezone to UTC |
| String bounds | unbounded `text` is available | indexed keys need bounded `varchar` | `text` | Schema files and shared validation |
| Insert result | `RETURNING` exists | no `RETURNING` | `RETURNING` exists | Avoid in shared code; application IDs or adapter follow-up |
| Upsert | `onConflictDoUpdate` | `onDuplicateKeyUpdate` | `onConflictDoUpdate` | `DialectOperations.upsertProject`-style methods |
| Row lock | `FOR UPDATE` | `FOR UPDATE` | none | Adapter lock method; SQLite writer queue |
| Advisory lock | available | no equivalent used | none | Replace with lock rows, such as `audit_chain_head` |
| Writer concurrency | row locks | row locks | one writer; libSQL returned `SQLITE_BUSY` | One process-wide queue in SQLite adapter |
| Transaction options | supports read-only/repeatable-read options | syntax and capabilities differ | modes such as deferred/immediate | Adapter transaction methods |
| DDL rendering | constraints and indexes in PostgreSQL form | MySQL constraint/index form | many constraints become indexes | Generated per-dialect migrations |
| SQLite integer PK insert inference | required | required | inferred optional due to rowid | Explicit application insert DTOs |

The full coffre conversion will hit additional differences already visible in
the present PostgreSQL schema and SQL:

- PostgreSQL regex checks and `octet_length` checks need dialect-specific schema
  expressions, or preferably shared application validation plus the simplest
  portable database checks.
- Partial indexes are not available in MySQL. Active-row uniqueness must be
  modeled explicitly, for example with an active sentinel/generated column, or
  with a different lifecycle model. This belongs in the schemas and migrations,
  not the repositories.
- PostgreSQL `ANY(array)` becomes Drizzle `inArray`, which is a shared query.
- `array_agg`, lateral joins, `FILTER`, `IS NOT DISTINCT FROM`, interval
  arithmetic, `NULLS FIRST`, and PostgreSQL JSON casts/operators occur in the
  current services. Prefer portable Drizzle builder operations and application
  aggregation. Where the engines have materially different algorithms, expose
  one narrowly named adapter capability rather than putting a dialect switch in
  a service.
- JSON fields that participate in joins or filters should become ordinary typed
  columns. Recreating PostgreSQL `jsonb ->>` predicates three ways is slower,
  less indexable, and spreads dialect knowledge.
- Case-insensitive identity matching should store one canonical normalized
  value. Depending on `lower()` plus engine collation rules is not a stable
  three-dialect contract.
- The current `UPDATE ... RETURNING` call sites need either app-known keys plus
  a separate shared select, or an adapter operation when atomic returned state
  matters.

These are schema/modeling tasks, not evidence that every repository should be
duplicated.

## Cloudflare D1

D1 still does not support the interactive transaction needed by the present
audit algorithm. Its Worker API documents `batch()` as an atomic transaction,
but all statements must be prepared before the batch runs; D1 otherwise operates
in auto-commit
([D1 database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)).
The audit append must read the current hash, compute a new hash in JavaScript,
and only then issue the insert and head update. That dependency cannot be put in
one predeclared batch.

Drizzle 0.45.2 does not bridge the gap. Its D1 `transaction()` implementation
issues SQL `BEGIN`, `COMMIT`, and `ROLLBACK`, which D1 rejects. The current
Drizzle issue remains open
([drizzle-orm #2463](https://github.com/drizzle-team/drizzle-orm/issues/2463)).

An optimistic protocol may be possible: read the head, compute the row, then
atomically batch an insert keyed by the expected sequence and a guarded head
update, retrying on a unique conflict. That is a different concurrency
algorithm with subtle failure invariants. It was not part of this prototype and
must not be claimed safe without a dedicated D1/Miniflare concurrency spike.

Durable Object SQLite is the proven Cloudflare fit. Cloudflare exposes
`transactionSync()` for SQLite-backed Durable Objects, and Drizzle 0.45.2's
`durable-sqlite` session delegates to it. Cloudflare documents that the callback
is synchronous, atomic, and rolls back on exceptions
([Durable Object SQLite transactions](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)).
The audit hash uses synchronous CPU work and synchronous storage calls, so it
fits this model. The conclusion in `docs/architecture.md` is correct: do not
advertise D1 as a coffre app database; use Durable Object SQLite for the
all-Cloudflare deployment.

## Conversion estimate

The current services contain 102 syntactic `.query(...)` call sites across seven
files; 26 are explicit `BEGIN`, `COMMIT`, or `ROLLBACK` calls. Some remaining
sites select among several SQL bodies, so “about 120 queries” remains a fair
description of the behavioral surface.

A realistic solo estimate is 4–6 engineering weeks:

- 4–6 days for the full three-dialect schemas, constraint decisions, migration
  trees, and parity contract;
- 8–12 days to convert and behavior-test the ordinary reads and writes;
- 4–6 days for locks, upserts, returned-state operations, sync leasing,
  offboarding/sign-in races, and the complex admin queries;
- 3–4 days for three-engine CI, fixture cleanup, migration checks, and failure
  testing.

Add another dedicated spike before adding D1. The main schedule risk is not the
builder syntax; it is finding the PostgreSQL-specific queries that encode a
business invariant and choosing a portable model instead of transliterating the
SQL three times.

## Risks and guardrails

- The canonical cast is not guaranteed by Drizzle's public API. Pin Drizzle,
  run the complete three-engine suite on every upgrade, and keep the cast module
  tiny and documented.
- Never allow a connector to pair one dialect's database with another dialect's
  tables. Construct both together and expose them as one adapter value.
- Keep shared queries to builder APIs supported by all three dialects. A code
  review rule should reject dialect checks and raw query fragments outside the
  schema/adapter layer.
- Make the SQLite writer queue process-wide for a database instance. Multiple
  independent queues would reintroduce `SQLITE_BUSY` and audit races. An
  on-disk SQLite deployment with multiple OS processes needs a single-writer
  coordinator as well; an in-memory promise queue cannot serialize processes.
- Treat schema parity as semantic. Physical type names and index implementation
  will differ, while logical constraints must not. Size equivalence matters:
  MySQL `BLOB` is not a safe stand-in for PostgreSQL `bytea` when coffre accepts
  a 64 KiB string before UTF-8 encoding and authenticated-encryption overhead;
  use `LONGBLOB`.
- Keep the audit concurrency test at more than one connection and verify every
  hash, not just the row count.

The prototype answers the open question positively, with one caveat: Drizzle
does not make this pattern formally sound. A narrow, audited cast plus generated
per-dialect schemas and mandatory real-engine tests is the smallest practical
way to write coffre's queries once without giving up useful typing.
